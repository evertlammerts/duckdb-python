DuckDB for Python

duckdb is the DuckDB engine inside your Python process: an analytical SQL database that runs in memory or on a file, with no server and no dependencies. A query is a plain value you build in Python and run on a connection. Two more modules share the engine: duckdb.dbapi, a strict DB-API 2.0 interface, and duckdb.compat, the previous client's interface for code that already exists.

Start here

import duckdb
from duckdb import col, table, count_all

con = duckdb.connect()
con.run("CREATE TABLE orders (customer VARCHAR, region VARCHAR, total DECIMAL(6,2))")
con.run("INSERT INTO orders VALUES ('acme', 'emea', 1400), ('bolt', 'amer', 320), ('acme', 'emea', 2600)")

orders = table("orders")
orders.filter(col("total") > 1000).rows(con)
# [('acme', 'emea', Decimal('1400.00')), ('acme', 'emea', Decimal('2600.00'))]

con is a connection: a database, open, in memory. orders is a plan: a query that has not run. con.run() runs a statement and returns the number of rows it changed. rows(con) runs a plan on a connection and returns its rows as tuples. A plan holds no connection, so orders runs on any database that has a table called orders.

spent = orders.group_by("region").agg(col("total").sum().alias("spent"), count_all().alias("orders"))
spent.sort(col("spent").desc()).show(con)

│ region  │ spent         │ orders │
│ VARCHAR │ DECIMAL(38,2) │ BIGINT │
├─────────┼───────────────┼────────┤
│ emea    │ 4000.00       │ 2      │
│ amer    │ 320.00        │ 1      │

Each verb returns a new plan and leaves the old one alone. Nothing runs until a method takes a connection. The rest is in Frames and Plans.

duckdb, duckdb.dbapi and duckdb.compat

Each of the three is a complete way to use DuckDB. They share the engine and the exception classes, and nothing else; a program picks one and stays on it.

duckdb: the main API

duckdb.connect() opens a database. duckdb.table(), duckdb.sql() and the file readers make plans; col() and its relatives make expressions. A connection is somewhere to run things: it has run(), transaction(), interrupt(), create_macro(), create_function(), duplicate() and close(), and nothing else. There is no execute(), no fetch family and no cursor(). Rows come out of plans.

import duckdb
from duckdb import col, table

con = duckdb.connect("shop.db")
table("orders").filter(col("total") > 1000).rows(con)

duckdb.dbapi: PEP 249, strictly

A connection with cursor(), commit() and rollback(); a cursor with execute(), executemany(), fetchone(), fetchmany(), fetchall() and description. paramstyle is qmark. Cursors share their connection's transaction, which the specification requires and the previous client could not do. The execute and fetch vocabulary is here because PEP 249 asks for it, and it lives in its own module so that the main API owes it nothing.

import duckdb.dbapi as dbapi

con = dbapi.connect("shop.db")
cur = con.cursor()
cur.execute("SELECT customer, total FROM orders WHERE total > ?", (1000,))
cur.fetchall()

duckdb.compat: the previous client, for migration

connect() returns a connection that executes and fetches directly, with description and rowcount on the connection itself; sql(), table() and query() return relations that compose SQL text; a module level default connection backs duckdb.compat.execute() and its siblings. Old habits are reproduced on purpose, the questionable ones included, so that code written against the old client keeps running while it moves. import duckdb does not load this module; ask for it by name.

import duckdb.compat

con = duckdb.compat.connect("shop.db")
con.execute("SELECT customer, total FROM orders WHERE total > ?", [1000]).fetchall()
con.table("orders").filter("total > 1000").fetchall()

New code uses the main API. The other two exist for code that already speaks PEP 249 or the previous client. A duckdb.compat connection is a duckdb connection with the old client's interface added, so a plan runs on it as well. A duckdb.dbapi connection is not, and a plan handed one is refused with TypeError; to run a plan through the DB-API, execute plan.render() on a cursor.

Installing and connecting

The package is called duckdb. It needs Python 3.12 or later and nothing else: importing it loads no other library, and the engine ships inside the wheel.

pip install duckdb

opening a database

con = duckdb.connect()                                    # in memory
con = duckdb.connect("shop.db")                           # a file, created if it does not exist
con = duckdb.connect("shop.db", access_mode="read_only")  # a setting, applied as the database opens
con = duckdb.connect(threads=2)

The default is an in-memory database, which lives as long as a connection to it is open. A path opens a file, creating it when it is not there. Keyword arguments are DuckDB settings, applied as the database opens; the value is passed as text, and a setting the engine does not know is refused by name. Settings that can only be chosen at open time, access_mode among them, go here. The rest can also be changed later with con.run("SET ...").

One process opens a file once. A second duckdb.connect("shop.db") while the first is open is refused by the engine. For more connections to the same database, con.duplicate() gives a second one with its own transaction.

closing

with duckdb.connect("shop.db") as con:
    table("orders").count(con)

close() releases the database and closes every result the connection is still reading. A connection is a context manager, so a with block does that on the way out. A closed connection refuses further work with InterfaceError. Plans built while it was open are unaffected; they hold no connection.

Versions

>>> import duckdb
>>> duckdb.__version__
'0.0.1.dev0'
>>> duckdb.duckdb_version()
'v2.0.0-dev83383'

__version__ is this package. duckdb_version() is the DuckDB engine linked into it. They are versioned and released separately, so neither can be read from the other: a package release may carry a new engine or the same one. A problem in SQL belongs to the engine version, a problem in rows() to the package version; report both. duckdb.library_version() is the same engine string, read from the extension module directly.

Errors

Every error the engine reports arrives as a class from duckdb.exceptions. The hierarchy is rooted in PEP 249. Error is at the top. Under it, InterfaceError is misuse of the package itself and DatabaseError is anything the database reports. Under DatabaseError sit the specification's DataError, OperationalError, IntegrityError, InternalError, ProgrammingError and NotSupportedError. Under those, one concrete leaf for each engine error code that carries a meaning of its own.

from duckdb import exceptions

try:
    table("nope").rows(con)
except exceptions.CatalogError as error:
    print(error)      # Catalog Error: Table with name nope does not exist!
ParserError
A ProgrammingError. The SQL could not be parsed.
CatalogError
A ProgrammingError. A referenced object does not exist, or already does.
InvalidInputError
A ProgrammingError. An argument was malformed or out of range.
ConfigurationError
A ProgrammingError. A setting was unknown, invalid or not permitted.
ConversionError
A DataError. A value could not be converted to the requested type.
ConstraintError
An IntegrityError. A key, NOT NULL or CHECK constraint was violated.
IOError / OutOfMemoryError / ConnectionError / TransactionError / InterruptError
Each an OperationalError: reading or writing failed; an allocation failed; the connection is no longer usable; the transaction could not proceed; the query was interrupted. A database file already in use, by another connection or another process, is an OperationalError too.
FatalError
An InternalError. The database is no longer usable and must be reopened.

Catch a leaf when the program can do something about that case, and DatabaseError when it cannot. A code the engine adds later, one this package has never seen, arrives as a plain DatabaseError rather than being lost. The message is the engine's own, as it would be given to any client; the one above goes on to suggest orders and point at the SQL.

A mistake caught before the engine sees the query is Python's own TypeError or ValueError: a string where filter wants an expression, and between two expressions, a plan handed a dbapi connection. NeedsConnection, raised when a plan is asked something only the engine can answer and no connection was given, is a ValueError.

duckdb.dbapi exports the same classes under the names PEP 249 lists, so except dbapi.Error and except exceptions.Error catch the same thing. duckdb.compat aliases the previous client's names, CatalogException and the rest, to these classes.

A Ctrl‑C while a query runs cancels it and raises KeyboardInterrupt. con.interrupt() from another thread cancels the running query, which fails with InterruptError.

The SQL dialect, its functions and its settings are DuckDB's own, documented at duckdb.org; this manual covers the Python package around them. Where the engine refuses something, the message is the one it gives every client.
