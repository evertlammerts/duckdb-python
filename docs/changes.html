Coming from DuckDB 1.5.6

This page lists what changes when you move Python code from the duckdb 1.5.6 package to this one, whose DuckDB engine is version 2.0. Each item shows what you wrote before and what to write now. It covers the Python side: connecting, running queries and getting results. Changes in DuckDB's SQL itself, and in its database file format, are in DuckDB's release notes.

The short version

  • There is no default connection. You open one with frame.connect() and pass it to whatever runs a query. duckdb.sql(...), duckdb.connect() and the other functions on the duckdb module are gone, apart from duckdb_version() (see Versions).
  • sql(text) builds a query without running it. The query runs when you give it a connection: sql(text).rows(con).
  • Getting results has new names: fetchall() is rows(con), df() is to_pandas(con). arrow() gave you a reader that hands out the result in batches; to_arrow(con) gives you the whole result as a pyarrow Table, and to_reader(con) gives you the reader.
  • A query no longer finds a pandas or polars variable by its name. Register it first: con.register("df", df).
  • The classic execute(), cursor and fetchall() style is in its own module, duckdb.dbapi. Use it to keep SQL strings with ? or $name placeholders, or for a tool that needs a DB-API driver. There, changes become final only when you call commit(), and all cursors of a connection share that one transaction.
  • Python functions match an argument written as x := 1 to the parameter x (1.5.6 matched by position), and they use their Python defaults.
  • Error classes have new names that end in Error: CatalogException is now CatalogError, in duckdb.exceptions.
  • A TIMESTAMP WITH TIME ZONE fetched as Python rows comes back in UTC, with the standard library's datetime.timezone. You no longer need pytz.

The examples on this page

Each pair of examples shows the 1.5.6 code on the left and the code to write now on the right. Each side builds on its own setup, shown here, and results appear in comments the way the Python prompt prints them:

DuckDB 1.5.6
import duckdb

con = duckdb.connect()
con.execute("CREATE TABLE orders (customer VARCHAR, region VARCHAR, total INTEGER)")
con.execute("INSERT INTO orders VALUES ('acme', 'emea', 1400), ('bolt', 'amer', 320), ('acme', 'emea', 2600)")
rel = con.table("orders")
now
from duckdb import frame
from duckdb.frame import sql, table, col, param

con = frame.connect()
con.run("CREATE TABLE orders (customer VARCHAR, region VARCHAR, total INTEGER)")
con.run("INSERT INTO orders VALUES ('acme', 'emea', 1400), ('bolt', 'amer', 320), ('acme', 'emea', 2600)")
plan = table("orders")

Importing and connecting

import duckdb gives you three modules: duckdb.frame to build and run queries, duckdb.dbapi for the classic database interface, and duckdb.exceptions for the error classes. The duckdb module itself has no connect(), sql(), execute(), read_csv() or create_function().

import duckdb

duckdb.sql("SELECT 42").fetchall()
# [(42,)]
now
sql("SELECT 42").rows(con)

Running SQL and getting results

In 1.5.6, con.sql(text) gave you a relation: a query object tied to that connection. A SELECT in it ran each time you fetched from it, and a statement such as CREATE ran at once. Now sql(text) gives you a plan: a query that has not run and belongs to no connection, until you give it one. Methods that return results, such as rows(con) and to_pandas(con), run it each time you call them. iter_rows(con) starts it when you start looping, and to_polars(con, lazy=True) when you collect. plan.on(con) only attaches a connection. A plan does not belong to any connection, so you can run the same plan on several databases.

DuckDB 1.5.6
pairs = con.sql("SELECT 1 AS x, 'a' AS y")
pairs.fetchall()
pairs.df()
con.sql("CREATE TABLE t (x INTEGER)")
now
pairs = sql("SELECT 1 AS x, 'a' AS y")
pairs.rows(con)
pairs.to_pandas(con)
con.run("CREATE TABLE t (x INTEGER)")

A statement that returns no rows, such as CREATE, INSERT or SET, goes to con.run(text). It runs and takes effect at once, and returns the number of rows it changed. Do not use it to get rows: for a query it throws the rows away, so con.run("SELECT 42") returns 0. plan.on(con) attaches a connection to a plan, so that plan.on(con).rows() needs no argument.

Building queries in Python

The 1.5.6 relation methods (project, filter, aggregate and so on) are replaced by plan methods with similar names. The biggest difference is what a plain string means.

  • A string where a method expects a column names that column. This holds for select, group_by, sort, drop and the like: select("total") picks the column total. select("total * 2") looks for a column literally called total * 2 and fails. Write col("total") * 2, or wrap SQL in sql_expr("total * 2"). sql_expr is one piece of SQL inside a plan, such as a condition or a computed column; sql(text) is a whole query.
  • A string inside an expression is a value. col("region") == "emea" compares with the text emea. To mean a column, write col(...).
  • filter() takes an expression. filter("total > 1000") is refused with TypeError. Write filter(col("total") > 1000), or filter(sql_expr("total > 1000")).
  • Combine conditions with & for AND, | for OR and ~ for NOT, with parentheses around each comparison: (col("total") > 1000) & (col("region") == "emea"). Python's and, or and not raise TypeError.
  • Find NULLs with .is_null(). NULL is SQL's missing value, and Python rows show it as None. == and != never match it: col("region") == None matches no rows, and col("region") != "emea" leaves out the rows whose region is NULL. To keep those, write (col("region") != "emea") | col("region").is_null().
DuckDB 1.5.6
rel.filter("total > 1000").project("customer, total * 2")
rel.aggregate("sum(total)", "customer")
now
from duckdb.frame import sql_expr

plan.filter(col("total") > 1000).select("customer", col("total") * 2).rows(con)
# [('acme', 2800), ('acme', 5200)]
plan.filter(sql_expr("total > 1000")).select("customer", sql_expr("total * 2")).rows(con)
# [('acme', 2800), ('acme', 5200)]
plan.aggregate(col("total").sum(), group_by="customer").rows(con)
# [('bolt', 320), ('acme', 4000)], in no particular order

A join with on=lambda left, right: ... calls that small function with its two sides. The function returns the condition that says which rows match, and left["customer"] means the column customer of the left side:

con.run("CREATE TABLE customers (id VARCHAR, country VARCHAR)")
con.run("INSERT INTO customers VALUES ('acme', 'NL'), ('bolt', 'US')")
both = plan.join(table("customers"), on=lambda left, right: left["customer"] == right["id"])
both.select("customer", "total", "country").sort("total").rows(con)
# [('bolt', 320, 'US'), ('acme', 1400, 'NL'), ('acme', 2600, 'NL')]

Querying Python data

In 1.5.6 a query could name a pandas DataFrame, a polars DataFrame or an Arrow table that was a variable in your code, and DuckDB would find it. That no longer happens. Register the object under a name first:

DuckDB 1.5.6
import pandas as pd

df = pd.DataFrame({"x": [1, 2]})
duckdb.sql("SELECT sum(x) FROM df").fetchall()
# [(3,)]
now
import pandas as pd

df = pd.DataFrame({"x": [1, 2]})
con.register("df", df)
sql("SELECT sum(x) FROM df").rows(con)
# [(3,)]
  • Without register, the query fails with CatalogError: Table with name df does not exist!.
  • Registering does not copy the data into the database. Each query reads the DataFrame as it is at that moment, and the name is gone when the database closes. To keep a copy as a real table, create one: table("df").create(con, "saved").
  • Registering keeps the object you passed, not the variable. If you assign a new DataFrame to df, as in df = df.assign(...), queries still read the old one until you call con.register("df", df) again.
  • If a real table has the same name, the real table wins. Pick a name no table has.
  • register also exists on a dbapi connection. Which objects it accepts is listed in Frames & Plans.

Parameters

A parameter is a value you send with a query instead of writing it into the SQL text. If your code already has SQL strings with ? or $name placeholders, keep them and run them through duckdb.dbapi, or with con.run for statements that return no rows:

DuckDB 1.5.6
con.execute("SELECT customer FROM orders WHERE region = ?", ["emea"]).fetchall()
con.execute("INSERT INTO orders VALUES (?, ?, ?)", ["cato", "amer", 90])
now, with duckdb.dbapi
from duckdb import dbapi

db = dbapi.connect()
cur = db.cursor()
cur.execute("CREATE TABLE orders (customer VARCHAR, region VARCHAR, total INTEGER)")
cur.execute("INSERT INTO orders VALUES (?, ?, ?)", ["cato", "amer", 90])
cur.execute("SELECT customer FROM orders WHERE region = ?", ["amer"]).fetchall()
# [('cato',)]
db.commit()
now, with con.run on the setup's connection
con.run("INSERT INTO orders VALUES (?, ?, ?)", ["dune", "emea", 700])
# 1

These are two alternatives with two separate databases. dbapi.connect() opens a new database in memory with its own orders table, so cato is only there, and dune is only in the setup's table.

A plan made with sql(text) takes no placeholders. In a plan, put param("name") where the value goes and pass the values when you run it:

by_region = plan.filter(col("region") == param("region"))
by_region.rows(con, parameters={"region": "amer"})
# [('bolt', 'amer', 320)]
  • With execute and con.run, the names in a dict of parameters must be strings. 1.5.6 accepted {1: 9} for $1; now that is refused with InvalidInputError. Write {"1": 9}.
  • One statement per call. 1.5.6 ran execute("SELECT 1; SELECT 2") and kept the last result; now that is refused with InvalidInputError. Run each statement on its own.

Python functions

con.create_function still registers a Python function that SQL can call, but its options changed. This is how the two are declared (not code to run):

# 1.5.6
con.create_function(name, function, parameters=None, return_type=None, *,
                    type="native", null_handling="default",
                    exception_handling="default", side_effects=False)
# now: everything after the * is passed by name
con.create_function(name, function, parameters=None, returns=None, *,
                    null_handling="default", stability="consistent")

And here is an actual call. x: int and -> int are Python type annotations; the package reads the SQL types from them. Without annotations, give the types as text: parameters=["BIGINT", "BIGINT"], returns="BIGINT".

def bump(x: int, k: int = 10) -> int:
    return x + k

con.create_function("bump", bump)
sql("SELECT bump(1) AS a, bump(1, k := 2) AS b").rows(con)
# [(11, 3)]: 1.5.6 refused bump(1), since it ignored the default

The DB-API

In 1.5.6 the connection itself had execute(), fetchall(), description and rowcount. Now that style lives in duckdb.dbapi, which follows Python's standard database interface (PEP 249) closely. A frame.connect() connection has none of these methods.

DuckDB 1.5.6
con = duckdb.connect("notes.db")
con.execute("CREATE TABLE notes (text VARCHAR)")
con.execute("INSERT INTO notes VALUES ('hi')")
con.close()   # the table and row are saved
now
db = dbapi.connect("notes.db")
cur = db.cursor()
cur.execute("CREATE TABLE notes (text VARCHAR)")
cur.execute("INSERT INTO notes VALUES ('hi')")
db.commit()   # without this, close() throws the changes away
db.close()
DuckDB 1.5.6Now
Each statement took effect by itself (autocommit)The first statement opens a transaction. commit() makes its changes final; rollback(), or closing without a commit, throws them away. With dbapi.connect(autocommit=True) each statement takes effect by itself, as before.
Each cursor was independent, with its own transaction and its own resultAll cursors of a connection share one transaction, so one cursor sees what another wrote before the commit. They also share one open result: running a statement on one cursor ends the result another cursor was still reading, whose next fetch raises InterfaceError. Read a result to the end, or keep it with fetchall(), before running the next statement.
rowcount was always -1The real number for INSERT, UPDATE, DELETE and CREATE TABLE AS; -1 for a query
with con: closed the connectionwith con: is a transaction: it commits at the end, rolls back on an error, and leaves the connection open
execute("a; b") ran both statementsOne statement per call

On a frame connection, by contrast, each statement takes effect at once, unless you group statements with with con.transaction():. The details are in DB-API 2.0.

Errors

The error classes are in duckdb.exceptions and end in Error. They still fit Python's standard database hierarchy, so except duckdb.exceptions.Error catches them all, apart from errors that reach you through pyarrow or polars (see Errors).

A few mistakes are now caught in Python, before DuckDB sees the query, and raise TypeError or ValueError: a string passed to filter(), a value given for a param() name the plan does not use, a plan given a dbapi connection.

In a dbapi transaction, most failed statements leave the transaction aborted, for example a missing table, a missing column or a value that does not convert. Every later statement then raises TransactionError until you call rollback(); a syntax error (ParserError) does not do this. The rollback also undoes the earlier changes you had not committed:

from duckdb import dbapi, exceptions

db = dbapi.connect()
cur = db.cursor()
cur.execute("CREATE TABLE stock (item VARCHAR, n INTEGER)")
db.commit()
cur.execute("INSERT INTO stock VALUES ('pen', 5)")
try:
    cur.execute("INSERT INTO stock VALUES ('ink', 'lots')")
except exceptions.ConversionError:
    db.rollback()
cur.execute("SELECT count(*) FROM stock").fetchall()
# [(0,)]: the rollback also undid the 'pen' row, which was not committed

Versions

duckdb.__version__ is the version of this Python package. The version of the DuckDB engine inside it is duckdb.duckdb_version(). In 1.5.6 the two were the same number.

import duckdb

duckdb.__version__        # this package
duckdb.duckdb_version()   # the DuckDB engine, such as 'v2.0.0-alpha46057'

Not available yet

  • Finding Python variables by name in a query: register them, as above.
  • Removing a registered Python function. Registering the name again with the same parameter types replaces it; with other types it adds a version, and the first stays. A function lasts until its database closes.
  • Arrow-based Python functions (type="arrow").
  • torch() and tf(): go through to_numpy(con).
  • Python file systems. fsspec, a Python library that reads files from many kinds of storage through one interface, cannot be used: register_filesystem() is gone. read_csv and the other readers take a path or a URL, not an open Python file such as open(...) or io.BytesIO; that raises TypeError. DuckDB still reads local paths, http(s):// URLs and s3:// URLs by itself.

Something you relied on in 1.5.6 is not on this page? It may be under Not available yet, or it may be a change in DuckDB's SQL itself, which DuckDB's release notes cover.
