Macros and extensions

DuckDB can be extended at four levels. An expression is built in Python and runs in the engine. A macro is SQL the engine writes into every query that calls it. A Python function is called once per row. An extension is compiled code loaded into the engine, and it can add anything the engine itself has, from a function to a file system.

Four ways to add something

Each level costs more than the one before it and can do more. Most work that ends up as a Python function could have been a macro, and most people never find out that the fourth level exists.

LevelWritten asCost per rowCan addWhere
Expressioncol() and operators, in the plan that uses itNone. It is the query.A computation over columnsFrames & Plans
MacroSQL, from an expression or a plan, with con.create_macroNone. The engine writes it into the query.A named computation, or a whole parameterised querybelow
Python functionA callable, with con.create_functionA trip into Python and back, per rowAnything Python can computeUDFs
ExtensionC++ or Rust, loaded with LOADNone. It is engine code.Functions, aggregates, table functions, types, file systems, storage, whole subsystemsbelow

Read the table from the top. If a thing can be an expression, it is one. If it needs a name or parameters, it is a macro. Only what needs Python is a function, and only what needs to change the engine is an extension.

Macros

from duckdb import col, table, sql

con.create_macro("add_up", ["a", ("b", 1)], col("a") + col("b"))
con.create_macro("big_orders", ["floor"], table("orders").filter(col("total") > col("floor")))

sql("SELECT add_up(2), add_up(2, 5)").rows(con)     # [(3, 7)]
sql("SELECT id FROM big_orders(1000)").rows(con)    # [(1,), (3,)]

A macro is a piece of SQL with a name and parameters, kept in the database. When a query calls it, the engine puts the body in place of the call, with the arguments in place of the parameters, and then plans the query as if you had written it out. No row ever reaches Python, and there is nothing to call at run time.

con.create_macro(name, parameters, body, *, replace=False, temporary=False)
name
The SQL name, quoted. A dotted name puts the macro in a schema: "util.add_up".
parameters
A list of names, or (name, default) pairs. Every name after the first one with a default must have one too; the engine refuses the definition otherwise.
body
An expression, which makes a scalar macro, or a plan, which makes a table macro. Anything else raises TypeError.
replace
Redefine a macro of that name. Without it a second definition raises CatalogError.
temporary
The macro lives on this connection only, and is gone when it closes. Not visible from con.duplicate().

parameters

Inside the body, col(name) refers to a parameter of that name. The engine tells a parameter from a column by name alone, and the parameter wins. A default is a plain value, written into the definition: a number, text, a date, None. An expression as a default is refused.

from duckdb import lit

con.create_macro("vat", ["price", ("rate", 0.21)], col("price") * (1 + col("rate")))
con.create_macro("greet", [("who", "world")], lit("hello ").concat(col("who")))

sql("SELECT vat(100), vat(100, 0.09)").rows(con)     # [(Decimal('121.00'), Decimal('109.00'))]
sql("SELECT greet(), greet('there')").rows(con)     # [('hello world', 'hello there')]
sql("SELECT add_up(b := 5, a := 2)").rows(con)      # [(7,)]  arguments by name

A parameter shadows a column of the same name. create_macro("above", ["total"], table("orders").filter(col("total") > 1000)) compares the argument with 1000, not the column, and above(5) returns no rows. Name parameters so they cannot collide with the columns the body reads.

A parameter is a value. It cannot be a table name, because a name in a FROM clause is not a value; the engine refuses the definition. To take a table by name, read it through query_table:

con.run("CREATE MACRO first_rows(t, n) AS TABLE SELECT * FROM query_table(t) LIMIT n")
sql("SELECT count(*) FROM first_rows('orders', 2)").rows(con)   # [(2,)]

the body

A scalar macro's body is any expression, aggregates and windows included. A plan's .scalar() puts a whole query in it. A table macro's body is any plan.

from duckdb import count_all, fn

con.create_macro("my_avg", ["x"], col("x").mean())
con.create_macro("running", ["x", "o"], col("x").sum().over(order_by=col("o")))
con.create_macro("n_above", ["x"], table("orders").filter(col("total") > col("x")).aggregate(count_all()).scalar())

sql("SELECT region, my_avg(total) FROM orders GROUP BY region ORDER BY region").rows(con)   # [('amer', 320.0), ('emea', 2000.0)]
sql("SELECT id, running(total, id) FROM orders ORDER BY id").rows(con)
sql("SELECT n_above(1000)").rows(con)                                                       # [(2,)]

Values in the body are written into the definition as literals, escaped, since a definition has no parameters to bind: col("c") == "it's" becomes ("c" = 'it''s'). A param() is refused for the same reason: create_macro raises TypeError, param() has no value inside a macro body; a macro parameter is col(name). A value that changes per call is a parameter of the macro, col(name) in the body.

A body can call anything the engine has, a Python function registered with create_function included, so the levels compose: the macro does the arithmetic around a call into Python.

con.create_function("plus_one", lambda x: x + 1, ["BIGINT"], "BIGINT")
con.create_macro("plus_two", ["x"], fn("plus_one", col("x")) + 1)
sql("SELECT plus_two(1)").rows(con)   # [(3,)]

A macro and a function registered with create_function both live in schema main. The engine stores a registered function as internal, like a built-in, and a macro of the same name takes precedence over it, as it does over a built-in. That is the engine's rule, not this package's.

con.create_macro("abs", ["x"], col("x") + 100)
sql("SELECT abs(-1)").rows(con)   # [(99,)]

writing the statement yourself

create_macro renders the body and runs CREATE MACRO. The same statement can be written by hand, with a plan's render() as the body, when the macro needs something the method does not offer, such as several signatures under one name:

body = sql('SELECT unnest("i") AS uid').filter(col("uid") > 2)
print(body.render())
# WITH "_s0" AS (
# SELECT unnest("i") AS uid
# )
# SELECT * FROM "_s0" WHERE ("uid" > 2)

con.run("CREATE MACRO big_ids(i) AS TABLE " + body.render())
sql("SELECT * FROM big_ids([1, 3, 9])").rows(con)   # [(3,), (9,)]

con.run("CREATE MACRO m(a) AS a, (a, b) AS a + b")   # two signatures
sql("SELECT m(1), m(1, 2)").rows(con)                  # [(1, 3)]

render() takes no connection, so a plan that names a parameter renders without anyone asking what "i" is. The engine finds out when the macro is defined.

calling it

From SQL, as above. From a plan, a scalar macro is a function and a table macro is a table function; fn and table_function call either by name, and the engine knows the result like any function's.

from duckdb import fn, table_function

table("orders").select(fn("add_up", col("total"), 10).alias("x")).rows(con)
table_function("big_orders", 1000).select("id").rows(con)             # [(1,), (3,)]
table_function("big_orders", floor=1000).render()                   # SELECT * FROM "big_orders"("floor" := 1000)

sql("SELECT add_up(2, 5) AS v").types(con)      # ['INTEGER']
table_function("big_orders", 1000).columns(con)   # ['id', 'customer', 'region', 'total']

when the body is checked

The engine checks the body when the macro is defined. A table, function or column it cannot find is refused there, with the engine's message: CatalogError for a table or function, ProgrammingError for a name that is neither a parameter nor a column. A macro cannot call itself, and cannot call a macro defined after it, since the name does not exist yet.

con.create_macro("nope", ["x"], table("missing").filter(col("v") > col("x")))
# CatalogError: Table with name missing does not exist!
con.create_macro("nope", ["x"], col("x") + col("y"))
# ProgrammingError: Referenced column "y" was not found because the FROM clause is missing

Parameters have no types, so anything that depends on the arguments' types is settled at each call. create_macro("up", ["s"], col("s").str().upper()) is accepted; up('abc') gives 'ABC' and up(1) is refused with the message upper gives an integer: no function matches the given name and argument types.

Tables are looked up again at every call. The body is text the engine substitutes, not a result it kept, so a macro over orders sees rows inserted after it was defined. One consequence: an unqualified table name in the body resolves from the caller's search path, not from the schema the macro lives in. A macro created as util.rate_of that reads rates must say table("util.rates"); with table("rates") the engine refuses the definition when rates is not on the definer's own path.

con.create_macro("util.rate_of", ["p"], table("rates").select((col("p") * col("rate")).alias("v")))
# CatalogError: Table with name rates does not exist!
# Did you mean "util.rates"?

where it lives

In the database, like a table: a macro created on a file database is there when the file is opened again. temporary=True keeps it on this connection. duckdb_functions() lists macros with their parameter names and their definition, and DROP MACRO removes one:

sql("SELECT function_name, parameters, macro_definition FROM duckdb_functions() WHERE function_name = 'add_up'").rows(con)
# [('add_up', ['a', 'b'], '(a + b)')]     the engine's own spelling; defaults are not shown

con.run("DROP MACRO add_up")
con.run("DROP MACRO TABLE big_orders")

Defaults are not introspectable: parameters lists the names without them, and macro_definition is the engine's normalised spelling of the body, not what was written.

what a macro cannot do

Run Python
The body is SQL. It can call a function registered from Python, and that is the only way Python enters.
Take a table
Parameters are values. query_table(name) reads a table whose name is a value.
Change anything
A body is an expression or a query. There is no macro for INSERT or UPDATE.
Recurse, or look ahead
Every name in the body must exist when the macro is defined.
Keep state
Each call is the body written out afresh. A volatile argument, random(), is written wherever the parameter appears and runs that many times.

why it is fast

After substitution the macro is gone. The plan shows the expression, and the engine treats it like any expression: a scalar macro in a WHERE is pushed into the scan, so rows that fail it are never read out.

con.create_macro("is_big", ["t"], col("t") > 1000)
con.create_function("is_big_py", lambda t: t > 1000, ["DECIMAL(6,2)"], "BOOLEAN")

print(table("orders").filter(fn("is_big", col("total"))).explain(con))
# ╭─ Seq Scan ────────────────╮
# │ Table: memory.main.orders │
# │ Filters: total > 1000.00  │        the macro became a scan filter
# ╰───────────────────────────╯

print(table("orders").filter(fn("is_big_py", col("total"))).explain(con))
# ╭─ Filter ─────────────────────╮
# │ Expression: is_big_py(total) │      every row is read, then handed to Python
# ╰───────────────┬──────────────╯
# ╭─ Seq Scan ────┴──────────────╮
# │ Table: memory.main.orders    │
# ╰──────────────────────────────╯

The same arithmetic three ways, summed over five million rows:

con.run("CREATE TABLE big AS SELECT i FROM range(5000000) t(i)")
con.create_function("score_py", lambda a: (a * 3 + 7) % 11, ["BIGINT"], "BIGINT")
con.create_macro("score", ["a"], (col("a") * 3 + 7) % 11)

sql("SELECT sum((i * 3 + 7) % 11) FROM big").rows(con)
sql("SELECT sum(score(i)) FROM big").rows(con)
sql("SELECT sum(score_py(i)) FROM big").rows(con)
Query14 threads1 thread
the expression written out2 ms
score(i), the macro2 ms13 ms
score_py(i), the Python function510 ms480 ms

Medians over repeated runs on one laptop (Apple M3 Max, threads at its default of 14). The numbers move with the machine; the ratio does not move much. The macro costs the same as the expression because it is the expression. The Python function barely gains from threads, because one interpreter runs all of them.

A macro or a Python function

The test is whether the body can be written with col(), operators and the engine's functions. If it can, it is a macro, and the per-row cost is zero. A Python function is for what SQL cannot say: a library call, a lookup into Python state, a format the engine has no parser for.

a trip into Python per row: 0.5 s
con.create_function(
    "score",
    lambda a: (a * 3 + 7) % 11,
    ["BIGINT"], "BIGINT",
)
written into the query: 2 ms
con.create_macro(
    "score",
    ["a"],
    (col("a") * 3 + 7) % 11,
)

The macro also gives the engine the whole expression to plan with: filters move into scans, constant calls are computed once, and the engine's own types apply. A function is a closed box; the engine can only call it. When a function is needed, keep it to the part that needs Python and let a macro or the query do the rest, as in plus_two above. The function's own page, UDFs, covers what it receives and returns, NULL, stability and threads.

Extensions

An extension is a compiled library, loaded into the process, that registers things with the engine: functions, types, table functions, file systems, ways to read other databases. Several are built into the engine and are there in every connection. The rest are installed once, downloaded into a directory under your home, and loaded per process.

sql("SELECT extension_name, loaded, installed FROM duckdb_extensions() WHERE loaded").rows(con)
# [('core_functions', True, True), ('icu', True, True), ('json', True, True), ('parquet', True, True), ('tpch', True, True)]

sql("SELECT count(*) FROM duckdb_extensions()").rows(con)   # [(30,)]  the ones the engine knows by name

What is built in depends on the build; the list above is this one's. The engine records which extension each function came from, so a name can be traced:

sql("""SELECT DISTINCT function_name, function_type, extension_name FROM duckdb_functions()
       WHERE function_name IN ('json_extract', 'parquet_metadata', 'read_json') ORDER BY 1""").rows(con)
# [('json_extract', 'scalar', 'json'), ('parquet_metadata', 'table', 'parquet'), ('read_json', 'table', 'json')]

sql("""SELECT extension_name, function_type, count(DISTINCT function_name) AS n FROM duckdb_functions()
       WHERE extension_name IS NOT NULL GROUP BY ALL ORDER BY 1, 2""").rows(con)
# [('core_functions', 'aggregate', 68), ('core_functions', 'scalar', 260),
#  ('icu', 'scalar', 289), ('icu', 'table', 2),
#  ('json', 'macro', 6), ('json', 'pragma', 1), ('json', 'scalar', 40), ('json', 'table', 10),
#  ('parquet', 'pragma', 1), ('parquet', 'scalar', 2), ('parquet', 'table', 8),
#  ('tpch', 'pragma', 1), ('tpch', 'table', 3)]

sql("SELECT type_name, extension_name FROM duckdb_types() WHERE extension_name IS NOT NULL").rows(con)
# [('JSON', 'json')]

So the five loaded here add aggregates, scalar functions, table functions, macros and a type between them. The engine's own description of the others it knows shows how far the list goes:

installing and loading

Both are statements, run on the connection. INSTALL downloads the extension once, for this engine version and platform, into ~/.duckdb/extensions/<version>/<platform>/; LOAD loads it into the process.

con.run("INSTALL httpfs")
con.run("LOAD httpfs")

con.run("INSTALL h3 FROM community")   # from the community repository
con.run("FORCE INSTALL httpfs")        # download again
con.run("UPDATE EXTENSIONS")           # every installed one, to the latest for this engine
con.run("LOAD '/path/to/my.duckdb_extension'")   # a file, not a name

Downloading needs an engine the repository knows. An extension is built for one engine version, and the engine looks it up under its own version name. The repository has every release, and every one of DuckDB's nightly builds under the name that build carried, such as v2.0.0-alpha40145, the engine this page was written against: on it, INSTALL httpfs, FORCE INSTALL httpfs, INSTALL excel and INSTALL quack all download and load. An engine built from the same commit without that name calls itself v2.0.0-dev83455, looks under its commit hash instead, and gets IOError: HTTP Error: Failed to download extension "httpfs" at URL "http://extensions.duckdb.org/8a81c84987/osx_arm64/httpfs.duckdb_extension.gz" (HTTP 404). Community extensions are published for releases only, so INSTALL h3 FROM community fails the same way on any nightly.

The directory is the extension_directory setting, and can be given when connecting: duckdb.connect(extension_directory="/srv/duckdb/ext"). Loading an extension that is not installed raises IOError naming the file the engine looked for.

autoloading

The engine keeps a list of extensions it knows and the functions each one has. With autoload_known_extensions on, a query that names one of those functions loads its extension when the query is planned; with autoinstall_known_extensions on as well, it is downloaded first if it has to be. Both are on by default, so on a release read_xlsx on a fresh connection fetches excel and reads the file.

sql("SELECT * FROM read_xlsx('book.xlsx')").rows(con)   # on a release: installs and loads excel, then reads the file

sql("SELECT current_setting('autoload_known_extensions'), current_setting('autoinstall_known_extensions')").rows(con)
# [(True, True)]

con.run("SET autoload_known_extensions = false")      # or duckdb.connect(autoload_known_extensions="false")

With autoloading off, the engine refuses the query and says which extension has the function:

# CatalogError: Table Function with name "read_xlsx" is not in the catalog, but it exists in the excel extension.
# Please try installing and loading the excel extension by running:
# INSTALL excel;
# LOAD excel;

With loading on and installing off, a function whose extension is not installed raises IOError with the same advice. Not every extension is on the list: on this build read_xlsx tried to fetch excel, while st_point raised the CatalogError above naming spatial without trying, and needs an explicit INSTALL and LOAD.

core and community

Core extensions are built and signed by the DuckDB team and come from extensions.duckdb.org, which is where a bare INSTALL name looks. Community extensions are built and signed by the community repository from other people's source, and come from community-extensions.duckdb.org with INSTALL name FROM community. The list of both, with a page per extension, is at duckdb.org/community_extensions. The engine checks the signature when it loads; a library that is not signed, one you built yourself, loads only when the database was opened with duckdb.connect(allow_unsigned_extensions="true"). That setting cannot be changed once the database is running.

from a plan

Once loaded, an extension's functions are the engine's. A scalar function is called with fn, or through the namespaces when one covers it; a table function is a plan through table_function, with named arguments spelled the way SQL spells them.

from duckdb import fn, table_function

table_function("parquet_metadata", "orders.parquet").select("row_group_id", "path_in_schema", "num_values").rows(con)
# [(0, 'id', 3), (0, 'customer', 3), (0, 'region', 3), (0, 'total', 3)]

table_function("read_json", "events.json", format="array").render()
# SELECT * FROM "read_json"('events.json', "format" := 'array')

table_function("tpch_queries").select("query_nr").head(2).rows(con)   # [(1,), (2,)]

payload = sql("""SELECT '{"id": 7, "tags": ["a"]}' AS payload""")
payload.select(fn("json_extract", col("payload"), "$.id").alias("id"), col("payload").json().keys().alias("keys")).rows(con)
# [('7', ['id', 'tags'])]

read_csv, read_parquet and read_json are table_function with the name filled in. A type an extension adds is a type: sql("SELECT '{\"a\": 1}'::JSON AS j").types(con) is ['JSON'].

Writing an extension

In Polars, the way to add a fast expression the library does not have is an expression plugin: a Rust function, compiled to a library and registered as an expression. What it adds is an expression, because that is what the plugin API registers.

A DuckDB extension registers with the engine, and it can register anything the engine's own extensions do. The five loaded on this machine add scalar functions, aggregates, table functions, macros and a type between them. The ones the engine lists beside them add file systems, other databases as storage, lakehouse formats, indexes, collations and a user interface. All of that goes through the same mechanism, so an extension written for a domain can bring its types, its functions over them, its file format and its index together, and they plan and run inside the engine with the rest of the query.

Because it is loaded into the engine and not into a client, an extension works from every client that runs that engine: this one, the command line, R, Java, Node, and whatever else loads the same library.

where to start

C++
The extension template is the supported route. It comes with the build system, a SQL-based test runner and CI that builds for Linux, macOS, Windows and Wasm, and it is the route the community extension guide describes.
Rust
The Rust template builds on the engine's C extension API, with no C++ and no engine build. Its own README calls it experimental.
Docs
The extensions overview on duckdb.org, and the community extension development guide, which is also how an extension gets into the community repository and becomes an INSTALL name FROM community for everyone.

Those pages document the extension API itself, and this manual does not repeat it. From here, an extension you built is LOAD '/path/to/it.duckdb_extension' on a connection opened with allow_unsigned_extensions, and once it is in the repository, INSTALL and LOAD like any other.

Reference

Macros

con.create_macro(name, parameters, body, replace=False, temporary=False)
Define a macro. An expression makes a scalar macro, a plan a table macro. parameters are names or (name, default) pairs; a default is a plain value. col(name) in the body is a parameter; a param() there is refused with TypeError.
con.run("CREATE MACRO name(p) AS ...")
The statement itself. AS TABLE and a plan's render() for a table macro. Several signatures: AS a, (a, b) AS a + b.
con.run("DROP MACRO name") / "DROP MACRO TABLE name"
Remove a scalar or a table macro. IF EXISTS works.
fn(name, *args)
Call a scalar macro from a plan.
table_function(name, *args, **named)
A table macro as a plan; named arguments render as name := value.
duckdb_functions()
Every function the engine has, macros included: function_type is macro or table_macro, parameters the names without their defaults, macro_definition the body in the engine's spelling, extension_name where it came from.

Extensions

con.run("INSTALL name")
Download for this engine version and platform. FROM community, FROM core_nightly or FROM 'https://...' chooses the repository. FORCE INSTALL downloads again.
con.run("LOAD name")
Load an installed extension into the process. A quoted path loads a file.
con.run("UPDATE EXTENSIONS")
Bring every installed extension up to date.
duckdb_extensions()
Every extension the engine knows: loaded, installed, install_path, description, extension_version, install_mode, installed_from.
duckdb_types()
Every type, with extension_name for one an extension added.
duckdb_settings()
Every setting with its description; the extension ones match name LIKE '%extension%'.

Settings

autoload_known_extensions
Load a known extension when a query needs it. On by default.
autoinstall_known_extensions
Install it first if it is not. On by default.
allow_community_extensions
Whether FROM community may be loaded. On by default.
allow_unsigned_extensions
Load a library with no signature. Only at connect().
extension_directory
Where installed extensions are kept. Empty means ~/.duckdb/extensions.
custom_extension_repository
Where a bare INSTALL name looks instead of the core repository.

A macro and an extension belong to the engine, not to this client. Either works from every DuckDB client on the same engine, and an error in one comes from DuckDB, with the message it would give any of them.
