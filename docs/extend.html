Macros and extensions

This page shows two ways to add to DuckDB. A macro is a piece of SQL you give a name and reuse in your queries. An extension is a package of compiled code that adds new features to DuckDB, such as functions, file formats or ways to read other databases. To decide between a macro, a Python function and an extension, see A macro, a Python function or an extension?

Start here

from decimal import Decimal
from duckdb import frame
from duckdb.frame import col, sql

con = frame.connect()
con.run("CREATE TABLE orders (id INTEGER, customer VARCHAR, region VARCHAR, total DECIMAL(6,2))")
con.run("INSERT INTO orders VALUES (1, 'acme', 'emea', 1400), (2, 'bolt', 'amer', 320), (3, 'acme', 'emea', 2600)")

con.create_macro("with_vat", ["amount"], col("amount") * Decimal("1.21"))
sql("SELECT id, with_vat(total) AS gross FROM orders").rows(con)
# [(1, Decimal('1694.0000')), (2, Decimal('387.2000')), (3, Decimal('3146.0000'))]

A comment shows what the call returns, as you see it at the Python prompt or in a notebook; in a script, pass the result to print(). con.run(...) runs one statement and returns the number of rows it changed; sql(...).rows(con) gives you a query's rows.

create_macro takes three things here:

  • "with_vat" is the name you call it by in SQL.
  • ["amount"] lists the names of its parameters.
  • col("amount") * Decimal("1.21") is the body: what the macro stands for. It is an expression, a piece of a query built in Python (see Frames & Plans). Inside the body, col("amount") means the parameter amount.

When a query calls with_vat(total), DuckDB puts the body in place of the call, with total in place of amount. It then runs the query as if you had written total * 1.21 yourself. A macro adds no Python call of its own, so it is as fast as the SQL it stands for. If its body calls a Python function, DuckDB calls that function just as often as it would without the macro, with the same rules for NULL and for reusing results (see Python Functions).

The body uses Decimal("1.21") because a Python float is an approximate number. It would become DuckDB's DOUBLE, and with_vat would return floats such as 1694.0. In SQL, 1.21 is an exact DECIMAL, and a Python Decimal becomes one too.

The column total is a DECIMAL(6,2): a number with six digits in all, two of them after the decimal point. Multiplying two decimals adds up their decimal places, so the result has four. The macro does not round it; round(with_vat(total), 2) gives whole cents.

As an alternative to create_macro, you can write the same macro in SQL. OR REPLACE replaces the macro of that name, so running both is fine:

con.run("CREATE OR REPLACE MACRO with_vat(amount) AS amount * 1.21")

create_macro takes an expression or a plan, not SQL text: a string as the body raises TypeError. It is a method of a connection from frame.connect(). A connection from duckdb.dbapi.connect() does not have it and raises AttributeError; there, use CREATE MACRO. TypeError and AttributeError are Python's own errors; the other errors this page names, such as CatalogError, are classes in duckdb.exceptions.

Scalar and table macros

There are two kinds of macro:

  • A scalar macro computes one value, like a function. Its body is an expression, as in with_vat above.
  • A table macro returns rows, like a table. Its body is a plan, a query built in Python.
from duckdb.frame import table

con.create_macro("big_orders", ["floor"], table("orders").filter(col("total") > col("floor")))
sql("SELECT id, total FROM big_orders(1000)").rows(con)
# [(1, Decimal('1400.00')), (3, Decimal('2600.00'))]

You call a table macro wherever SQL expects a table, in FROM. It reads the table each time you call it, so it sees rows added after you defined it.

A parameter hides a column with the same name. Inside the body, col(name) means the parameter whenever a parameter has that name. So create_macro("above", ["total"], table("orders").filter(col("total") > 1000)) compares the argument with 1000, not the column, and above(5) returns no rows. In the query of a scalar macro's .scalar(), the same clash raises ProgrammingError instead. Give parameters names that differ from the columns the body reads.

What a body can hold

A scalar macro's body can be any expression, including aggregate functions, which combine many rows into one value, such as mean(). It can also be a window function, which keeps every row and gives each one a value computed from other rows: running below gives each order the running total, in order of id. To put a whole query in a scalar macro, end the plan with .scalar(), which turns a query that returns one value into an expression. A table macro's body can be any plan.

from duckdb.frame import count_all, fn

con.create_macro("my_avg", ["x"], col("x").mean())
con.create_macro("running", ["x", "o"], col("x").sum().over(order_by=col("o")))
con.create_macro("n_above", ["x"], table("orders").filter(col("total") > col("x")).aggregate(count_all()).scalar())

sql("SELECT region, my_avg(total) FROM orders GROUP BY region ORDER BY region").rows(con)
# [('amer', 320.0), ('emea', 2000.0)]
sql("SELECT id, running(total, id) FROM orders ORDER BY id").rows(con)
# [(1, Decimal('1400.00')), (2, Decimal('1720.00')), (3, Decimal('4320.00'))]
sql("SELECT n_above(1000)").rows(con)   # [(2,)]

The query inside .scalar() must return one column, or create_macro raises ProgrammingError. When the query's result has no row, the value is NULL. That is not the case for n_above(9999), which is 0: counting no orders still gives one row, holding 0. When the result has more than one row, the query that calls the macro raises InvalidInputError.

A body can call any function DuckDB has, a Python function you registered with create_function included. fn(name, ...) builds a call to the function with that name. So you can keep the Python part small and do the rest in the macro:

con.create_function("plus_one", lambda x: x + 1, ["BIGINT"], "BIGINT")
con.create_macro("plus_two", ["x"], fn("plus_one", col("x")) + 1)
sql("SELECT plus_two(1)").rows(con)   # [(3,)]

A table name as an argument

A parameter holds a value, and a table name in FROM is not a value. To pass a table by name, read it with DuckDB's query_table function, in a macro you write in SQL:

con.run("CREATE MACRO first_rows(t, n) AS TABLE SELECT * FROM query_table(t) LIMIT n")
sql("SELECT count(*) FROM first_rows('orders', 2)").rows(con)   # [(2,)]

Defaults and named arguments

A parameter can have a default: write it as a (name, default) pair. A call can then leave it out, or pass any argument by name with name := value:

from duckdb.frame import lit

con.create_macro("add_up", ["a", ("b", 1)], col("a") + col("b"))
con.create_macro("greet", [("who", "world")], lit("hello ").concat(col("who")))

sql("SELECT add_up(2), add_up(2, 5), add_up(b := 5, a := 2)").rows(con)   # [(3, 7, 7)]
sql("SELECT greet(), greet('there')").rows(con)                        # [('hello world', 'hello there')]

lit turns a plain Python value into an expression, so that you can call expression methods such as .concat() on it; a plain string has no .concat(). A default is a plain value, such as a number, text, a date or None. An expression as a default raises TypeError. Every parameter after the first one with a default needs a default too; otherwise DuckDB refuses the macro with ParserError.

A macro has no rule of its own for NULL. A NULL argument, or a None default, goes into the body like any other value, and the SQL there decides the result: add_up(2, NULL) is NULL, because 2 + NULL is.

A default keeps the type of its Python value. That matters for numbers with a decimal point:

from decimal import Decimal

con.create_macro("vat", ["price", ("rate", 0.21)], col("price") * (1 + col("rate")))
sql("SELECT vat(100), vat(100, 0.09)").rows(con)   # [(121.0, Decimal('109.00'))]

con.create_macro("vat", ["price", ("rate", Decimal("0.21"))], col("price") * (1 + col("rate")), replace=True)
sql("SELECT vat(100), vat(100, 0.09)").rows(con)   # [(Decimal('121.00'), Decimal('109.00'))]

The Python float 0.21 becomes a DOUBLE, so vat(100) gives a float. The 0.09 in the SQL text is read by DuckDB as an exact DECIMAL. A Decimal default keeps both calls exact.

Calling a macro from a plan

In a plan, call a scalar macro with fn, like any function, and a table macro with table_function, like any function that returns rows. Keyword arguments are passed by name, so you can choose which parameters with a default to give:

from duckdb.frame import table_function

table("orders").select(fn("add_up", col("id"), b=10).alias("x")).rows(con)   # [(11,), (12,), (13,)]
table_function("big_orders", 1000).select("id").rows(con)                     # [(1,), (3,)]
print(table_function("big_orders", floor=1000).render())   # SELECT * FROM big_orders("floor" := 1000)

Every parameter without a default still needs an argument. fn only builds an expression, so a missing argument, like a name DuckDB does not know, is reported when DuckDB checks or runs the plan: by rows(con), types(con) or columns(con), not by fn.

table("orders").select(fn("add_up", b=10)).rows(con)
# ProgrammingError: Binder Error: Macro add_up() does not support the supplied arguments. You might need to add explicit type casts.

A plan can tell you its result types and column names without fetching any rows:

sql("SELECT add_up(2, 5) AS v").types(con)        # ['INTEGER']
table_function("big_orders", 1000).columns(con)   # ['id', 'customer', 'region', 'total']

While it works these out, DuckDB may still call a Python function whose arguments are fixed values: sql("SELECT plus_two(1)").types(con) calls plus_one once.

Where a macro lives

A macro is kept in the database, like a table. Every connection to the database can call it, and a macro made in a database file is still there when you open the file again. A Python function is not kept. If a macro calls one, register the function again with create_function after you open the file, or calling the macro raises CatalogError.

The examples on this page use an in-memory database, from frame.connect() with no file name. Its macros are gone when it closes, and another frame.connect() does not see them, but con.duplicate() shares the same database. To keep macros between runs, connect to a file, such as frame.connect("shop.db").

  • temporary=True keeps the macro on this connection only. It is gone when the connection closes, and con.duplicate() cannot see it.
  • Defining a macro with the name of another macro of the same kind, in the same schema, raises CatalogError. replace=True replaces the old macro.
  • A macro may take the name of a built-in function or of a Python function you registered. It then hides that function; see the Details of What a macro cannot do.

A schema is a named group of tables, macros and other objects in a database. Unless you say otherwise, they go into the schema main. To put a macro in another schema, create the schema first, then give the name as a tuple:

con.run("CREATE SCHEMA util")
con.create_macro(("util", "twice"), ["x"], col("x") * 2)

sql("SELECT util.twice(21)").rows(con)                        # [(42,)]
table("orders").select(fn(("util", "twice"), col("id"))).rows(con)   # [(2,), (4,), (6,)]

Without CREATE SCHEMA, create_macro raises CatalogError. A name given as one string is used as written, so a dot in it is part of the name: table("orders").select(fn("util.twice", col("id"))).rows(con) looks for a macro called util.twice and raises CatalogError.

To see your macros, ask duckdb_functions(). To remove one, use DROP MACRO, or DROP MACRO TABLE for a table macro:

sql("SELECT function_name, function_type, parameters, macro_definition FROM duckdb_functions() WHERE function_name = 'add_up'").rows(con)
# [('add_up', 'macro', ['a', 'b'], '(a + b)')]

con.run("DROP MACRO add_up")
con.run("DROP MACRO TABLE big_orders")

The list does not show defaults, and macro_definition is DuckDB's own rewriting of the body, not the text you gave it.

What a macro cannot do

Run Python
The body is SQL. It can call a Python function you registered, and that is the only way Python comes in.
Take a table
Parameters are values. Use query_table(name) to read a table whose name is a value.
Change data
A body is an expression or a query. There is no macro for INSERT or UPDATE.
Call itself, or a later macro
Every name in the body must exist when you define the macro.
Keep state
Each call is the body written out again, with nothing kept from the last one.

Details

  • DuckDB checks the body when you define the macro. A table or function it cannot find raises CatalogError; a name that is neither a parameter nor a column of a table the body reads raises ProgrammingError.
  • Tables and functions are looked up again at every call. A macro sees rows added after you defined it, and a macro over a table that has since been dropped fails at its next call.
  • Parameters have no types, so anything that depends on an argument's type is checked at each call. With create_macro("up", ["s"], col("s").str().upper()), up('abc') gives 'ABC', and up(1) is refused with ProgrammingError, the error upper gives for a number.
  • An argument is copied to every place its parameter appears. A changing argument such as random() then runs once per place, so x - x in the body need not be 0.
  • A table name in the body without a schema is looked up from where the macro is called, not from the macro's own schema. A macro made as ("util", "rate_of") that reads util.rates must say table(("util", "rates")). With table("rates"), DuckDB refuses the macro when rates cannot be found from where you define it.
  • Values in the body are written into the macro as SQL text: col("c") == "it's" becomes (c = 'it''s'). So param(), a placeholder whose value you give when the query runs, has nothing to stand for there, and create_macro refuses it with TypeError: param() has no value inside a macro body; a macro parameter is col(name).
  • A macro with the same name as a built-in function, or as a Python function you registered, takes precedence over it. That is DuckDB's own rule.
  • You can also write the CREATE MACRO statement yourself, for something create_macro does not offer, such as several versions under one name. A plan's render() gives its SQL text, to use as a table macro's body.
con.create_macro("abs", ["x"], col("x") + 100)
sql("SELECT abs(-1)").rows(con)   # [(99,)]: the macro, not the built-in abs
con.run("DROP MACRO abs")      # the built-in abs is back

con.run("CREATE MACRO m(a) AS a, (a, b) AS a + b")
sql("SELECT m(1), m(1, 2)").rows(con)   # [(1, 3)]: one name, two versions

body = table("orders").filter(col("total") > 1000).select("id")
con.run("CREATE MACRO big_ids() AS TABLE " + body.render())
sql("SELECT * FROM big_ids()").rows(con)   # [(1,), (3,)]

A macro, a Python function or an extension?

There are four ways to add a computation to your queries. They can do different things, as the last column shows: a macro can return one value or rows, a Python function returns one value per call, and an extension can also add table functions, types and more. Going down the table, each takes more work to write. Only a Python function adds a trip into Python and back for every row. The computation itself takes time whichever way you write it.

WayWritten asTrip into PythonCan add
Expressioncol() and operators, in the plan that uses it (Frames & Plans)None: it is the queryA computation over columns
MacroAn expression or a plan, with con.create_macro (this page)None: DuckDB copies it into the queryA named computation, or a whole query with parameters
Python functionA Python function, with con.create_function (Python Functions)There and back, for every rowAnything Python can compute
ExtensionC++ or Rust, loaded with LOAD (below)None: it runs inside DuckDBFunctions, aggregate functions, table functions, types, file systems, storage

Read the table from the top and stop at the first row that fits. If you can write it with col(), operators and DuckDB's functions, it is an expression, and if you want to reuse it under a name, a macro. Use a Python function only for what needs Python: a call into a Python library, a lookup in your Python data, a format DuckDB cannot read. An extension is for adding something DuckDB itself does not have, and most people install one rather than write one.

a trip into Python for every row
con.create_function(
    "score_py",
    lambda a: (a * 3 + 7) % 11,
    ["BIGINT"], "BIGINT",
)
copied into the query
con.create_macro(
    "score",
    ["a"],
    (col("a") * 3 + 7) % 11,
)

The two agree for the numbers in the example below, but not for every number:

  • A Python integer has no size limit. SQL does the arithmetic in the argument's integer type, and a result too large for it raises DataError. score_py(1000000000) is 4, but score(1000000000) overflows, because DuckDB reads 1000000000 as an INTEGER.
  • For a negative number, Python's % and SQL's % differ: score_py(-3) is 9, and score(-3) is -2.

Check such details when you move Python code into a macro.

Here is the same sum three ways, over five million rows:

con.run("CREATE TABLE big AS SELECT i FROM range(5000000) t(i)")

sql("SELECT sum((i * 3 + 7) % 11) FROM big").rows(con)   # [(25000007,)]
sql("SELECT sum(score(i)) FROM big").rows(con)             # [(25000007,)]
sql("SELECT sum(score_py(i)) FROM big").rows(con)          # [(25000007,)]
Query64 threads1 thread
the expression written out2 ms40 ms
score(i), the macro2 ms40 ms
score_py(i), the Python function2050 ms1950 ms

These are middle values of seven runs on one 64-core Linux machine, with threads at its default of one per core, and then with SET threads = 1. Your numbers will differ, but the gap stays about the same. The macro costs the same as the expression because it is the expression. The Python function hardly gains from more threads, because only one thread at a time can run Python code.

Why a macro is fast

DuckDB sees the SQL inside a macro, so it can treat it like any other part of the query. A condition in a macro can be applied while DuckDB reads the table, so rows that fail it are skipped early. DuckDB cannot look inside a Python function, so it cannot use the function's condition while reading. Every row that reaches the function goes to Python, though other conditions in the query can still remove rows first. explain(con) shows the steps DuckDB will take:

con.create_macro("is_big", ["t"], col("t") > 1000)
con.create_function("is_big_py", lambda t: t > 1000, ["DECIMAL(6,2)"], "BOOLEAN")

print(table("orders").filter(fn("is_big", col("total"))).explain(con))
# ╭─ Seq Scan ────────────────╮
# │ Table: memory.main.orders │
# │ Type: Sequential Scan     │
# │ Projections: id,          │
# │              customer,    │
# │              region,      │
# │              total        │
# │ Filters: total > 1000.00  │      the macro's condition, applied while reading
# │ ~1 row                    │
# ╰───────────────────────────╯

print(table("orders").filter(fn("is_big_py", col("total"))).explain(con))
# ╭─ Filter ─────────────────────╮
# │ Expression: is_big_py(total) │   every row is read first, then handed to Python
# │ ~1 row                       │
# ╰───────────────┬──────────────╯
# ╭─ Seq Scan ────┴──────────────╮
# │ Table: memory.main.orders    │
# │ Type: Sequential Scan        │
# │ Projections: id, customer,   │
# │              region, total   │
# │ ~3 rows                      │
# ╰──────────────────────────────╯

When you do need Python, keep the Python function to the part that needs it, and let a macro or the query do the rest, as plus_two does above. Python Functions covers what such a function receives and returns, NULL, and threads.

Extensions

An extension is a package of compiled code that DuckDB loads into your program. It can add functions, data types, file formats, ways to read other databases, and access to files on the web or in cloud storage. A few extensions are built into DuckDB and always loaded. Others you download once with INSTALL and load with LOAD.

sql("SELECT extension_name FROM duckdb_extensions() WHERE loaded").rows(con)
# [('autocomplete',), ('core_functions',), ('icu',), ('json',), ('parquet',)]

sql("SELECT count(*) FROM duckdb_extensions()").rows(con)   # [(30,)]: the ones DuckDB knows by name

Which extensions are built in depends on how your DuckDB was built; the list above is from the one this page was tested with. duckdb_extensions() also describes each extension it knows. Some of them, and what they add:

Installing and loading

Both are SQL statements that you run on a connection. INSTALL downloads the extension from the internet, built for your DuckDB version and your computer, and keeps it on disk. So you run it once per computer and DuckDB version. LOAD makes the extension work in the database the connection belongs to:

con.run("INSTALL httpfs")
con.run("LOAD httpfs")
sql("SELECT loaded, installed FROM duckdb_extensions() WHERE extension_name = 'httpfs'").rows(con)   # [(True, True)]

con.run("FORCE INSTALL httpfs")   # download it again
con.run("UPDATE EXTENSIONS")      # bring every installed extension up to date

Downloads go to ~/.duckdb/extensions, in a folder for each DuckDB version and platform. Give another place when you connect: frame.connect(extension_directory="/srv/duckdb/ext"). Loading an extension that is not installed raises IOError, which names the file DuckDB looked for and tells you to run INSTALL. LOAD '/path/to/name.duckdb_extension', with a path in quotes, loads a file instead.

A loaded extension lasts until its database is closed. Run LOAD again in every database you open, and in every new run of your program. A connection from con.duplicate() shares its database, and so the extension. Some extensions also load by themselves when a query needs them, as the next part shows.

Without a network, INSTALL raises IOError: Failed to download extension. To install on such a computer, copy the extension file from one with the same DuckDB version and platform, and give its path in quotes: INSTALL '/path/to/httpfs.duckdb_extension'. The install_path column of duckdb_extensions() shows where an installed file is.

This IOError is DuckDB's own class from duckdb.exceptions, not Python's built-in IOError, so except IOError does not catch it. Write from duckdb import exceptions and catch exceptions.IOError.

Loading by itself

DuckDB knows which extension has which function. When a query uses a function from a known extension that is not loaded yet, DuckDB installs and loads it for you. Here text, which formats a number, comes from the excel extension:

sql("SELECT text(1234.5, '#,##0.00')").rows(con)   # [('1,234.50',)]: excel was installed and loaded first

sql("SELECT current_setting('autoload_known_extensions'), current_setting('autoinstall_known_extensions')").rows(con)
# [(True, True)]

Two settings control this, and both are on by default: autoload_known_extensions loads the extension, and autoinstall_known_extensions downloads it first when it is not installed. With loading off, DuckDB refuses the query and tells you which extension has the function:

strict = frame.connect(autoload_known_extensions="false")
sql("SELECT * FROM read_xlsx('book.xlsx')").rows(strict)
# CatalogError: Catalog Error: Table Function with name "read_xlsx" is not in the catalog, but it exists in the excel extension.
#
# Please try installing and loading the excel extension by running:
# INSTALL excel;
# LOAD excel;
# ...

With loading on and installing off, a function whose extension is not installed raises IOError with the same advice. Not every extension loads by itself: st_point from spatial raises the CatalogError above even with both settings on, and needs INSTALL spatial and LOAD spatial.

Core and community extensions

Core extensions are built and signed by the DuckDB team, and a plain INSTALL name downloads them. Community extensions are written by other people and built and signed by DuckDB's community repository; install one with INSTALL name FROM community. The list of both, with a page for each, is at duckdb.org/community_extensions.

DuckDB checks the signature when it loads an extension. An extension without one, such as one you built yourself, loads only when you connect with frame.connect(allow_unsigned_extensions="true"). You cannot turn that setting on later: SET allow_unsigned_extensions = true on an open database raises InvalidInputError.

Using an extension from a plan

Once an extension is loaded, its functions are DuckDB's. Call a function with fn, or with a method where the package has one, such as col("payload").json().keys() below. Call a function that returns rows with table_function. Keyword arguments are passed by name, as SQL's name := value:

con.run("COPY orders TO 'orders.parquet'")
table_function("parquet_metadata", "orders.parquet").select("row_group_id", "path_in_schema", "num_values").rows(con)
# [(0, 'id', 3), (0, 'customer', 3), (0, 'region', 3), (0, 'total', 3)]

print(table_function("read_json", "events.json", format="array").render())
# SELECT * FROM read_json('events.json', "format" := 'array')

payload = sql("""SELECT '{"id": 7, "tags": ["a"]}' AS payload""")
payload.select(fn("json_extract", col("payload"), "$.id").alias("id"), col("payload").json().keys().alias("keys")).rows(con)
# [('7', ['id', 'tags'])]

read_csv, read_parquet and read_json in duckdb.frame are table_function with the name filled in. A type an extension adds is a type like any other: sql("SELECT '{\"a\": 1}'::JSON AS j").types(con) is ['JSON'].

Details

  • INSTALL downloads the build of the extension made for your exact DuckDB version. Releases and DuckDB's preview builds have them. A DuckDB you built from source yourself may not: without a release or preview version name, it looks for extensions under its commit, and finds none. INSTALL then fails with IOError: HTTP Error: Failed to download extension ... (HTTP 404).
  • Community extensions are published for releases only. On a preview build, such as the one this page was tested with, INSTALL h3 FROM community fails with the same IOError.
  • FROM core_nightly or FROM 'https://...' after INSTALL name picks another repository, and the custom_extension_repository setting changes where a plain INSTALL name looks.
  • DuckDB records which extension each function and type came from, so you can trace a name:
sql("""SELECT DISTINCT function_name, function_type, extension_name FROM duckdb_functions()
       WHERE function_name IN ('json_extract', 'parquet_metadata', 'text') ORDER BY 1""").rows(con)
# [('json_extract', 'scalar', 'json'), ('parquet_metadata', 'table', 'parquet'), ('text', 'scalar', 'excel')]

sql("SELECT type_name, extension_name FROM duckdb_types() WHERE extension_name IS NOT NULL").rows(con)
# [('JSON', 'json')]

Writing your own extension

If you use polars, you may know expression plugins: a function written in Rust and added to polars as a new expression. A DuckDB extension can add more than that. It can add anything DuckDB's own extensions add: functions, aggregate functions, table functions (functions that return rows), types, file systems, file formats, other databases to read, and indexes. An extension for one field of work can bring its types, its functions and its file format together, and they all run inside DuckDB with the rest of the query.

Because an extension is loaded into DuckDB and not into a Python package, it works from every program that uses DuckDB: this package, the command line, R, Java, Node and others.

C++
The extension template is the main way. It comes with the build setup, a test runner that runs SQL files, and automatic builds for Linux, macOS, Windows and the web. It is the way the community extension guide describes.
Rust
The Rust template uses DuckDB's C interface for extensions, with no C++ and no build of DuckDB itself. Its own README calls it experimental.
Docs
The extensions overview on duckdb.org, and the community extension development guide, which also explains how to publish an extension so that anyone can INSTALL name FROM community.

Those pages describe how to write an extension, and this manual does not repeat them. To try one you built, connect with allow_unsigned_extensions="true" and run LOAD '/path/to/it.duckdb_extension'. Once it is published, INSTALL and LOAD it like any other.

Reference

Macros

con.create_macro(name, parameters, body, *, replace=False, temporary=False)
Define a macro. Returns None. An expression as the body makes a scalar macro, a plan makes a table macro, and anything else raises TypeError. A tuple as the name puts the macro in a schema, which must already exist.
parameters
Names, or (name, default) pairs. A default is a plain value, kept with its Python type. After the first default, every parameter needs one.
body
In a scalar macro's expression, outside any plan, col(name) must name a parameter; any other name raises ProgrammingError, even one a table has as a column. Inside a plan, the body of a table macro or the query in .scalar(), col(name) is a parameter when name is in parameters, and otherwise a column of that plan's tables. In a table macro, a parameter hides a column of the same name; in .scalar(), the same clash raises ProgrammingError. Values are written in as SQL text; a param() raises TypeError.
replace=True
Replace a macro of that name. Without it, a second definition raises CatalogError.
temporary=True
Only this connection sees the macro, until it closes.
con.run("CREATE MACRO name(p) AS ...")
The SQL statement itself. AS TABLE and a plan's render() for a table macro. Several versions: AS a, (a, b) AS a + b.
con.run("DROP MACRO name") / "DROP MACRO TABLE name"
Remove a scalar or a table macro. IF EXISTS works.
fn(name, /, *args, **named)
Call a scalar macro in a plan. Keyword arguments are passed by name. A tuple as the name, such as ("util", "twice"), calls a macro in a schema.
table_function(name, *args, **named)
A table macro as a plan. Keyword arguments are passed by name.
duckdb_functions()
Every function DuckDB has, macros included: function_type is macro or table_macro, parameters the names without defaults, macro_definition the body as DuckDB writes it, extension_name where a function came from.

Extensions

con.run("INSTALL name")
Download for this DuckDB version and computer. FROM community, FROM core_nightly or FROM 'https://...' picks the repository. FORCE INSTALL downloads again.
con.run("LOAD name")
Load an installed extension. A path in quotes loads a file.
con.run("UPDATE EXTENSIONS")
Bring every installed extension up to date.
duckdb_extensions()
Every extension DuckDB knows: loaded, installed, install_path, description, extension_version, install_mode, installed_from.
duckdb_types()
Every type, with extension_name for one an extension added.
duckdb_settings()
Every setting with its description; the ones for extensions match name LIKE '%extension%'.

Settings

autoload_known_extensions
Load a known extension when a query needs it. On by default.
autoinstall_known_extensions
Download it first if it is not installed. On by default.
allow_community_extensions
Whether community extensions may be installed and loaded. On by default.
allow_unsigned_extensions
Load an extension without a signature. Only when you connect.
extension_directory
Where installed extensions are kept. Empty means ~/.duckdb/extensions.
custom_extension_repository
Where a plain INSTALL name looks instead of the core repository.

A macro and an extension belong to DuckDB, not to this Python package. Both work from every program that uses the same DuckDB, and an error from either is DuckDB's own. A macro that calls a Python function also needs that function registered in the program that calls the macro. Moving from DuckDB 1.5.6? See Coming from DuckDB 1.5.6.
