Python functions

You can write a function in Python and call it from SQL, like any function DuckDB has. Register it once with con.create_function. DuckDB then calls it with one row's values at a time, as ordinary Python values. By default it skips the call when an argument is NULL, and it may reuse a result instead of calling again: see NULL and Stability.

Start here

from duckdb import frame
from duckdb.frame import sql

con = frame.connect()
con.create_function("plus_one", lambda x: x + 1, ["BIGINT"], "BIGINT")

sql("SELECT plus_one(i) FROM range(5) t(i)").rows(con)   # [(1,), (2,), (3,), (4,), (5,)]

range(5) t(i) is a table named t with one column, i, holding the numbers 0 to 4. rows(con) runs the query and returns a list of tuples, one per row. A comment shows what the call returns, as you see it at the Python prompt or in a notebook; in a script, pass the result to print(). create_function is a method of a connection from frame.connect(); a DB-API connection, from duckdb.dbapi, does not have it.

create_function takes four things here:

  • "plus_one" is the name you call it by in SQL.
  • The lambda is the Python function. Any function works: a def, a lambda, a method, a functools.partial, a closure that remembers values from where it was made. It must not run a query on con itself, see Errors.
  • ["BIGINT"] lists the SQL type of each parameter. There is one parameter here, a whole number. Types are written as text, the way SQL writes them.
  • "BIGINT" is the SQL type of the result.

From then on, plus_one works like any DuckDB function: in a query, in a plan (a query you build in Python), in a view, or in a macro (a named piece of SQL). DuckDB turns each argument into a Python value before the call, and turns what you return into a value of the result type.

Your function returns one value per call. A list or dict it returns is still one value, not several rows. create_function cannot make a function that returns a table, or one that combines many rows into one value, as sum does.

The function belongs to the database, not to the connection. Every connection to the same database can call it, con.duplicate() included, while any of them is open: after con.close(), a duplicate can still call it. A new frame.connect() opens a different database, which does not have it. Python functions are not saved in a database file, so register them again when you open the file again.

Giving the types

DuckDB needs the type of each parameter and of the result before it first calls your function. You can give them in three ways: as a list, from the function's type hints, or as a dict for some parameters.

A list, in order

def weave(a, b, c):
    return f"{a}-{b}-{c}"

con.create_function("weave", weave, ["VARCHAR", "BIGINT", "BOOLEAN"], "VARCHAR")
sql("SELECT weave('x', 7, true)").rows(con)   # [('x-7-True',)]

The list has one type per parameter, in order. Each type is SQL type text, such as "DOUBLE", "DATE", "VARCHAR[]" or "DECIMAL(18, 2)", not a Python class. DECIMAL(18, 2) is an exact decimal number with up to 18 digits, 2 of them after the point. DuckDB's documentation lists every type.

From type hints

Type hints are the : str after a parameter and the -> str after the parentheses. If your function has them, you can leave the types out:

def shout(text: str, times: int) -> str:
    return text.upper() * times

con.create_function("shout", shout)
sql("SELECT shout('hi', 3)").rows(con)   # [('HIHIHI',)]

Here str means VARCHAR and int means BIGINT. Each hint gives the SQL type DuckDB uses for a Python value of that class:

Type hintSQL type
bool, int, float, str, bytesBOOLEAN, BIGINT, DOUBLE, VARCHAR, BLOB
datetime, date, time, timedelta, UUIDTIMESTAMP, DATE, TIME, INTERVAL, UUID
list[T], tuple[T, ...]a list of T, written T[]
dict[K, V]MAP(K, V), DuckDB's type for keys and values
T | None, Optional[T]the type for T, since any SQL value can be NULL
typing.Any, or no hintANY: a value of any type, see ANY

T, K and V stand for a type from the table other than Any, which only a whole parameter can have: list[int] means BIGINT[], and dict[str, int] means MAP(VARCHAR, BIGINT). An optional hint such as int | None only picks the SQL type. It does not make DuckDB pass a NULL, SQL's missing value, to your function as None: null_handling="special" does that (see NULL).

The result type works the same way: give returns, or a return hint such as -> str. You need one of the two. Without either, create_function raises InvalidInputError.

A dict, for some parameters

Some hints have no single SQL type. A Decimal, for example, does not say how many digits it has. For such a hint create_function raises InvalidInputError and names the parameter. Give that parameter's type in a dict, by name. The others still come from their hints:

from datetime import datetime
from decimal import Decimal

def price(amount: Decimal, when: datetime) -> str:
    return f"{amount} on {when:%Y-%m-%d}"

con.create_function("price", price, {"amount": "DECIMAL(18, 2)", "when": "TIMESTAMPTZ"})
sql("SELECT price(9.99, TIMESTAMPTZ '2026-03-01 10:00:00+00')").rows(con)   # [('9.99 on 2026-03-01',)]

The dict also changes a hint that works but is not what you want. A datetime hint means TIMESTAMP, a timestamp without a time zone, and a TIMESTAMPTZ value does not fit it. The dict above makes when a TIMESTAMPTZ instead.

These hints are refused unless you give the type:

  • Decimal: give the digits you need, for example "DECIMAL(18, 2)".
  • A bare list, tuple or dict, which does not say what it holds. Write list[int] instead, or give the type.
  • A choice of two types, such as int | str.
  • Any other class, your own classes included.

Details

  • The classes in the table must match exactly. A subclass, such as an IntEnum, is refused, because your function would receive plain values and not members of your class.
  • A tuple of fixed length, such as tuple[int, str], is refused, and so is typing.Any inside another type, such as list[Any].
  • The result cannot be ANY, whether from returns="ANY" or from -> typing.Any. That raises InvalidInputError: an ANY return type is not supported yet, because DuckDB must know the result type before the first call.

Names and defaults

Your function's parameters keep their names and their defaults in SQL. A call from SQL reaches your function the way the same call from Python would.

def area(width: float, height: float = 1) -> float:
    return width * height

con.create_function("area", area)
sql("SELECT area(3), area(3, 2), area(height := 4, width := 2)").rows(con)   # [(3.0, 6.0, 8.0)]

area(3) leaves height out, so your function gets its default. To pass an argument by name in SQL, write name := value or name => value: area(height := 4, width := 2) is area(height=4, width=2) in Python. *args, **kwargs and Python's other kinds of parameter work too: see More about parameters and type hints.

A call that does not fit is refused with ProgrammingError before the query runs. That happens for a missing argument, a name the function does not have, too many positional arguments, or a positional argument after a named one. The message lists the parameters:

sql("SELECT area(3, depth := 2)").rows(con)
# ProgrammingError: Binder Error: No function matches the given name and argument types
# 'area(INTEGER_LITERAL, "depth" := INTEGER_LITERAL)'. You might need to add explicit type casts.
#     Candidate functions:
#     area(width DOUBLE, height DOUBLE := 1.0) -> DOUBLE

Defaults

A default is turned into a value of its parameter's SQL type once, when you register. A default the type cannot hold is reported then, with InvalidInputError naming the parameter, and not at the first call. Each call gets a fresh copy of the default, so a list or dict default, even one inside another, is never shared between calls, unlike in plain Python:

def collect(item: int, bag: list[int] = []) -> int:
    bag.append(item)
    return len(bag)

con.create_function("collect", collect)
sql("SELECT collect(i) FROM range(3) t(i)").rows(con)   # [(1,), (1,), (1,)]

A default of None counts as a NULL argument. By default, DuckDB does not call your function when an argument is NULL, and the result is NULL. So a call that leaves out a parameter whose default is None returns NULL without calling your function. Register with null_handling="special" to receive the None. See NULL.

Details

  • Names are matched ignoring case, as everywhere in DuckDB: area(WIDTH := 2) reaches width. So two parameters whose names differ only in case, as in def f(a, A), are refused with InvalidInputError when you register.
  • A positional argument after a named one, or the same name given twice, gets an error message of its own, which says just that.
  • A default for a typed parameter is converted the way a returned value is (see Values in and out), so x: float = 1 arrives as 1.0. A default for an ANY parameter keeps its own type, so a date default arrives as a date.
  • A default that is not a SQL value at all, such as object(), is refused when you register, with InvalidInputError naming the parameter.
  • A default is converted with the settings of the connection that registers the function. A text default for a TIMESTAMPTZ parameter is read in that connection's TimeZone setting, and every connection then gets that same moment in time.

Any type: ANY

A parameter of type ANY takes a value of any SQL type. DuckDB does not cast it to another SQL type first, but it still turns it into a Python value, as for any parameter. A parameter with no type in parameters and no hint is ANY, and so is one hinted typing.Any.

con.create_function("kind", lambda x: type(x).__name__, ["ANY"], "VARCHAR")
sql("SELECT kind(1), kind('x'), kind([1]), kind(DATE '2026-01-02')").rows(con)   # [('int', 'str', 'list', 'date')]

Each value arrives as the Python value for its own SQL type, as in the table under Values in and out. So one function can take different types, even in the same query. A NULL follows the NULL handling. Other parameters of the same function still convert their values to their own types. Only parameters can be ANY: the result needs a real type.

Calling your function

Call it in SQL, in any query or statement on a connection to the database. con.run runs a statement and returns the number of rows it changed; for a query's rows, use sql(...).rows(con):

from duckdb.frame import col, fn, table

con.run("CREATE TABLE orders (id INTEGER, customer VARCHAR, total DECIMAL(6,2))")
con.run("INSERT INTO orders VALUES (1, 'acme', 1400), (2, 'bolt', 320)")

sql("SELECT id, plus_one(id) AS next_id FROM orders").rows(con)   # [(1, 2), (2, 3)]
con.run("CREATE TABLE next_ids AS SELECT plus_one(id) AS id FROM orders")   # 2

In a plan (a query you build in Python, see Frames & Plans), call it with fn, which calls any DuckDB function by name. Keyword arguments to fn are passed by name:

table("orders").select(col("id"), fn("plus_one", col("id")).alias("next_id")).rows(con)   # [(1, 2), (2, 3)]
table("orders").filter(fn("plus_one", col("id")) > 2).rows(con)   # [(2, 'bolt', Decimal('320.00'))]
table("orders").select(fn("area", col("id"), height=2).alias("a")).rows(con)   # [(2.0,), (4.0,)]
fn("area", col("id"), height=2)   # <Expr area("id", "height" := 2)>

types(con) gives a plan's column types from the declared result type, without running the query:

sql("SELECT plus_one(3) AS v").types(con)   # ['BIGINT']

While it works the types out, DuckDB may still call your function when its arguments are fixed values: sql("SELECT plus_one(3) + 1 AS v").types(con) calls it once.

Arguments are converted to the parameter types, as for any DuckDB function. DuckDB makes some conversions by itself: an INTEGER passed to a BIGINT parameter is widened, and a whole number or a DECIMAL passed to a DOUBLE parameter becomes a float. Some of these lose precision. 9007199254740993::BIGINT arrives in a DOUBLE parameter as 9007199254740992.0, and a DECIMAL with three digits after the point is rounded to two for a DECIMAL(18, 2) parameter. Other conversions DuckDB does not make by itself, such as a DECIMAL or a DOUBLE to a BIGINT, or a number to VARCHAR. Such a call is refused with ProgrammingError before the query runs:

table("orders").select(fn("plus_one", col("total"))).rows(con)
# ProgrammingError: Binder Error: No function matches the given name and argument types 'plus_one(DECIMAL(6,2))'.
# You might need to add explicit type casts.
#     Candidate functions:
#     plus_one(x BIGINT) -> BIGINT

Convert it yourself when that is what you mean:

table("orders").select(fn("plus_one", col("total").cast("BIGINT"))).rows(con)   # [(1401,), (321,)]

On a pandas DataFrame

To use your function on your own data, register the DataFrame as a table, call the function in a query, and get the result back as a DataFrame:

import pandas as pd

people = pd.DataFrame({"name": ["ann", "bob"]})
con.register("people", people)
sql("SELECT name, shout(name, 2) AS loud FROM people").to_pandas(con)
#   name    loud
# 0  ann  ANNANN
# 1  bob  BOBBOB

Watch out for whole numbers with a missing value. pandas stores such a column as float64, so DuckDB reads it as DOUBLE, and plus_one refuses it with ProgrammingError. pandas' nullable "Int64" dtype keeps the column whole numbers, and the missing value arrives as NULL:

ages = pd.DataFrame({"age": pd.Series([20, None], dtype="Int64")})
con.register("ages", ages)
table("ages").types(con)                        # ['BIGINT']
sql("SELECT plus_one(age) FROM ages").rows(con)   # [(21,), (None,)]

Querying Python data tells you what else you can register, such as a polars DataFrame.

What your function returns is converted to the result type you declared, the way SQL's CAST converts a value of the type in the second table below. A float is a DOUBLE there, so for an INTEGER it becomes the nearest whole number, and a value exactly halfway becomes the even one:

con.create_function("half", lambda x: x / 2, ["BIGINT"], "INTEGER")
sql("SELECT half(9), half(11)").rows(con)   # [(4, 6)]: 4.5 becomes 4, and 5.5 becomes 6

con.create_function("as_date", lambda x: f"2020-01-0{x}", ["BIGINT"], "DATE")
sql("SELECT as_date(5)").rows(con)   # [(datetime.date(2020, 1, 5),)]: the text becomes a DATE

con.create_function("wide", lambda x: 2**70, ["BIGINT"], "INTEGER")
sql("SELECT wide(1)").rows(con)
# InvalidInputError: Invalid Input Error: the UDF 'wide' returned a value that cannot be converted to its declared type INTEGER:
# Failed to cast value: Type UINT128 with value 1180591620717411303424 can't be cast because the value is out of range for the destination type INT32

A value that cannot be converted fails the query, and the message names your function and its result type. DuckDB calls your function a UDF there, short for user-defined function. Since every result is checked this way, declare the type you mean: a function that should return an INTEGER should say "INTEGER".

Turn them into Python values before you return them, with int(), float(), bool() or .item(), and an array with .tolist(). np.float64 works as it is, because it is a Python float.

Lists and structs

con.create_function("total", lambda xs: sum(xs), ["BIGINT[]"], "BIGINT")
con.create_function("field", lambda s: s["a"], ["STRUCT(a INTEGER)"], "INTEGER")
sql("SELECT total([1, 2, 3]), field({'a': 7})").rows(con)   # [(6, 7)]

con.create_function("pair", lambda x: [x, x + 1], ["BIGINT"], "BIGINT[]")
con.create_function("wrap", lambda x: {"v": x}, ["BIGINT"], "STRUCT(v BIGINT)")
sql("SELECT pair(3), wrap(9)").rows(con)   # [([3, 4], {'v': 9})]

A list arrives as a list and goes back as one. A struct arrives as a dict and goes back as one. An empty list you return becomes an empty list of the declared type: [] for a BIGINT[] is an empty BIGINT[].

Details

  • Dates and times are converted more strictly than CAST would. A date or timestamp that the result type cannot hold exactly is refused, not rounded: a timestamp with microseconds returned for TIMESTAMP_S, for example.
  • A date or time without a time zone, returned for a type with one, is refused, and so is the reverse, because the conversion would have to guess a time zone. A timestamp with a time zone returned for TIME is refused for the same reason. A timestamp without one, returned for TIME, keeps only its time of day.
  • These date and time rules hold inside lists and structs too, at any depth.
  • Text returned for a TIMESTAMPTZ is read in the connection's TimeZone setting, as CAST reads the same text, and then arrives in Python in UTC like any TIMESTAMPTZ. After SET TimeZone = 'America/New_York', the text '2026-03-01 10:00:00' comes back as 15:00 UTC. SELECT current_setting('TimeZone') shows the setting.
  • SQL reads 4.5 written in a query as a DECIMAL, which rounds halves away from zero: CAST(4.5 AS INTEGER) is 5, but CAST(4.5::DOUBLE AS INTEGER) is 4, as for your function's float.
  • A dict returned for a STRUCT is matched to the fields by name, ignoring case. A field the dict does not have is NULL, and a key that matches no field is dropped without its value being read. At least one key must match a field: for STRUCT(a BIGINT, b BIGINT), {"a": 1} gives {'a': 1, 'b': None}, but {} and {"other": 5} fail the query.
  • A dict whose only key is the empty string fills the one field of a struct that has one field, and fails the query for a struct with more.

Details: a UNION result

A UNION holds one value of one of several types, each with a name: its members. union_tag tells you which member a value is in:

con.create_function("num_or_text", lambda x: x if x < 10 else f"{x} is big", ["BIGINT"], "UNION(num BIGINT, txt VARCHAR)")
sql("SELECT num_or_text(5), num_or_text(50)").rows(con)                       # [(5, '50 is big')]
sql("SELECT union_tag(num_or_text(5)), union_tag(num_or_text(50))").rows(con)   # [('num', 'txt')]
  • DuckDB reads your value by its Python type, as in the table above, and puts it in the member of that type: an int in a BIGINT member, a str in a VARCHAR member.
  • If no member has that type, the value goes into a member that DuckDB converts the type to by itself, as for arguments (see Calling your function): an int into a DOUBLE member, a date into a TIMESTAMP member. When several members could take it, DuckDB picks the one SQL's CAST to the same UNION picks.
  • The query fails if no member can take the value, or if two members of the same type can. So an int does not go into an INTEGER member, a float does not go into a BIGINT or VARCHAR member, and a dict goes into a struct member only when it has exactly that member's fields.
  • The date and time rules above then apply in the member chosen, and no other member is tried: a timestamp without a time zone is refused for UNION(z TIMESTAMPTZ, s VARCHAR).

To be sure where a value goes, declare a member of exactly the type DuckDB reads your value as.

NULL

By default, if any argument is NULL, DuckDB does not call your function for that row, and the result is NULL:

calls = []

def observe(x):
    calls.append(x)
    return x

con.create_function("observe", observe, ["BIGINT"], "BIGINT", stability="volatile")
sql("SELECT observe(x) FROM (VALUES (1), (NULL), (3)) t(x)").rows(con)   # [(1,), (None,), (3,)]
calls                                                                    # [1, 3]

observe records its calls, so it is registered as "volatile", which tells DuckDB not to reuse its results (see Stability).

The rule looks at each argument as a whole. A list that holds a NULL is not NULL itself, so your function is called, and the NULL arrives as None inside the list. The same goes for a field of a struct. So total([1, NULL, 3]), with the total above, fails the query, because sum cannot add None. Skip such items yourself, as in sum(x for x in xs if x is not None).

With null_handling="special", your function is called with None and decides what to return:

con.create_function("backfill", lambda x: -1 if x is None else x, ["BIGINT"], "BIGINT", null_handling="special")
sql("SELECT backfill(x) FROM (VALUES (1), (NULL)) t(x)").rows(con)   # [(1,), (-1,)]

Every argument counts, however it was passed. A parameter left out whose default is None, an extra argument in *args, and a NULL passed by name into **kwargs all give NULL without a call under the default setting:

con.create_function("tagged", lambda x, tag=None: f"{x}:{tag}", ["BIGINT", "VARCHAR"], "VARCHAR")
sql("SELECT tagged(1), tagged(1, 'a')").rows(con)   # [(None, '1:a')]

con.create_function("tagged", lambda x, tag=None: f"{x}:{tag}", ["BIGINT", "VARCHAR"], "VARCHAR",
                    null_handling="special")
sql("SELECT tagged(1), tagged(1, 'a')").rows(con)   # [('1:None', '1:a')]

Return None for a missing result: it gives NULL, whichever setting you chose. pd.NaT gives NULL too, but float("nan") stays NaN, and pd.NA is refused:

con.create_function("odd_only", lambda x: x if x % 2 else None, ["BIGINT"], "BIGINT")
sql("SELECT odd_only(i) FROM range(4) t(i)").rows(con)   # [(None,), (1,), (None,), (3,)]

Details

  • A None inside a list or dict you return is a NULL of the declared type at that place: [ts, None] returned for TIMESTAMP[] holds a NULL TIMESTAMP. An empty list, or an empty dict for a MAP, is an empty value of the declared type. An empty dict for a STRUCT fails the query, see Values in and out.
  • For a UNION result, a list or dict that holds only None values has no type of its own, so it can change which member DuckDB picks. Return None for the whole value when you mean NULL.

Errors

An exception raised inside your function fails the query that called it, with InvalidInputError. The message names your function, then the exception's class and text, then the traceback. To handle it in your program, catch the error class, which you import from duckdb.exceptions:

from duckdb.exceptions import InvalidInputError

def boom(x):
    raise ValueError(f"no thanks: {x}")

con.create_function("boom", boom, ["BIGINT"], "BIGINT")
try:
    sql("SELECT boom(7)").rows(con)
except InvalidInputError as error:
    print(error)
# Invalid Input Error: Python exception occurred while executing the UDF 'boom': ValueError: no thanks: 7
# Traceback (most recent call last):
#   ...
# ValueError: no thanks: 7

print(sql("SELECT 42").rows(con))   # [(42,)]: the connection still works

The function still works afterwards, and outside a transaction so does the connection. Inside a transaction you started with BEGIN, the failed query aborts the transaction: every later statement fails with TransactionError until you end it with ROLLBACK, or with COMMIT, which then also discards its changes. A with con.transaction(): block rolls back for you when the error leaves it. A KeyboardInterrupt raised inside your function, which is what pressing Ctrl‑C during such a query does, is reported the same way, as InvalidInputError, so except KeyboardInterrupt does not catch it.

A returned value that DuckDB cannot read, or cannot convert to the result type, also fails the query with InvalidInputError:

con.create_function("odd", lambda x: object(), ["BIGINT"], "BIGINT")
sql("SELECT odd(1)").rows(con)
# InvalidInputError: Invalid Input Error: the UDF 'odd' returned a value of type object, which cannot be converted to a DuckDB value

Your function must not run a query on the connection that is calling it, because a connection runs one query at a time. The inner query fails, and so does yours:

def order_count(x):
    return sql("SELECT count(*) FROM orders").rows(con)[0][0]

con.create_function("order_count", order_count, ["BIGINT"], "BIGINT")
sql("SELECT order_count(1)").rows(con)
# InvalidInputError: Invalid Input Error: Python exception occurred while executing the UDF 'order_count':
# OperationalError: Resource In Use Error: connection has a live result; ...

Every use of the connection from inside your function, such as types(), count(), or a plan with a step such as filter(), fails at once with the same error. A second connection from con.duplicate() fails the same way when DuckDB calls your function from several threads at once. Do the lookup in the query instead, with a join, or read what your function needs into a Python dict before the query.

Closing the connection is not refused, but do not close it while a query that calls your function is running, either from inside your function or from another thread. With rows(), the program can then hang: ending the query waits for your function, which cannot finish. To stop such a query from another thread, call con.interrupt().

Handling an error

If you want NULL instead of an error, catch the exception inside your function and return None:

def parse_age(text):
    try:
        return int(text)
    except ValueError:
        return None

con.create_function("parse_age", parse_age, ["VARCHAR"], "BIGINT")
sql("SELECT parse_age('42'), parse_age('old')").rows(con)   # [(42, None)]

Which error, when

create_function checks everything it can when you register, so most mistakes show up there, not at the first call:

Inside a transaction, a refused registration can abort the transaction. This happens when DuckDB refuses a type you give it: a name it does not know, or a type it cannot build, such as DECIMAL(5, 9). The transaction is then aborted, as after any failed statement, and every following statement fails with TransactionError until you run ROLLBACK. A default DuckDB cannot convert, such as "five" or 2**70 for a BIGINT, leaves the transaction usable, and so does a mistake the package catches before asking DuckDB: a default such as object(), a timestamp default without a time zone for a TIMESTAMPTZ, a hint no type can be read from, or a list with too many types.

Stability

stability tells DuckDB whether it may reuse a result instead of calling your function again. DuckDB trusts what you say and never checks it, so a wrong setting gives wrong rows, not an error.

"consistent"
The default. The same arguments always give the same result. DuckDB may call your function once for a call whose arguments are fixed values and reuse the result, and may compute f(x) once when a query uses it twice.
"consistent_within_query"
The same arguments give the same result within one query, but a later query may get another. DuckDB's own now() works this way.
"volatile"
The result may differ on every call, so DuckDB never reuses one. It promises no number of calls: each use in a query calls separately, and a filter with LIMIT can call it for more rows than come back.

Use "volatile" for anything random, anything that keeps state, and anything with side effects. A function with no arguments shows the difference most clearly:

consistent: one call, five copies
counter = iter(range(1_000_000))
con.create_function("tick", lambda: next(counter), [], "BIGINT")
sql("SELECT tick() FROM range(5) t(i)").rows(con)
# [(0,), (0,), (0,), (0,), (0,)]
volatile: one call per row
counter = iter(range(1_000_000))
con.create_function("tick", lambda: next(counter), [], "BIGINT", stability="volatile")
sql("SELECT tick() FROM range(5) t(i)").rows(con)
# [(0,), (1,), (2,), (3,), (4,)]

The same goes for a function with arguments: SELECT observe(1) FROM range(5) t(i) calls the volatile observe above five times, and would call it once if it were consistent. For a function whose result depends only on its arguments, keep the default. Computing a call once and reusing the result is what makes it cheap in a WHERE or a join condition.

Volatile does not make DuckDB call your function where the query does not need the result. SELECT count(*) FROM (SELECT observe(i) FROM range(5) t(i)) never calls it, and a NULL argument still skips the call unless you register with null_handling="special". So do not count on a query to run your function once per row for what it does on the side, such as sending a message: loop over the rows in Python instead.

Threads

DuckDB splits a large query across several threads so it finishes sooner. Your function can be called from any of those threads, and from several of them during one query:

import threading

con.run("SET threads = 4")
seen = set()
lock = threading.Lock()

def note_thread(x):
    with lock:
        seen.add(threading.get_ident())
    return x + 1

con.create_function("note_thread", note_thread, ["BIGINT"], "BIGINT", stability="volatile")
con.run("CREATE TABLE million AS SELECT i FROM range(1000000) t(i)")
sql("SELECT sum(note_thread(i)) FROM million").rows(con)   # [(500000500000,)]
len(seen)                                                # 4 on our machine; it can be fewer
con.run("RESET threads")                                   # back to the default, one thread per core

Python runs only one thread's Python code at a time, but it can switch threads in the middle of your function. So if your function changes something shared between calls, such as the set seen, a list, a counter or a network client, guard that change with a threading.Lock, as note_thread does. Only one thread at a time runs the code inside with lock:. A counter needs the lock too:

count = 0

def counted(x):
    global count
    with lock:
        count += 1
    return x

con.create_function("counted", counted, ["BIGINT"], "BIGINT", stability="volatile")
sql("SELECT sum(counted(i)) FROM million").rows(con)   # [(499999500000,)]
count                                                 # 1000000

A function that uses only its arguments and its own local variables needs no lock.

What is shared: the objects your function reaches through global variables or its closure are the same objects on every thread. So is the default of a parameter SQL cannot pass (see More about parameters and type hints). A default SQL can pass is different: each call gets a fresh copy of it, as in Defaults.

What is not shared: values that belong to one thread. A threading.local or a contextvars.ContextVar that you set in your own thread reads as unset when one of DuckDB's threads calls your function. Your own thread may run part of the query too, and there it still sees its own value. Pass such a value in as an argument, or read it in your own thread before the query, as in value = var.get() for a ContextVar called var, and let your function use value: capturing var itself does not help.

You can also run queries that call the same function from several Python threads at once, each with its own connection from con.duplicate().

Details

  • Each of DuckDB's threads takes Python's global lock (the GIL) for a batch of rows, calls your function once per row of that batch, and then lets the lock go. This is why more threads barely speed up a Python function: see Speed.
  • While a query runs, the thread that started it does not hold the lock, so your other Python threads keep running.

Free-threaded Python is not tested here yet. On a Python built without the global lock, such as 3.14t, the package installs and imports. Nothing has yet tested your function being called from several DuckDB threads at the same moment with no lock between them.

Registering a name again

Register a name again with the same parameter types to replace the function. Register it with other types, or with another number of parameters, and you add a second version beside the first:

con.create_function("spell", lambda x: f"number {x}", ["BIGINT"], "VARCHAR")
con.create_function("spell", lambda x: f"text {x}", ["VARCHAR"], "VARCHAR")
sql("SELECT spell(1), spell('a')").rows(con)   # [('number 1', 'text a')]

con.create_function("spell", lambda x: f"#{x}", ["BIGINT"], "VARCHAR")
sql("SELECT spell(1), spell('a')").rows(con)   # [('#1', 'text a')]: the BIGINT version was replaced

DuckDB picks the version that the arguments fit with the least converting, as it does for its own functions. If two versions fit equally well, the query is refused with ProgrammingError.

You cannot remove a function: DROP FUNCTION refuses with CatalogError. It stays until the database is closed, and registering the name again is how you change it.

Pick a name DuckDB does not already use. A built-in's name, such as upper, replaces DuckDB's own version with the same parameter types on every connection to the database, and nothing brings it back while the database is open; the name of an aggregate or a macro, such as sum or nullif, raises InternalError.

Details

  • The name is a plain string. A function cannot go in a schema: a tuple such as ("util", "f") raises TypeError. A dot is part of the name, so "util.f" registers a function called util.f, which SQL then has to quote: "util.f"(1).
  • Whether a parameter is positional-only or plain makes no difference here: def f(x) and def f(x, /) with the same type replace each other. A keyword-only parameter does make a difference: def f(x) and def f(*, x) under one name are two versions, and a call by name that both fit, f(x := 1), is refused with ProgrammingError as ambiguous.
  • A macro with the same name as your function takes precedence over it. See Macros & Extensions.

Speed, and when a macro is better

Every row costs a trip into Python and back. DuckDB turns the arguments into Python objects, calls your function, and turns the result back into a DuckDB value. For work you can write in SQL, a macro is much faster. A macro is a piece of SQL with a name: DuckDB copies it into the query and never calls Python.

con.run("CREATE TABLE big AS SELECT i FROM range(5000000) t(i)")
con.create_macro("add_one", ["x"], col("x") + 1)

sql("SELECT sum(plus_one(i)) FROM big").rows(con)   # [(12500002500000,)] in about 1.8 s on a 64-core Linux machine
sql("SELECT sum(add_one(i)) FROM big").rows(con)    # [(12500002500000,)] in about 1.4 ms, the same as sum(i + 1)

That is more than a thousand times faster. More threads hardly help the Python function, because only one thread can run Python code at a time.

Use a Python function for what SQL cannot do: calling a Python library, looking something up in your Python data, or reading a format DuckDB has no function for. For anything you can write as an expression, a computation over columns with SQL's operators and functions, however long, a macro is usually the better choice. Macros & Extensions shows how to write one and how to choose. When you do need a Python function:

  • Keep its own work small, and let DuckDB do the filtering and grouping around it.
  • Keep stability="consistent" when its result depends only on its arguments, so DuckDB can reuse results.

More about parameters and type hints

You need this section only when your function uses *args, **kwargs or Python's other kinds of parameter, when SQL should not see a parameter, or when you register one of Python's built-in functions. Its Details also say how type hints are read.

The five kinds of parameter

Python has five ways to declare a parameter. Each one works from SQL as it does in Python:

Python parameterFrom SQL, you pass it
positional-only, before a /: def f(x, /)by position only
a plain parameter: def f(x)by position, or by name: f(x := 1)
*argsas the extra positional arguments, which arrive as a tuple
keyword-only, after * or *args: def f(*, x)by name only
**kwargsas the extra named arguments, which arrive as a dict
 
def label(value, /, prefix="id", *parts, sep="-", **extra):
    tags = "".join(f"[{k}={v}]" for k, v in extra.items())
    return sep.join([prefix, str(value), *map(str, parts)]) + tags

con.create_function("label", label, returns="VARCHAR")
sql("SELECT label(7)").rows(con)                                      # [('id-7',)]
sql("SELECT label(7, 'x', 1, 2, sep := '/', loud := true)").rows(con)   # [('x/7/1/2[loud=True]',)]

label(7) uses every default. In the second call, 'x' goes to prefix, 1 and 2 go to parts, sep := '/' goes to sep, and loud := true, which matches no parameter, goes to extra. These parameters have no type hints, so they take values of any type (see ANY).

Keeping a parameter out of SQL

A list of types can be shorter than the list of parameters. SQL then sees only the parameters the list covers, and Python fills in the rest from their defaults, as in any call that leaves them out. This is useful when a default only carries a value into the function, as in this loop:

for offset in range(3):
    con.create_function(f"plus_{offset}", lambda x, offset=offset: x + offset, ["BIGINT"], "BIGINT")

sql("SELECT plus_0(1), plus_2(1)").rows(con)   # [(1, 3)]

SQL cannot pass offset: plus_2(1, 5) is refused with ProgrammingError. Every parameter after the end of the list needs a default, or must be *args or **kwargs, which then receive nothing. Otherwise create_function raises InvalidInputError.

Built-in functions such as max

Python cannot tell what parameters some of its built-in functions take, such as max and dict. For those, give parameters as a list:

  • Each plain type is one parameter, passed by position.
  • "*T" gives the type T of any extra positional arguments, as for *args.
  • "**T" gives the type T of any extra named arguments, as for **kwargs.

Put them in that order, with at most one "*T" and one "**T". returns is required.

con.create_function("biggest", max, ["*BIGINT"], "BIGINT")
con.create_function("pack", dict, ["**BIGINT"], "MAP(VARCHAR, BIGINT)")
sql("SELECT biggest(1, 5, 3), pack(a := 1, b := 2)").rows(con)   # [(5, {'a': 1, 'b': 2})]

Details

  • **kwargs receives each name spelled the way the caller wrote it.
  • SQL cannot see the name of a positional-only parameter. A named argument with that name goes to **kwargs, as in Python.
  • The type of *args applies to each extra positional argument, and the type of **kwargs to each extra named one, as their hints mean in Python. With *rest: int, every extra argument is converted to BIGINT. An argument that cannot be converted fails the query with ConversionError.
  • In a list of types, the type for *args or **kwargs may carry its mark: "*BIGINT", "**BIGINT". A mark that does not match the parameter is refused. In a dict, *args and **kwargs are named without the mark: {"rest": "BIGINT"}.
  • A list with more types than parameters is refused, and so is a dict key that is not a parameter's name. Both raise InvalidInputError.
  • A default after the end of a shorter list stays Python's own object: every call, on every thread, gets that same object, as with any object a closure or a global variable refers to. A default SQL sees is different: it is converted once and arrives as a fresh value on every call. See Threads.
  • A hint written wholly as text, such as "int", is evaluated, and so is every hint in a module that uses from __future__ import annotations. A quoted name inside another hint, such as list["int"] or Optional["int"], is not evaluated, and is refused like any hint no type can be read from.
  • Python evaluates all of a function's hints together. If one of them fails, for example a name you import only for type checking, none of them can be read. Then every parameter with a hint, and the result, needs its type in parameters and returns. The error names the hint and Python's own error.
  • On Python 3.14, a hint whose code raises an error other than a missing name leaves Python with no description of the function at all. The registration is then refused, whatever parameters says.
  • A hint naming one of the function's own type parameters, such as T in def f[T](x: T), is refused like any hint no type can be read from. On Python 3.12.0 to 3.12.4, a type parameter named in a hint of a function reached through functools.partial, a wrapper or a callable object resolves as a module name, as it does in Python itself there.

Reference

Registering

con.create_function(name, function, parameters=None, returns=None, *, null_handling="default", stability="consistent")
Make function callable from SQL as name, on every connection to the database. Its parameters keep their names, kinds and defaults. Returns None. The same name with the same parameters replaces the function; with other parameters it adds a version.
name
A plain string. It cannot be put in a schema.
function
Any callable: a def, a lambda, a method, a functools.partial, a closure. It must not run a query on the connection that calls it.
parameters
SQL types as text. A list gives them in order; parameters after its end are left to their Python defaults. A dict gives some of them by name; the rest come from the type hints. A parameter with neither is ANY. For a built-in Python cannot describe, a list of plain types, then "*T", then "**T".
returns
The result type as SQL text. Without it, the return type hint. What your function returns is converted to it.
null_handling="default"
A NULL argument, or a left-out parameter whose default is None, gives NULL without a call.
null_handling="special"
None is passed to your function, which decides.
stability="consistent"
The same arguments always give the same result. DuckDB may reuse results.
stability="consistent_within_query"
The same within one query, free to change between queries.
stability="volatile"
No result is reused, but the number of calls is not fixed. A NULL argument still skips the call under null_handling="default". For anything random, stateful or with side effects.
con.create_macro(name, parameters, body)
The faster choice for anything you can write as an expression. See Macros & Extensions.

Calling

name(...) in SQL
In any query or statement, on a connection to the database the function was registered on. name := value or name => value passes an argument by name.
fn(name, /, *args, **named)
Calls any function by name in a plan. Keyword arguments are passed by name.
