User-defined functions

A user-defined function is a Python callable registered as a scalar SQL function on the database. The engine calls it once per row, from its own threads, with the arguments as Python values, and casts what it returns to the type you declared.

Start here

import duckdb
from duckdb import sql

con = duckdb.connect()
con.create_function("plus_one", lambda x: x + 1, ["BIGINT"], "BIGINT")

sql("SELECT plus_one(i) FROM range(5) t(i)").rows(con)   # [(1,), (2,), (3,), (4,), (5,)]

create_function registers a Python callable as a scalar SQL function on the database. From then on plus_one is a function like any the engine has: it can be called from SQL, from a plan, inside a view, inside a macro.

Registering

con.create_function(name, function, parameters, returns, *, null_handling="default", stability="consistent")
name
The SQL name. Registering a name that is already registered replaces the function.
function
Any callable taking one positional argument per parameter: a lambda, a def, a bound method, a functools.partial. A closure keeps its state.
parameters
The argument types, as SQL type text: ["VARCHAR", "BIGINT"], ["STRUCT(a INTEGER)"], [] for a function of no arguments. Not Python types.
returns
The result type, as SQL type text.
null_handling
"default" or "special". See NULL.
stability
"consistent", "consistent_within_query" or "volatile". See Stability.
def weave(a, b, c):
    return f"{a}-{b}-{c}"

con.create_function("weave", weave, ["VARCHAR", "BIGINT", "BOOLEAN"], "VARCHAR")
sql("SELECT weave('x', 7, true)").rows(con)   # [('x-7-True',)]

prefix = "state"
con.create_function("tag", lambda x: f"{prefix}:{x}", ["BIGINT"], "VARCHAR")
sql("SELECT tag(1)").rows(con)   # [('state:1',)]

The type texts are parsed by the engine when you register, so a mistake in one is reported here and not at the first call: a type that does not exist raises CatalogError naming it, and ANY is refused with InvalidInputError: ANY parameters are not supported yet, or an ANY return type is not supported yet for returns. An option that is not one of the choices above raises InvalidInputError. A closed connection raises InterfaceError.

The function belongs to the database, not to the connection. Every connection to that database sees it, con.duplicate() included, and the engine keeps it until the database closes. There is no way to remove one; register the same name again to replace it. A fresh duckdb.connect() is a different database, and does not have it.

Calling it

From SQL, on any plan or statement that runs on the connection:

sql("SELECT plus_one(i) FROM range(3) t(i)").rows(con)
con.run("CREATE TABLE next_ids AS SELECT plus_one(id) AS id FROM orders")

From a plan, through fn, which calls any function by name; a registered function is one:

from duckdb import col, fn, table

table("orders").with_columns(next_id=fn("plus_one", col("id"))).rows(con)
table("orders").filter(fn("plus_one", col("id")) > 1).rows(con)

sql("SELECT plus_one(3) AS v").types(con)   # ['BIGINT']: the engine knows it like any function

The call renders as plus_one("id") in the SQL, and nothing about it differs from a call to an engine function. DuckDB matches the arguments to the declared parameters as it does for every function: a TINYINT or an INTEGER passed to a BIGINT parameter is cast on the way in; a DECIMAL passed to it is refused when the query is planned, with the usual ProgrammingError that no function matches the given name and argument types.

con.create_function("half", lambda x: x / 2, ["BIGINT"], "INTEGER")
sql("SELECT half(9)").rows(con)        # [(4,)]: the DOUBLE 4.5 is cast to INTEGER

con.create_function("as_date", lambda x: f"2020-01-0{x}", ["BIGINT"], "DATE")
sql("SELECT as_date(5)").rows(con)     # [(datetime.date(2020, 1, 5),)]: the text is cast to DATE

con.create_function("wide", lambda x: 2**70, ["BIGINT"], "INTEGER")
sql("SELECT wide(1)").rows(con)        # InvalidInputError: Failed to cast value ... out of range for the destination type INT32

A cast that fails fails the query, with the engine's message for that cast. Every result is cast to the declared type, so a function that means to return an INTEGER should declare INTEGER and let the cast check it.

nested types

con.create_function("total", lambda xs: sum(xs), ["BIGINT[]"], "BIGINT")
con.create_function("field", lambda s: s["a"], ["STRUCT(a INTEGER)"], "INTEGER")
sql("SELECT total([1, 2, 3]), field({'a': 7})").rows(con)   # [(6, 7)]

con.create_function("pair", lambda x: [x, x + 1], ["BIGINT"], "BIGINT[]")
con.create_function("wrap", lambda x: {"v": x}, ["BIGINT"], "STRUCT(v BIGINT)")
sql("SELECT pair(3), wrap(9)").rows(con)   # [([3, 4], {'v': 9})]

A list arrives as a list and goes back as one; a struct arrives as a dict and goes back as one. An empty list returned has no element type of its own and is cast to the declared one, so [] for a BIGINT[] is an empty BIGINT[].

NULL

With null_handling="default", a NULL in any argument makes the result NULL for that row, and the function is not called for it:

calls = []

def observe(x):
    calls.append(x)
    return x

con.create_function("observe", observe, ["BIGINT"], "BIGINT")
sql("SELECT observe(x) FROM (VALUES (1), (NULL), (3)) t(x)").rows(con)   # [(1,), (None,), (3,)]
calls                                                                    # [1, 3]

With null_handling="special", None arrives and the function decides:

con.create_function("backfill", lambda x: -1 if x is None else x, ["BIGINT"], "BIGINT", null_handling="special")
sql("SELECT backfill(x) FROM (VALUES (1), (NULL)) t(x)").rows(con)   # [(1,), (-1,)]

Returning None makes the result NULL under either setting:

con.create_function("odd_only", lambda x: x if x % 2 else None, ["BIGINT"], "BIGINT")
sql("SELECT odd_only(i) FROM range(4) t(i)").rows(con)   # [(None,), (1,), (None,), (3,)]

So does returning pandas' pd.NA, when pandas is around.

Stability

stability is a promise about the function, and the engine plans by it. It is never checked; a wrong promise gives wrong rows, not an error.

"consistent"
The default. Same arguments, same result, always. The engine may compute a call whose arguments are constant once and reuse the value, and may treat repeated calls as one.
"consistent_within_query"
Same arguments, same result within one query, but a later query may see another. What the engine's own now() declares.
"volatile"
The result may differ per row. The engine calls the function once per row, every time.

Anything random, stateful or side-effecting is volatile, and a function of no arguments is the clearest case: declared consistent, it is called once and its value repeated.

consistent: one call, five copies
counter = iter(range(1_000_000))
con.create_function("tick", lambda: next(counter), [], "BIGINT")
sql("SELECT tick() FROM range(5) t(i)").rows(con)
# [(0,), (0,), (0,), (0,), (0,)]
volatile: one call per row
counter = iter(range(1_000_000))
con.create_function("tick", lambda: next(counter), [], "BIGINT", stability="volatile")
sql("SELECT tick() FROM range(5) t(i)").rows(con)
# [(0,), (1,), (2,), (3,), (4,)]

The same holds with arguments: SELECT observe(1) FROM range(5) t(i) calls a consistent observe once and a volatile one five times. Declare a pure function consistent: computing a call once and reusing the value is what makes it cheap in a WHERE or a join condition.

Threads

The engine runs a query on its worker threads, and it calls the function from whichever worker is executing that part of the query. For each batch of rows the worker takes the GIL once, converts the batch's arguments, calls the function once per row, and releases the GIL again. The thread that started the query drops the GIL while it waits on the engine, which is what lets the workers take it.

Two things are tested in tests/test_udf.py:

1
With SET threads = 4 and a million-row aggregate over the function, the function was entered from more than one thread. The calling thread was among them; it was not the only one.
2
Three Python threads, each on its own con.duplicate(), ran a query over the same function at the same time, and each got the right answer.
con.run("SET threads = 4")
seen = set()

def bump(x):
    seen.add(threading.get_ident())
    return x + 1

con.create_function("bump", bump, ["BIGINT"], "BIGINT")
con.run("CREATE TABLE big AS SELECT i FROM range(1000000) t(i)")
sql("SELECT sum(bump(i)) FROM big").rows(con)   # [(500000500000,)]
len(seen)                                          # 4 on this machine; the test asserts at least 2

What this means for the function: it may be entered from any thread, and from several over the course of one query. The GIL serialises bytecode, not calls, so two workers can be inside the function at once, interleaved. State it shares across calls, a list it appends to, a counter, a client, needs to be safe for that, or the function needs to take a lock.

Free-threaded Python is untested here. The free-threaded wheel builds and imports with the GIL off, and that is all that has been verified. Nothing yet exercises a function being called from several engine workers at once without a GIL to serialise them.

Errors

An exception raised inside the function fails the query that called it. The error is the query's InvalidInputError; its message names the function, then the exception's class and text, then the traceback:

def boom(x):
    raise ValueError(f"no thanks: {x}")

con.create_function("boom", boom, ["BIGINT"], "BIGINT")
sql("SELECT boom(7)").rows(con)
# InvalidInputError: Invalid Input Error: Python exception occurred while executing the UDF 'boom': ValueError: no thanks: 7
# Traceback (most recent call last):
#   ...
# ValueError: no thanks: 7

sql("SELECT 42").rows(con)   # [(42,)]: the connection is fine

The connection survives, and so does the function; the next query runs as usual. A KeyboardInterrupt raised inside the function is reported the same way, as the query's InvalidInputError: the engine owns the call and sees only that it failed.

The other failures at run time are a returned value that cannot be read and one that cannot be cast to returns (InvalidInputError, with the engine's cast message). Both fail the query the same way, and the message carries one Invalid Input Error: prefix. Failures at registration are listed under Registering.

con.create_function("odd", lambda x: object(), ["BIGINT"], "BIGINT")
sql("SELECT odd(1)").rows(con)
# InvalidInputError: Invalid Input Error: the UDF 'odd' returned a value of type object, which cannot be converted to a DuckDB value

Performance

Every row costs a trip through Python: the arguments are turned into Python objects, the function is called, the result is turned back into a value and cast. Anything expressible as an expression runs orders of magnitude faster as a macro, because a macro is inlined into the query and never leaves the engine.

from duckdb import col

con.run("CREATE TABLE big AS SELECT i FROM range(5000000) t(i)")
con.create_function("plus_one", lambda x: x + 1, ["BIGINT"], "BIGINT")
con.create_macro("bump", ["x"], col("x") + 1)

sql("SELECT sum(plus_one(i)) FROM big").rows(con)   # 0.45 s on one laptop
sql("SELECT sum(bump(i)) FROM big").rows(con)       # 0.002 s, the same as sum(i + 1)

Use a function for what SQL cannot say: a call into a library, a lookup into Python state, a format the engine has no parser for. For anything that is an expression, however long, a macro is usually the better answer; create_macro and how far a macro goes are on Macros & Extensions. Keep a function's own work small, declare it consistent when it is pure so the engine can compute a call once and reuse the value, and let the engine do the filtering and grouping around it.

Reference

Registration

con.create_function(name, function, parameters, returns, *, null_handling, stability)
Register function as scalar SQL function name on the database. Returns nothing. A name already registered is replaced.
parameters
SQL type texts, one per positional argument. Empty for no arguments. ANY is refused.
returns
One SQL type text. The returned value is cast to it.
null_handling="default"
A NULL argument gives NULL without a call.
null_handling="special"
None is passed in; the function decides.
stability="consistent"
Pure. The engine may compute a call once and reuse the value, and may treat repeated calls as one.
stability="consistent_within_query"
Stable within one query, free to change between queries.
stability="volatile"
Called once per row, every time. For anything random, stateful or side-effecting.
con.create_macro(name, parameters, body, replace, temporary)
The alternative for anything that is an expression.

Calling

fn(name, *args)
Any function by name, in an expression. A registered function is one.
sql(text).rows(con) / con.run(text)
SQL that names the function, on a connection to the database it was registered on.

Errors

CatalogError
A type text names a type that does not exist. At registration.
InvalidInputError
At registration: ANY, or an option value that is not one of the choices. At run time: an exception inside the function, a returned value that cannot be read, or one that cannot be cast to returns.
InterfaceError
The connection is closed.
ProgrammingError
The engine found no function taking the arguments given in the query.

Changes from the old client

The old client's create_function had this signature, and duckdb.compat keeps it:

con.create_function(name, function, parameters=None, return_type=None, *,
                    type="native", null_handling="default", exception_handling="default", side_effects=False)
duckdb.create_function(...)     # the same, on the implicit default connection
con.remove_function(name)       # and duckdb.remove_function(name)
OldNative
return_type=, optionalreturns, positional and required
parameters=None: types inferred from the function's annotationsrequired, as SQL type text; nothing is inferred
a function with no annotations and no types fell back to ANY parametersANY is refused; declare the types
type="native" or "arrow"no type; every function is called per row with Python values
null_handling took a string or one of the client's enum valuesthe strings "default" and "special"
under "default", returning None was refused: "The UDF is not expected to return NULL values"returning None makes the result NULL under either setting
exception_handling="return_null": an exception inside the function became NULLgone; an exception fails the query. Catch it in the function and return None
side_effects=True / Falsestability="volatile" / "consistent", plus "consistent_within_query"
returned the connection, for chainingreturns None
registering a name twice was refused, "already created"; remove_function firstregistering again replaces; there is no remove_function, the engine keeps a function until the database closes
duckdb.create_function on an implicit default connectionno module-level function; a connection is always explicit
InvalidInputExceptionInvalidInputError; the old name is an alias in duckdb.compat

The inference the old client did, and duckdb.compat still does, read bool, int, float, str, bytes, bytearray, datetime, date, time, timedelta and UUID as BOOLEAN, BIGINT, DOUBLE, VARCHAR, BLOB, BLOB, TIMESTAMP, DATE, TIME, INTERVAL and UUID; list[T] as T[], dict[K, V] as MAP(K, V), and T | None as T. Write those texts yourself. The rule is simple enough that a helper in your own code can do it, and the registration then says what the engine will see.

old
def shout(text: str, times: int) -> str:
    return text.upper() * times

con.create_function("shout", shout)
con.create_function("brittle", brittle,
    exception_handling="return_null")
con.create_function("tick", tick, [], "BIGINT",
    side_effects=True)
native
def shout(text, times):
    return text.upper() * times

con.create_function("shout", shout, ["VARCHAR", "BIGINT"], "VARCHAR")
con.create_function("brittle", safe(brittle), ["BIGINT"], "BIGINT")
    # where safe() catches and returns None
con.create_function("tick", tick, [], "BIGINT",
    stability="volatile")

One more difference is recorded in the behaviour notes: a KeyboardInterrupt raised inside the function is now the query's InvalidInputError, like any other exception in it, since the engine owns the call and sees only its failure.

Two things the old client had are not here in any form. Arrow functions, type="arrow": duckdb.compat refuses them with NotSupportedError until they arrive. And ANY-typed parameters, which a registered Python function cannot yet declare. Code that needs the old create_function as it was, the inference, return_null, the chaining, runs unchanged on duckdb.compat.

A registered function is one of the engine's functions: it lives as long as the database does, and its errors come through the query that called it.
