User-defined functions

A user-defined function is a Python callable registered as a scalar SQL function on the database. The engine calls it once per row, from its own threads, with the arguments as Python values, and casts what it returns to the type you declared.

Start here

from duckdb import frame
from duckdb.frame import sql

con = frame.connect()
con.create_function("plus_one", lambda x: x + 1, ["BIGINT"], "BIGINT")

sql("SELECT plus_one(i) FROM range(5) t(i)").rows(con)   # [(1,), (2,), (3,), (4,), (5,)]

create_function registers a Python callable as a scalar SQL function on the database. From then on plus_one is a function like any the engine has: it can be called from SQL, from a plan, inside a view, inside a macro.

Registering

con.create_function(name, function, parameters=None, returns=None, *, null_handling="default", stability="consistent")
name
The SQL name, a bare string: the engine registers a Python function by its bare name, so it cannot be schema-qualified. Registering the name again with the same parameters, the same types in the same kinds, replaces the function; with other parameters it adds a second version beside the first, and the engine picks between them as for any function with several versions: the one the arguments fit with the cheapest casts, and a call two versions fit equally well is refused as ambiguous.
function
Any callable: a lambda, a def, a bound method, a functools.partial. Its parameters keep their names, kinds and defaults in SQL; see Parameters. A closure keeps its state.
parameters
Optional. The argument types, as SQL type text, overriding the annotations: a list for the parameters in order, ["VARCHAR", "BIGINT"], or a dict for some of them by name, {"when": "TIMESTAMPTZ"}. Not Python types. A parameter with neither a type here nor an annotation is ANY, which takes an argument of any type, uncast; see Types from annotations and ANY.
returns
Optional. The result type, as SQL type text; without it the return annotation gives it, and one of the two is required.
null_handling
"default" or "special". See NULL.
stability
"consistent", "consistent_within_query" or "volatile". See Stability.
def weave(a, b, c):
    return f"{a}-{b}-{c}"

con.create_function("weave", weave, ["VARCHAR", "BIGINT", "BOOLEAN"], "VARCHAR")
sql("SELECT weave('x', 7, true)").rows(con)   # [('x-7-True',)]

def shout(text: str, times: int) -> str:
    return text.upper() * times

con.create_function("shout", shout)   # VARCHAR, BIGINT -> VARCHAR, from the annotations

prefix = "state"
con.create_function("tag", lambda x: f"{prefix}:{x}", ["BIGINT"], "VARCHAR")
sql("SELECT tag(1)").rows(con)   # [('state:1',)]

Everything is checked when you register, so a mistake is reported here and not at the first call: a type that does not exist raises CatalogError naming it, and an ANY return type, from returns or from -> typing.Any, is refused with InvalidInputError: an ANY return type is not supported yet, since the result type must be known before the function is first called. InvalidInputError also refuses a list with more types than parameters, a shorter list past which a parameter has no default, a dict naming no parameter, an annotation no type is read from, a default its parameter cannot hold, and an option that is not one of the choices above. A function that is not callable, or a parameters that is neither a list nor a dict, raises TypeError. A closed connection raises InterfaceError. Inside a transaction you opened, a registration the engine refuses, for a type text it does not know or a default its parameter cannot hold, aborts the transaction, as a failed statement does: the next statement fails until you ROLLBACK.

The function belongs to the database, not to the connection. Every connection to that database sees it, con.duplicate() included, and the engine keeps it until the database closes. There is no way to remove one; register the same name again to replace it. A fresh duckdb.frame.connect() is a different database, and does not have it.

Parameters

Each parameter keeps its kind, its name and its default, so a call from SQL reaches the function as the same call from Python would. DuckDB's parameter kinds are Python's:

Python parameterPassed from SQL
before /, positional-onlyby position only
plain, positional or keywordby position, or by name: f(x := 1) or f(x => 1)
*argsthe positional arguments left over, as a tuple
after * or *args, keyword-onlyby name only
**kwargsthe named arguments no other parameter takes, as a dict
 
def label(value, /, prefix="id", *parts, sep="-", **extra):
    tags = "".join(f"[{k}={v}]" for k, v in extra.items())
    return sep.join([prefix, str(value), *map(str, parts)]) + tags

con.create_function("label", label, returns="VARCHAR")
sql("SELECT label(7)").rows(con)                                      # [('id-7',)]
sql("SELECT label(7, 'x', 1, 2, sep := '/', loud := true)").rows(con)   # [('x/7/1/2[loud=True]',)]

A call that does not fit the signature, one missing a parameter without a default, naming one that does not exist, passing too many positional arguments, or a positional one after a named one, is refused when the query is planned with ProgrammingError. Where no version of the function fits, the message shows the signature as the engine sees it, in Python's notation; a positional argument after a named one, or a name given twice, gets a message of its own.

Names are matched ignoring case, as everywhere in DuckDB: f(Value := 1) reaches a parameter value, and two parameters whose names differ only in case cannot be registered. A name **kwargs receives keeps the spelling the caller wrote. A positional-only parameter's name is not visible to callers, so a named argument of the same name goes to **kwargs, as in Python.

The type of *args is the type of each extra positional argument, and that of **kwargs the type of each extra named one, as their annotations mean in Python: *rest: int casts every extra argument to BIGINT.

Defaults

A parameter with a default may be left out, and the function then receives its default. The default is converted when you register: to a declared type by the same rules as a returned value, so x: float = 1 arrives as 1.0; for an ANY parameter as a query parameter would be, keeping its own type. A default its parameter cannot hold, or one that is no SQL value at all, such as a sentinel = object(), is refused at registration naming the parameter. The function receives a fresh copy of the default on every call, so a list or dict default, nested ones included, is never shared between calls. The conversion happens once, with the settings of the connection registering the function, as Python evaluates a default once when the def runs: a text default for a TIMESTAMPTZ parameter is read in that connection's time zone, and every connection then receives that instant.

A default of None is a NULL argument. Under null_handling="default" a call that leaves the parameter out is NULL without calling the function, as is any NULL argument; register with null_handling="special" for the function to receive None. See NULL.

Giving some types

A list of types goes through the parameters in order, *args and **kwargs included. A dict gives the types of some parameters by name, and the others are read from their annotations.

A list may stop before the last parameter. SQL then sees only the parameters it covers, and Python fills in the rest from their defaults, as for any call that leaves them out; each of them needs a default, or must be *args or **kwargs, which receive nothing. This is how a default that only keeps a value for the function stays out of SQL:

for offset in range(3):
    con.create_function(f"plus_{offset}", lambda x, offset=offset: x + offset, ["BIGINT"], "BIGINT")
sql("SELECT plus_2(1)").rows(con)   # [(3,)]; plus_2(1, 5) is refused, SQL has no offset

Such a default is the function's own object, held on the function since it was defined: every call, on every engine thread, gets that same object, as it gets the objects a closure or a global names. A default SQL sees is different: it is converted to a SQL value at registration and arrives as a fresh Python value on each call. See Threads for what sharing an object across threads asks of it.

A type in the list may carry the kind's mark, "*BIGINT" for *args and "**BIGINT" for **kwargs; one that does not match the parameter's kind is refused.

Callables without a signature

Some built-in functions, such as max and dict, have no signature Python can read. For them parameters must be a list, its plain types positional-only parameters, then at most one "*T" giving the type of extra positional arguments, then at most one "**T" giving the type of extra named ones; returns is then required.

con.create_function("biggest", max, ["*BIGINT"], "BIGINT")
con.create_function("pack", dict, ["**BIGINT"], "MAP(VARCHAR, BIGINT)")
sql("SELECT biggest(1, 5, 3), pack(a := 1, b := 2)").rows(con)   # [(5, {'a': 1, 'b': 2})]

Types from annotations

A parameter parameters gives no type for takes it from its annotation, and one without an annotation is ANY. The return type is read the same way when returns is left out. An annotation names the type a value of that class gets as a query parameter:

AnnotationSQL type
bool, int, float, str, bytesBOOLEAN, BIGINT, DOUBLE, VARCHAR, BLOB
datetime, date, time, timedelta, UUIDTIMESTAMP, DATE, TIME, INTERVAL, UUID
list[T], tuple[T, ...]T[]
dict[K, V]MAP(K, V)
T | None, Optional[T]T; every SQL value can be NULL
typing.Any, or noneANY

The classes are matched exactly: a subclass, an IntEnum say, is a different annotation, since the function would be handed the base class's values and not its own. A datetime is TIMESTAMP, without a time zone, so a TIMESTAMPTZ argument does not fit it; give "TIMESTAMPTZ" in parameters for that. An annotation in quotes, or under from __future__ import annotations, is evaluated as Python evaluates it.

Anything else is refused at registration with InvalidInputError naming the parameter and the reason, unless parameters gives that parameter's type: a Decimal, whose width and scale its class does not say, a bare list, tuple or dict, a union of two types, ANY inside another type, and any other class.

Python evaluates a function's annotations together, so when one cannot be evaluated, a name that is only imported for type checking say, none of them is read: every parameter with an annotation, and the return, then needs its type in parameters and returns, and the refusal names the annotation and Python's error. On Python 3.14 an annotation whose code raises an error other than a missing name leaves Python no signature at all, and the registration is refused whatever parameters gives.

def price(amount: Decimal, when: datetime) -> str:
    ...

con.create_function("price", price, {"amount": "DECIMAL(18, 2)", "when": "TIMESTAMPTZ"})

Calling it

From SQL, on any plan or statement that runs on the connection:

sql("SELECT plus_one(i) FROM range(3) t(i)").rows(con)
con.run("CREATE TABLE next_ids AS SELECT plus_one(id) AS id FROM orders")

From a plan, through fn, which calls any function by name; a registered function is one:

from duckdb.frame import col, fn, table

table("orders").with_columns(next_id=fn("plus_one", col("id"))).rows(con)
table("orders").filter(fn("plus_one", col("id")) > 1).rows(con)
table("orders").select(fn("label", col("id"), sep="/")).rows(con)   # label("id", "sep" := '/')

sql("SELECT plus_one(3) AS v").types(con)   # ['BIGINT']: the engine knows it like any function

The call renders as plus_one("id") in the SQL, and nothing about it differs from a call to an engine function. DuckDB matches the arguments to the declared parameters as it does for every function: a TINYINT or an INTEGER passed to a BIGINT parameter is cast on the way in; a DECIMAL passed to it is refused when the query is planned, with the usual ProgrammingError that no function matches the given name and argument types.

ANY

A parameter declared ANY takes whatever the caller passes, without the cast a declared type brings: f(1) hands the function an int, f('x') a str, f([1, 2]) a list, and f(NULL) follows the NULL handling. Each place a query calls the function converts by the type passed there, so one function can serve several types in one query, and the value arrives as the table below gives it for that type, as a query returning it would. A parameter declared beside it is still cast.

con.create_function("kind", lambda x: type(x).__name__, ["ANY"], "VARCHAR")
sql("SELECT kind(1), kind('x'), kind([1]), kind(DATE '2026-01-02')").rows(con)   # [('int', 'str', 'list', 'date')]

out

The value the function returns is read by its Python type first, then cast to returns by the engine's own cast, as CAST would, except for dates and times and for structs. A date or timestamp that returns cannot hold exactly is refused rather than rounded, and a date or time without a time zone returned for a type with one, or the reverse, is refused, since the cast would assume a time zone. So is a timestamp with a time zone returned for a time of day, which it has only in a time zone chosen for it; a timestamp without one returned for a TIME drops its date. These hold at any depth. A list meets an element type holding a date, a time or a struct one element at a time. A dict meets a STRUCT as the engine's cast pairs them: by field name, ignoring case, or by position when the first name is empty; a field no declared name takes is dropped unread. A value returned for a UNION is read whole, as its own type, and the engine's cast puts it in a member as an implicit CAST does: the one it converts to most cheaply, and refused when there is none or two tie. So a dict goes in a struct member only with the same fields, none dropped or added, and an int, read as a BIGINT, does not go in an INTEGER member. A date or time inside is then held to the rules above in the member the cast chose, and the value refused if it breaks them; another member is never tried. So a timestamp without a time zone is refused for UNION(z TIMESTAMPTZ, s VARCHAR), where the cast would assume one. A string is a string, not a date or time: text returned for TIMESTAMPTZ is read in the session's time zone, exactly as SQL's CAST reads the same text.

con.create_function("half", lambda x: x / 2, ["BIGINT"], "INTEGER")
sql("SELECT half(9)").rows(con)        # [(4,)]: the DOUBLE 4.5 is cast to INTEGER

con.create_function("as_date", lambda x: f"2020-01-0{x}", ["BIGINT"], "DATE")
sql("SELECT as_date(5)").rows(con)     # [(datetime.date(2020, 1, 5),)]: the text is cast to DATE

con.create_function("wide", lambda x: 2**70, ["BIGINT"], "INTEGER")
sql("SELECT wide(1)").rows(con)        # InvalidInputError: the UDF 'wide' returned a value that cannot be converted to its declared type INTEGER: Failed to cast value ...

A cast that fails fails the query, naming the function and its declared type before the engine's message for that cast. Every result is cast to the declared type, so a function that means to return an INTEGER should declare INTEGER and let the cast check it.

nested types

con.create_function("total", lambda xs: sum(xs), ["BIGINT[]"], "BIGINT")
con.create_function("field", lambda s: s["a"], ["STRUCT(a INTEGER)"], "INTEGER")
sql("SELECT total([1, 2, 3]), field({'a': 7})").rows(con)   # [(6, 7)]

con.create_function("pair", lambda x: [x, x + 1], ["BIGINT"], "BIGINT[]")
con.create_function("wrap", lambda x: {"v": x}, ["BIGINT"], "STRUCT(v BIGINT)")
sql("SELECT pair(3), wrap(9)").rows(con)   # [([3, 4], {'v': 9})]

A list arrives as a list and goes back as one; a struct arrives as a dict and goes back as one. An empty list returned has no element type of its own and is cast to the declared one, so [] for a BIGINT[] is an empty BIGINT[].

NULL

With null_handling="default", a NULL in any argument makes the result NULL for that row, and the function is not called for it:

calls = []

def observe(x):
    calls.append(x)
    return x

con.create_function("observe", observe, ["BIGINT"], "BIGINT")
sql("SELECT observe(x) FROM (VALUES (1), (NULL), (3)) t(x)").rows(con)   # [(1,), (None,), (3,)]
calls                                                                    # [1, 3]

With null_handling="special", None arrives and the function decides:

con.create_function("backfill", lambda x: -1 if x is None else x, ["BIGINT"], "BIGINT", null_handling="special")
sql("SELECT backfill(x) FROM (VALUES (1), (NULL)) t(x)").rows(con)   # [(1,), (-1,)]

Every argument counts, however it was passed: a parameter left out whose default is None, an extra one in *args, and a NULL passed by name into **kwargs all make the result NULL without a call under "default":

con.create_function("tagged", lambda x, tag=None: f"{x}:{tag}", ["BIGINT", "VARCHAR"], "VARCHAR")
sql("SELECT tagged(1), tagged(1, 'a')").rows(con)   # [(None, '1:a')]

con.create_function("tagged", lambda x, tag=None: f"{x}:{tag}", ["BIGINT", "VARCHAR"], "VARCHAR",
                    null_handling="special")
sql("SELECT tagged(1), tagged(1, 'a')").rows(con)   # [('1:None', '1:a')]

Returning None makes the result NULL under either setting:

con.create_function("odd_only", lambda x: x if x % 2 else None, ["BIGINT"], "BIGINT")
sql("SELECT odd_only(i) FROM range(4) t(i)").rows(con)   # [(None,), (1,), (None,), (3,)]

A None anywhere in a return is a NULL of the declared type at that place, and an empty list or dict an empty value of it, so [ts, None] returned for TIMESTAMP[] holds a NULL TIMESTAMP. Inside a value returned for a UNION the declared place is not fixed until the engine's cast picks the member, so a list or dict of only Nones can steer that choice; name the member's type in the value, or return None whole.

Stability

stability is a promise about the function, and the engine plans by it. It is never checked; a wrong promise gives wrong rows, not an error.

"consistent"
The default. Same arguments, same result, always. The engine may compute a call whose arguments are constant once and reuse the value, and may treat repeated calls as one.
"consistent_within_query"
Same arguments, same result within one query, but a later query may see another. What the engine's own now() declares.
"volatile"
The result may differ per row. The engine calls the function once per row, every time.

Anything random, stateful or side-effecting is volatile, and a function of no arguments is the clearest case: declared consistent, it is called once and its value repeated.

consistent: one call, five copies
counter = iter(range(1_000_000))
con.create_function("tick", lambda: next(counter), [], "BIGINT")
sql("SELECT tick() FROM range(5) t(i)").rows(con)
# [(0,), (0,), (0,), (0,), (0,)]
volatile: one call per row
counter = iter(range(1_000_000))
con.create_function("tick", lambda: next(counter), [], "BIGINT", stability="volatile")
sql("SELECT tick() FROM range(5) t(i)").rows(con)
# [(0,), (1,), (2,), (3,), (4,)]

The same holds with arguments: SELECT observe(1) FROM range(5) t(i) calls a consistent observe once and a volatile one five times. Declare a pure function consistent: computing a call once and reusing the value is what makes it cheap in a WHERE or a join condition.

Threads

The engine runs a query on its worker threads, and it calls the function from whichever worker is executing that part of the query. For each batch of rows the worker takes the GIL once, converts the batch's arguments, calls the function once per row, and releases the GIL again. The thread that started the query drops the GIL while it waits on the engine, which is what lets the workers take it.

Two things are tested in tests/test_udf.py:

1
With SET threads = 4 and a million-row aggregate over the function, the function was entered from more than one thread. The calling thread was among them; it was not the only one.
2
Three Python threads, each on its own con.duplicate(), ran a query over the same function at the same time, and each got the right answer.
con.run("SET threads = 4")
seen = set()

def bump(x):
    seen.add(threading.get_ident())
    return x + 1

con.create_function("bump", bump, ["BIGINT"], "BIGINT")
con.run("CREATE TABLE big AS SELECT i FROM range(1000000) t(i)")
sql("SELECT sum(bump(i)) FROM big").rows(con)   # [(500000500000,)]
len(seen)                                          # 4 on this machine; the test asserts at least 2

What this means for the function: it may be entered from any thread, and from several over the course of one query. The GIL serialises bytecode, not calls, so two workers can be inside the function at once, interleaved. State it shares across calls, a list it appends to, a counter, a client, needs to be safe for that, or the function needs to take a lock.

The objects a function reaches through its globals, its closure and its defaults are the same objects on every thread. What belongs to a thread is not: a threading.local or a contextvars.ContextVar the calling thread set reads as unset on an engine worker, while the calling thread, which may run part of the query too, still sees its own value. Pass such a value in as an argument, or capture the object itself.

Free-threaded Python is untested here. The free-threaded wheel builds and imports with the GIL off, and that is all that has been verified. Nothing yet exercises a function being called from several engine workers at once without a GIL to serialise them.

Errors

An exception raised inside the function fails the query that called it. The error is the query's InvalidInputError; its message names the function, then the exception's class and text, then the traceback:

def boom(x):
    raise ValueError(f"no thanks: {x}")

con.create_function("boom", boom, ["BIGINT"], "BIGINT")
sql("SELECT boom(7)").rows(con)
# InvalidInputError: Invalid Input Error: Python exception occurred while executing the UDF 'boom': ValueError: no thanks: 7
# Traceback (most recent call last):
#   ...
# ValueError: no thanks: 7

sql("SELECT 42").rows(con)   # [(42,)]: the connection is fine

The connection survives, and so does the function; the next query runs as usual. A KeyboardInterrupt raised inside the function is reported the same way, as the query's InvalidInputError: the engine owns the call and sees only that it failed.

The other failures at run time are a returned value that cannot be read and one that cannot be cast to returns (InvalidInputError, with the engine's cast message). Both fail the query the same way, and the message carries one Invalid Input Error: prefix. Failures at registration are listed under Registering.

con.create_function("odd", lambda x: object(), ["BIGINT"], "BIGINT")
sql("SELECT odd(1)").rows(con)
# InvalidInputError: Invalid Input Error: the UDF 'odd' returned a value of type object, which cannot be converted to a DuckDB value

Performance

Every row costs a trip through Python: the arguments are turned into Python objects, the function is called, the result is turned back into a value and cast. Anything expressible as an expression runs orders of magnitude faster as a macro, because a macro is inlined into the query and never leaves the engine.

from duckdb.frame import col

con.run("CREATE TABLE big AS SELECT i FROM range(5000000) t(i)")
con.create_function("plus_one", lambda x: x + 1, ["BIGINT"], "BIGINT")
con.create_macro("bump", ["x"], col("x") + 1)

sql("SELECT sum(plus_one(i)) FROM big").rows(con)   # 0.45 s on one laptop
sql("SELECT sum(bump(i)) FROM big").rows(con)       # 0.002 s, the same as sum(i + 1)

Use a function for what SQL cannot say: a call into a library, a lookup into Python state, a format the engine has no parser for. For anything that is an expression, however long, a macro is usually the better answer; create_macro and how far a macro goes are on Macros & Extensions. Keep a function's own work small, declare it consistent when it is pure so the engine can compute a call once and reuse the value, and let the engine do the filtering and grouping around it.

Reference

Registration

con.create_function(name, function, parameters=None, returns=None, *, null_handling, stability)
Register function as scalar SQL function name on the database, its parameters keeping their names, kinds and defaults. Returns nothing. A name already registered with the same parameters is replaced; with other parameters a second version is added.
parameters
SQL type texts overriding the annotations: a list for the parameters in order, the ones past its end left to Python's defaults, or a dict by parameter name. ANY takes an argument of any type, uncast. For a callable without a signature, a list of positional types, then "*T", then "**T".
returns
One SQL type text, else the return annotation. The returned value is cast to it.
null_handling="default"
A NULL argument gives NULL without a call, a None default included.
null_handling="special"
None is passed in; the function decides.
stability="consistent"
Pure. The engine may compute a call once and reuse the value, and may treat repeated calls as one.
stability="consistent_within_query"
Stable within one query, free to change between queries.
stability="volatile"
Called once per row, every time. For anything random, stateful or side-effecting.
con.create_macro(name, parameters, body, replace, temporary)
The alternative for anything that is an expression.

Calling

fn(name, /, *args, **named)
Any function by name, in an expression; keyword arguments pass by name. A registered function is one.
sql(text).rows(con) / con.run(text)
SQL that names the function, on a connection to the database it was registered on.

Errors

CatalogError
A type text names a type that does not exist. At registration.
TypeError
A function that is not callable, or a parameters that is neither a list nor a dict. At registration.
InvalidInputError
At registration: an ANY return type, a list of types that does not fit the parameters, a dict naming no parameter, an annotation no type is read from, a default its parameter cannot hold, two parameter names equal ignoring case, or an option value that is not one of the choices. At run time: an exception inside the function, a returned value that cannot be read, or one that cannot be cast to returns.
InterfaceError
The connection is closed.
ProgrammingError
The engine found no function taking the arguments given in the query.

One more difference is recorded in the behaviour notes: a KeyboardInterrupt raised inside the function is now the query's InvalidInputError, like any other exception in it, since the engine owns the call and sees only its failure.

One thing the old client had is not here in any form: Arrow functions, type="arrow".

A registered function is one of the engine's functions: it lives as long as the database does, and its errors come through the query that called it.
