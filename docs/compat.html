Keeping old code running

duckdb.compat is the old client's API, built on top of the native connection: execute and fetchall on the connection, cursor(), lazy relations, the old expression constructors and the old exception names. It exists so that code written against the old client keeps running while it migrates. New code has no reason to be here.

What it is, and is not

The old client's duckdb.connect() returned a connection that executed and fetched directly: con.execute(...).fetchall(), with description and rowcount on the connection, cursor() handing back a duplicate whose lifetime was tied to its parent, and sql(), table() and query() returning lazy relations. This module reproduces that contract.

The old habits are reproduced deliberately, the questionable ones included:

  • cursor() is an independent connection with its own transaction, and closing a connection closes its cursors.
  • rowcount is always -1.
  • Relations compose SQL text.
  • connect() hands out connections into one shared database instance per path, with the old refusal when the configuration differs, and :memory:name is shared.
  • A default connection at module level backs execute(), sql(), query(), table() and the rest of the names there.

The native package does none of this. A connection from duckdb.connect() has no execute, no fetch family and no cursor(): plans run on it (Frames & Plans), statements go through run(), and the PEP 249 cursor lives in duckdb.dbapi (DB-API 2.0). Neither inherits anything from this module.

What this module still lacks is measured. A copy of the old client's own test suite runs against it (What is not here), and every remaining difference is an entry in the behaviour log, compat/BEHAVIOR.md.

Reaching for it

The module carries the names the old package had at module level, so the shortest first step is an import alias:

import duckdb.compat as duckdb

con = duckdb.connect("shop.db")
con.execute("SELECT count(*) FROM orders").fetchall()   # [(3,)]
duckdb.sql("SELECT 42").fetchone()                        # (42,), on the default connection

Under that alias duckdb.execute, duckdb.sql, duckdb.ConnectionException and the rest resolve to this module. The native package is untouched: import duckdb elsewhere in the same process still gives the native API. from duckdb import compat is the same module under its own name, for code that uses both at once.

one connection, both APIs

A compat connection is a native connection. CompatConnection subclasses duckdb.Connection, so everything on the native pages works on it: plans run on it, run() counts rows, transaction() is a block. Old calls and new calls can share one connection, which is what makes a gradual migration possible.

import duckdb.compat as compat
from duckdb import table, col

con = compat.connect("shop.db")
con.execute("SELECT count(*) FROM orders").fetchone()        # the old call
table("orders").filter(col("total") > 1000).rows(con)   # the native call, same connection

The connection

connect(database=":memory:", read_only=False, config=None) is the old signature: a positional path, a read_only flag and a config dict of settings. The native connect takes its settings as keyword arguments instead.

execute and fetch

con = duckdb.connect()
con.execute("CREATE TABLE orders (id INTEGER, customer VARCHAR, total INTEGER)")
con.execute("INSERT INTO orders VALUES (1, 'acme', 1400), (2, 'bolt', 320), (3, 'acme', 2600)")

con.execute("SELECT id, total FROM orders WHERE total > ?", [1000])
con.description     # [('id', 'INTEGER', None, None, None, None, None), ('total', 'INTEGER', None, None, None, None, None)]
con.fetchone()      # (1, 1400)
con.fetchall()      # [(3, 2600)]
con.fetchone()      # None
con.rowcount        # -1, always

execute runs one statement and returns the connection, so con.execute(...).fetchall() chains. A statement that produces rows is held on the connection and the fetch family drains it: fetchone(), fetchmany(size=1), fetchall(), fetchnumpy(), fetchdf() (also under the names df() and fetch_df()), fetch_df_chunk(). The next execute releases whatever is still held. A statement that produces no rows is applied at execute, as the old client's INSERT was, and description is then None. executemany(sql, sets) runs the statement once per parameter set and refuses an empty list.

rowcount is -1 whatever ran: the old client never reported a count. The real count is what con.run(sql) returns.

Parameters are a list for ? and $1, or a dict for names. A dict key of any type is taken as its text, so {1: value} fills $1; the native connection accepts only string keys, and the leniency is this module's.

Fetching with nothing held raises InvalidInputException, No open result set. The same error is raised after close(), since the held result is checked before the connection is.

cursors

con = duckdb.connect()
cur = con.cursor()
con.execute("CREATE TABLE t (v INTEGER)")
con.execute("BEGIN")
con.execute("INSERT INTO t VALUES (1)")
cur.execute("SELECT count(*) FROM t").fetchone()   # (0,): its own transaction
con.execute("COMMIT")
cur.execute("SELECT count(*) FROM t").fetchone()   # (1,)
con.close()
cur.execute("SELECT 1")                             # ConnectionException: closed with its parent

cursor() returns another CompatConnection: an independent duplicate with its own transaction and its own temporary schema. That is what the old client did, and it is the opposite of PEP 249, where a cursor shares its connection's transaction; the cursor that does that is in duckdb.dbapi. Closing a connection closes every cursor made from it.

begin(), commit() and rollback() exist as methods and run the statement of the same name. close() closes the cursors, releases the held result and closes the connection; the connection is also a context manager.

A held result and sql(). sql() on a connection holding a result nothing has fetched from discards that result silently, as the old client did. Once something has been fetched from it, sql() refuses with the engine's error for a live result instead; the old client had materialized the whole result at execute and kept the remainder. Fetch the result to the end, or call execute again, before building a relation on the same connection.

One database per path

a = duckdb.connect("shop.db")
b = duckdb.connect("shop.db")                    # the same database instance
a.execute("CREATE TABLE t AS SELECT 1 AS v")
b.execute("SELECT count(*) FROM t").fetchone()   # (1,)

duckdb.connect("shop.db", read_only=True)
# ConnectionException: Can't open a connection to same database file with a different configuration than existing connections

Two connect() calls to one path hand out connections into one database instance, so each sees the other's writes. The instance lives as long as any connection or cursor into it; when the last one closes, the file is released, and a later connect() opens it afresh. Asking for the same path with a different configuration, whether read_only or an entry in config, is refused in the old words, and the refusal is a ConnectionException. A pathlib.Path is accepted as well, and resolves to the same instance as the equal string.

:memory:name is shared the same way. A plain :memory: is never shared: every call is a fresh database.

The native connect() does none of this. Opening one file twice natively is refused by the engine (Unique file handle conflict); a second connection into a database that is already open is con.duplicate().

The connection announces itself to the engine as python/<major.minor> in the duckdb_api setting, as the old client did.

The default connection

import duckdb.compat as duckdb

duckdb.execute("CREATE TABLE numbers AS SELECT * FROM range(5) t(i)")
duckdb.execute("SELECT count(*) FROM numbers").fetchone()   # (5,)
duckdb.description()                                          # [('count_star()', 'BIGINT', None, None, None, None, None)]
duckdb.sql("SELECT i FROM numbers WHERE i > 2").fetchall()   # [(3,), (4,)]
duckdb.table("numbers").fetchall()                            # [(0,), (1,), (2,), (3,), (4,)]
duckdb.table_function("range", [3]).fetchall()                # [(0,), (1,), (2,)]

duckdb.default_connection()   # the CompatConnection behind all of the above
duckdb.close()                # closes it; the next call at module level makes a fresh, empty one

execute, sql, query, from_query, table, table_function, create_function, remove_function and description at module level all run on one connection that the module makes on first use, in memory. description is a function here, duckdb.description(), where on a connection it is a property.

default_connection() returns that connection. set_default_connection(con) points the names at module level at a connection of your own, and refuses anything that is not a CompatConnection with a TypeError. connect(":default:") returns the default connection as well. close() closes it, and with it every table it held; the next call at module level opens a new one.

Relations

con = duckdb.connect()
con.execute("CREATE TABLE orders AS SELECT * FROM (VALUES (1, 'acme', 1400), (2, 'bolt', 320), (3, 'acme', 2600)) t(id, customer, total)")

orders = con.table("orders")
big = orders.filter("total > 1000").project("customer, total")
big.sql_query()   # SELECT customer, total FROM (SELECT * FROM (SELECT * FROM "orders") WHERE total > 1000)
big.fetchall()    # [('acme', 1400), ('acme', 2600)]
big.aggregate("sum(total)").fetchone()   # (4000,)

con.sql(query) returns a CompatRelation: lazy, bound to that connection, and composed as SQL text. Every verb takes its argument as a SQL fragment and wraps the previous text in a subquery; sql_query() shows the result. The text is bound when the relation is made, so a bad fragment errors at the verb, not at the first fetch. con.query is the old alias. con.table(name) and con.view(name) read a table or view by name, and con.table_function(name, params) takes the function's arguments as a list.

sql() given anything other than a query runs it on the spot and returns None: DDL, INSERT, BEGIN. A statement that is not a query but still produces rows, such as INSERT ... RETURNING, runs exactly once, and its rows are carried in a materialized relation that gives the same rows on every fetch and takes verbs like any other.

fetching

r = con.sql("SELECT * FROM range(3)")
r.fetchall()      # [(0,), (1,), (2,)]: runs the query
r.fetchall()      # runs it again
r.fetchone()      # (0,): runs once more and holds the result
r.fetchmany(2)    # [(1,), (2,)], from the held result
r.fetchone()      # None
r.execute()       # runs again and holds the new result
r.close()         # releases it; every fetch afterwards raises "result closed"

That is the old model: a bare fetchall() runs fresh every call, fetchone() and fetchmany() run once and drain what they hold, execute() resets it. fetchdf() (also df() and to_df()), fetchnumpy() and fetch_df_chunk() follow the same rule.

description, columns and types (also dtypes) come from binding the text and run nothing; types are type text, where the old client returned type objects. shape and len() run a count. type is TABLE_RELATION, VIEW_RELATION, QUERY_RELATION or MATERIALIZED_RELATION. Printing a relation shows its first rows as a table, and show() prints them. "customer" in orders asks for a column; orders["customer"] projects one.

joining and combining

customers = con.table("customers")
orders.join(customers, "customer")                      # USING (customer): the condition is only names
orders.set_alias("o").join(customers.set_alias("c"), "o.customer = c.customer", how="left")   # ON (...)
orders.union(orders.set_alias("again"))                  # UNION ALL: duplicates stay

A condition that is only column names becomes USING; anything else is ON. Each side joins under its alias, which is a table's own name or one given by set_alias(); two sides with the same alias are refused. how is inner, left, right, outer, semi or anti. cross() is the cross product. union, except_ and intersect are the ALL forms, as they were.

the shorthands

orders.sum("total", groups="customer", projected_columns="customer").order("customer").fetchall()   # [('acme', 4000), ('bolt', 320)]
orders.count("*").fetchone()                                       # (3,)
orders.row_number("over (order by total desc)", "customer")    # a window shorthand
orders.describe()                                                  # count, mean, stddev, min, max, median, one row each

Every old aggregate shorthand is here, sum, min, max, mean, count, median, quantile, std, var, list, string_agg, histogram and the rest, each taking its columns as text with optional groups, window_spec and projected_columns; apply(function_name, columns) calls any aggregate by name. The window shorthands, row_number, rank, dense_rank, lag, lead, first_value and the rest, take the window as text. The full list is in the reference.

writing out

big.create("big_orders")              # a new table; to_table is the alias
big.insert_into("big_orders")         # append, by position
big.create_view("big_view")           # CREATE OR REPLACE VIEW; replace=False for a plain CREATE
con.table("orders").insert([4, "cog", 10])                     # one row; a table relation only
con.table("orders").update({"total": 0}, condition="id = 2")   # a table relation only
big.write_csv("big.csv", sep="|", header=True)
big.write_parquet("big.parquet", compression="zstd")
big.query("b", "SELECT count(*) FROM b").fetchone()   # (2,): the relation as a temporary view named b
big.explain()                                          # the plan as text; explain(type="analyze") runs it

write_csv takes the old option names, spelled the way pandas spells them, sep, na_rep, header, quotechar, escapechar, date_format, timestamp_format, quoting, encoding, compression, overwrite, per_thread_output, use_tmp_file, partition_by and write_partition_columns, and writes with COPY; to_csv is the alias. write_parquet and to_parquet do the same with the Parquet options. insert() and update() work on a relation from con.table() only, as they did.

Expressions

from duckdb.compat import ColumnExpression, FunctionExpression, CaseExpression, StarExpression, SQLExpression, CoalesceOperator

orders.filter(ColumnExpression("total") > 1000)
orders.filter(ColumnExpression("customer") == "acme")                 # a bare string is a value
orders.project(FunctionExpression("upper", ColumnExpression("customer")))
orders.project(StarExpression(exclude=["id"]))
orders.project(SQLExpression("total * 2"))
orders.project(CoalesceOperator(ColumnExpression("total"), 0))
orders.sort(ColumnExpression("total").desc())

tier = (CaseExpression(ColumnExpression("total") > 2000, "big")
        .when(ColumnExpression("total") > 500, "mid")
        .otherwise("small"))
orders.project("id", tier).order("id").fetchall()   # [(1, 'mid'), (2, 'small'), (3, 'big')]

Each constructor returns a CompatExpression, a thin wrapper over the native expression layer, so what an expression means is what the native layer says it means: a bare operand is a value, never a column name, and ColumnExpression("customer") == "acme" compares with the text acme. repr() of an expression is its SQL fragment.

ColumnExpression takes a dotted name or its parts; ColumnExpression("o", "id") and ColumnExpression("o.id") are the same. ConstantExpression(value) is a literal. FunctionExpression(name, *args) calls any function by name. CaseExpression(condition, value) opens a CASE with its first branch; chain .when(condition, value) and .otherwise(value), and without an otherwise the unmatched rows are NULL. StarExpression(exclude=[...]) takes names or column expressions. SQLExpression(text) is spliced as written. DefaultExpression() is the DEFAULT marker. CoalesceOperator(*args) is the first argument that is not NULL.

Comparison and arithmetic operators build bigger expressions, as do &, |, ~ and unary minus. The methods are cast(type), asc(), desc(), nulls_first(), nulls_last(), between(lo, hi), isin(*values) and isnotin(*values) with the values as separate arguments, isnull(), isnotnull(), collate(name), get_name() and show().

An expression goes wherever a relation verb takes a fragment: filter, project, aggregate (as a list), sort, a join condition, the values and condition of update. A native expression from col(), lit(), fn() or when() is accepted in the same places.

Expression is the old class name, an alias of CompatExpression, kept for isinstance checks in migrating code. A native Expr is not an instance of it.

Combine with &, | and ~, in parentheses. Python's and, or and not do not build an expression.

Exceptions

import duckdb.compat as duckdb

try:
    con.execute("SELECT * FROM nope")
except duckdb.CatalogException:
    ...                                   # the object raised is duckdb.exceptions.CatalogError

Every old exception name is an alias of the class this package raises for the same engine error, or of the nearest ancestor where the old class drew a finer line than the engine's error codes do. An except clause written against the old name keeps catching.

Two consequences. Where several old names alias one class, the clause is wider than it was: except TypeMismatchException catches every ProgrammingError, including the one DuckDB raises when it cannot resolve a query. And ConnectionException, which covered "closed or unusable", is InterfaceError: that is the class raised for a closed connection, and for the refusal in connect() when the configuration differs.

The PEP 249 names, Error, Warning, DatabaseError, DataError, IntegrityError, NotSupportedError, OperationalError and ProgrammingError, are here too, with apilevel, paramstyle, threadsafety and the type objects STRING, BINARY, NUMBER, DATETIME and ROWID, all taken from duckdb.dbapi.

Functions

con = duckdb.connect()
con.create_function("plus_one", lambda x: x + 1, ["BIGINT"], "BIGINT")
con.execute("SELECT plus_one(41)").fetchall()   # [(42,)]

def shout(text: str, times: int) -> str:
    return text.upper() * times

con.create_function("shout", shout)                 # types from the annotations
con.execute("SELECT shout('ha', 2)").fetchall()   # [('HAHA',)]

def brittle(x: int) -> int:
    return 100 // x

con.create_function("brittle", brittle, exception_handling="return_null")
con.execute("SELECT brittle(x) FROM (VALUES (4), (0), (10)) t(x)").fetchall()   # [(25,), (None,), (10,)]

create_function(name, function, parameters=None, return_type=None, *, type="native", null_handling="default", exception_handling="default", side_effects=False) registers a Python callable and returns the connection. Types left out are read from the function's annotations: bool, int, float, str, bytes, datetime, date, time, timedelta and UUID map to BOOLEAN, BIGINT, DOUBLE, VARCHAR, BLOB, TIMESTAMP, DATE, TIME, INTERVAL and UUID; list[T] is T[], dict[K, V] is MAP(K, V), and T | None is T. A parameter or return without an annotation and without an explicit type is refused, with directions.

With null_handling="default" a NULL argument gives NULL without calling the function, and a function that returns None anyway is refused with the old client's message. With "special", None passes in and a returned None is NULL. exception_handling="return_null" turns a Python error into NULL instead of failing the query. side_effects=True marks the function volatile, so the engine calls it once per row every time. Any of these may be given as the old enum value, which is taken by its name. type must be "native"; "arrow" raises NotSupportedError.

remove_function(name) raises NotSupportedError: the engine keeps a registered function until the database closes. Registering the same name again replaces it, where the old client refused. create_function and remove_function at module level act on the default connection.

The native registration is con.create_function(name, function, parameters, returns, null_handling=, stability=), types always given, on UDFs.

What is not here

compat/suite/ holds verbatim copies of 36 of the old client's own test files, taken from duckdb/duckdb-python main at 2ba111556c0a on 1 September 2026: the connection, statement, transaction, result and interrupt files, the DB-API set, and the relational API set with the data file it reads. They run against this package to report how much of the old API is here, and they gate nothing: the repository's own suite under tests/ gates changes; this slice only reports.

The files under suite/ are never edited to pass. A failure there is one of three things: a name this client does not have, a deliberate divergence recorded in compat/BEHAVIOR.md, or a bug. A test that asserts a recorded divergence is marked xfail from compat/conftest.py, with a reason naming its log entry. The slice grows file by file, each copied verbatim from the same source, with the source commit recorded in compat/README.md.

running it

uv run --no-sync python scripts/compat_report.py
uv run --no-sync python scripts/compat_report.py --facade

The report clusters the outcomes under its four labels, passed, missing surface, behavior and skipped, prints the top failure signatures, and always exits 0. Without --facade the old tests run against the native duckdb package, and nearly all of them fail on a missing name, which is expected: the native API is not the old one. With --facade, compat/conftest.py patches duckdb.connect and the old names at module level to duckdb.compat first, previewing what a package that shipped this module as its top level would score; the verbatim files are never touched. A path argument restricts the run to the suite files under it; every other argument is passed to pytest, so -k name narrows a run further. Each file runs in its own subprocess with a timeout, so one file that hangs cannot hide the files after it.

Left out of the slice so far: files importing pyarrow, polars, torch or tensorflow, files needing the old build tree or its data files, and test_query_progress.py.

pending

These parts of the old API are recorded as pending in compat/BEHAVIOR.md and are not here:

  • Several statements in one execute. The old client ran "a; b; c" and returned the last result; here it is refused: Execute expects exactly one statement.
  • The implicit FROM df scan of a local DataFrame or relation, and from_df. A query naming a local variable finds no such table.
  • Arrow UDFs, create_function(type="arrow").
  • UDF parameters typed ANY.

Every other difference from the old client, whether in values, expressions, connections, errors or functions, is an entry in compat/BEHAVIOR.md with the test that pins it.

Migrating off it

A compat connection is a native connection, so a migration can move one call at a time on the same connection object.

1
Change the import to import duckdb.compat as duckdb. What still fails is in the behaviour log or the report.
2
Replace fetches with plans on the same connection: con.execute(text).fetchall() becomes duckdb.sql(text).rows(con), then the SQL becomes verbs.
3
Replace statements: con.execute("INSERT ...") becomes con.run("INSERT ..."), which returns the count rowcount never had. begin(), commit() and rollback() become a with con.transaction(): block.
4
Replace the old exception names with the classes in duckdb.exceptions. They are the same objects, so the two spellings can coexist while it happens.
5
When no old call is left, compat.connect becomes duckdb.connect, and each cursor() becomes con.duplicate(), or a duckdb.dbapi cursor where PEP 249 was the point.
