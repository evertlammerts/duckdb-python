The DB-API

duckdb.dbapi lets you use DuckDB the way most Python database libraries work: you connect, get a cursor, run SQL with execute(), read rows with fetchall(), and save your changes with commit(). This page walks through those steps, then covers the details.

Start here

Python has a standard way for programs to talk to a database, called the DB-API and written down in PEP 249. Many tools expect it, such as ORMs (libraries that map Python classes to tables), notebook SQL cells and database migration tools. duckdb.dbapi gives DuckDB that interface, so tools that accept a DB-API connection can use it.

For code you write yourself, the main module, duckdb.frame, is usually simpler: see Frames & Plans. Use duckdb.dbapi when a tool needs a DB-API driver, or when you prefer this style.

from duckdb import dbapi

con = dbapi.connect()
cur = con.cursor()
cur.execute("CREATE TABLE orders (id INTEGER, customer VARCHAR, total DECIMAL(6,2), placed DATE)")
cur.execute("INSERT INTO orders VALUES (1, 'acme', 1400, '2026-01-12'), (2, 'bolt', 320, '2026-01-20'), (3, 'acme', 2600, '2026-02-03')")
con.commit()

cur.execute("SELECT customer, total FROM orders WHERE total > ?", [1000])
print(cur.fetchall())        # [('acme', Decimal('1400.00')), ('acme', Decimal('2600.00'))]

Line by line:

  • dbapi.connect() opens a new, empty database in memory. It disappears when the connection closes. To keep these tables in a file, write dbapi.connect("shop.db") here instead, before you create them: connecting to a file later does not move tables into it. See Connecting.
  • con.cursor() gives you a cursor: the object you run SQL with and read results from.
  • cur.execute(...) runs one SQL statement. The table's columns are an INTEGER, a VARCHAR (text), a DECIMAL(6,2) (a number of six digits, two of them after the point) and a DATE.
  • con.commit() saves your changes. Until you commit, con.rollback() or closing the connection undoes them.
  • The ? in the query is a parameter: a placeholder for a value you pass separately, here [1000]. DuckDB never pastes the value into the SQL text, so any value is safe to pass, even text a user typed.
  • fetchall() returns the rows as a list of tuples. A DECIMAL column comes back as Python's Decimal, an exact decimal number (see Reading rows for arithmetic with it).

The sections below follow these steps in order. Their examples run one after the other and build on each other: they use the con, cur and orders table made here. A comment after a line shows what it prints or, for a line without print(), what an interactive prompt or a notebook shows.

Connecting

db = dbapi.connect("archive.db")                      # a database file, created if it does not exist
mem = dbapi.connect()                                 # a new, empty database in memory
fast = dbapi.connect(threads=8, memory_limit="4GB")    # with DuckDB settings
auto = dbapi.connect(autocommit=True)                # every statement is saved as it runs
  • With a path, as a string or a pathlib.Path, you get a database file. It is created if it does not exist yet. What you commit is stored in the file, and is there the next time you connect to it.
  • With no path you get a new database in memory. Each such connection has its own database, which disappears when you close the connection.
  • Other keyword arguments are DuckDB settings, applied when the database opens. A few settings, such as access_mode="READ_ONLY", can only be given here. Most others can also be changed later with cur.execute("SET ..."), and a few only that way: max_streaming_buffer_size given to connect() raises InvalidInputError. A setting DuckDB does not know raises InvalidInputError. A value it cannot use raises an error that depends on the setting, such as InvalidInputError, ParserError or NotSupportedError; except dbapi.DatabaseError catches them all.
  • dbapi has the standard's error classes, such as dbapi.ProgrammingError. The more exact ones, such as InvalidInputError, are in duckdb.exceptions, and each is a kind of one of the standard's: except dbapi.ProgrammingError catches an InvalidInputError. See Errors.
  • autocommit=True is not a DuckDB setting: it makes every statement save itself as it runs, so you never call commit(). The default is False. See Transactions.

open a file once

dbapi.connect("archive.db")     # raises OperationalError: db has archive.db open already

A database file is opened by one connection at a time. A second connect() to the same file raises OperationalError, and so does a frame.connect() to it (for read-only connections, see Details). Open the file once and make as many cursors from that connection as you need. After you close the connection, you can open the file again.

a with block is a transaction

with con:
    con.cursor().execute("INSERT INTO orders VALUES (4, 'cato', 90, '2026-03-05')")
# the insert is saved, and con is still open

When the with block ends, the connection commits. If the block raises an exception, it rolls back (undoes) instead. Either way this covers the whole open transaction, which your first statement started, even a SELECT; entering the block does not start a new one. So changes made before the block are included, and an inner with con: block commits everything so far when it ends. An error you catch inside the block still fails the transaction, and the block's end then discards the earlier writes without raising: catch errors outside the block, or raise them again. The connection stays open after the block, as in Python's sqlite3.

closing

db.close()
db.close()        # does nothing: it is closed already
db.cursor()       # raises InterfaceError

close() rolls back any changes you have not committed, then closes the connection. Calling it again does nothing. After it, the connection and every cursor it made refuse any more work with InterfaceError.

Details

  • Setting values are sent to DuckDB as text, so threads=4 and threads="4" mean the same. DuckDB's settings are listed in its documentation at duckdb.org.
  • The path ":memory:", the default, also means a new database in memory.
  • While your connection can write to a file, another program that opens it gets an IOError saying the file is locked. Connections opened with access_mode="READ_ONLY" are not refused, but do not rely on them to share a file: when two in one program are open and one closes, another program can open the file and write to it while the other still reads the old data.

Cursors

A cursor is the object you run SQL with and read rows from. Get one with con.cursor(), and make as many as you like.

All cursors of a connection share one transaction. So what one cursor writes, another cursor of the same connection sees at once, even before you commit. A commit() saves the work of every cursor.

writer, reader = con.cursor(), con.cursor()
writer.execute("INSERT INTO orders VALUES (5, 'dune', 700, '2026-03-06')")
reader.execute("SELECT count(*) FROM orders")
reader.fetchone()      # (5,): the reader sees the insert
con.commit()           # saves it

One thing to know before you read from two cursors at once: a connection has only one open result at a time. See One result at a time.

closing a cursor

with con.cursor() as cur:
    cur.execute("SELECT 1")
    cur.fetchone()
# cur is closed here

cur.close() closes a cursor, and a with block closes it at the end. Closing it again does nothing. A closed cursor refuses execute and every fetch with InterfaceError. Closing a cursor commits nothing and undoes nothing: the transaction belongs to the connection.

Two attributes are useful now and then. cur.connection is the connection the cursor came from. cur.arraysize is how many rows fetchmany() returns when you do not say; it starts at 1.

Running SQL

cur = con.cursor()
cur.execute("SELECT count(*) FROM orders").fetchone()       # (5,)

cur.execute(sql, parameters) runs one SQL statement. It returns the cursor, so you can call a fetch method on it straight away, as above.

Each call runs exactly one statement. Text with two statements, such as "CREATE TABLE t (v INTEGER); INSERT INTO t VALUES (1)", is refused with InvalidInputError. Run each statement with its own execute.

parameters

cur.execute("SELECT ? + ?", [2, 3]).fetchone()                     # (5,)
cur.execute("SELECT $1 + $2", [2, 3]).fetchone()                   # (5,)
cur.execute("SELECT $a + $b", {"a": 2, "b": 3}).fetchone()         # (5,)

A parameter is a placeholder in the SQL for a value you pass next to it. There are three ways to write one:

  • ?, filled in order from a list or tuple. This is the standard style, and what tools use.
  • $1, $2 and so on, filled by position from a list or tuple.
  • $name, filled by name from a dict.

Other styles you may know from other libraries, :name, %s and %(name)s, are not DuckDB SQL and fail with ParserError or ProgrammingError. Passing too many or too few values raises InvalidInputError, and the message names the parameters concerned. Which Python values you can pass is the next section.

Parameters carry values, never table or column names. SELECT ? FROM orders with ["customer"] gives the text 'customer' on every row, and FROM ? raises ParserError. To choose a column, write its name into the SQL text yourself, in double quotes (see Querying Python data), taken from a fixed list of names you allow.

reading a file

cur.execute("COPY orders TO 'orders.csv'")
cur.execute("SELECT count(*) FROM read_csv(?)", ["orders.csv"]).fetchone()     # (5,)

SQL can read a file where it is, with read_csv, read_parquet or read_json, and you can send the file name as a parameter. COPY ... TO writes a table to a file, here to make one to read. It writes the file at once and replaces any file of that name, and rollback() does not undo that. A relative file name is taken from the program's current directory, os.getcwd(). Each reader's options are in DuckDB's documentation for CSV, Parquet and JSON.

executemany

cur.executemany("INSERT INTO orders VALUES (?, ?, ?, ?)", [
    (6, "eve", 10, "2026-04-01"),
    (7, "fay", 20, "2026-04-02"),
])
cur.rowcount        # 2
con.commit()

executemany runs one statement once for each set of values, in order. Afterwards rowcount is the total number of rows changed. If one set fails, the sets before it have already run. Most errors also fail the open transaction (see Transactions), and rollback() then undoes them all. With autocommit=True, though, each statement is saved on its own, so the sets before the failed one stay saved. executemany keeps no rows, so after a SELECT there is nothing to fetch.

if you also use duckdb.frame

from duckdb.frame import table, col, param

plan = table("orders").filter(col("total") > param("least")).select("customer", "total")
query, values = plan.render_parameterized(parameters={"least": 1000})
cur.execute(query, values).fetchall()      # [('acme', Decimal('1400.00')), ('acme', Decimal('2600.00'))]

This part is for readers who also build queries with duckdb.frame. Such a query (a plan) does not run on a dbapi connection: cur.execute(plan) raises TypeError. render_parameterized() gives you its SQL, with $1, $2 placeholders, and the values to send, and a cursor can run those. Do not use plan.render() for this: it writes each param() as NULL, so the query would run without its values.

Details

  • When an error appears. A query starts in execute, which returns as soon as the first rows are ready. DuckDB produces the rest while you fetch. So an error DuckDB meets early is raised by execute, and one it meets later by the fetch that gets to it. DuckDB works ahead until about 10 MB of rows are waiting (the max_streaming_buffer_size setting), so a small result is usually complete when execute returns.
  • A statement without a result, such as INSERT, UPDATE or CREATE, runs to its end inside execute. Any error is raised there, and the change is made when the call returns.
  • RETURNING makes an INSERT, UPDATE or DELETE give back rows about the rows it changed. It too makes its whole change inside execute, and you fetch the returned rows afterwards. Ending that result with abort() does not undo the change; rollback() does: 
    cur.execute("INSERT INTO orders VALUES (8, 'gus', 30, '2026-04-03') RETURNING id")
cur.fetchone()        # (8,)
cur.abort()
cur.execute("SELECT count(*) FROM orders WHERE id = 8").fetchone()     # (1,): the insert stays
con.rollback()        # undoes it
  • Pass a single value in a list: cur.execute("SELECT ?", ["ab"]). A bare string counts as a sequence of characters, so cur.execute("SELECT ?", "ab") sends two values, 'a' and 'b', and fails.
  • The keys of a dict of parameters must be strings: {1: 9} is refused with InvalidInputError, and {"1": 9} fills $1. Names match without regard to case, so $Name is filled by {"name": ...}.
  • A plan whose SQL depends on its tables' columns, such as a join with suffix=, cannot give its SQL this way: render_parameterized() raises NeedsConnection. Run such a plan on a duckdb.frame connection instead. When you have a frame connection to the same data, pass it, as in render_parameterized(fcon, parameters=...): without one the SQL can differ from what the plan runs, for example a column replaced by with_columns() moves to the end.

Sending Python values

import datetime
from decimal import Decimal

cur.execute("SELECT ?, ?, ?", [Decimal("9.99"), datetime.date(2026, 5, 1), None]).fetchone()
# (Decimal('9.99'), datetime.date(2026, 5, 1), None)

To find rows where a column is NULL, write WHERE customer IS NULL. A comparison with NULL is never true, so WHERE customer = ? with None finds no rows at all. For a value that may be None, write WHERE customer IS NOT DISTINCT FROM ?, which also matches NULL to NULL.

lists and dicts

cur.execute("SELECT typeof(?), typeof(?)", [[1, 2], {"customer": "acme", "vip": True}]).fetchone()
# ('BIGINT[]', 'STRUCT(customer VARCHAR, vip BOOLEAN)')

typeof() shows the DuckDB type of a value, and [] after a type means a list of it. A list or tuple becomes a LIST. A dict with string keys becomes a STRUCT: DuckDB's record type, a set of named fields, which Python sees as a dict. A dict with keys of any other type, such as {1: "one"}, becomes a MAP: its keys must all fit one type, and so must its values, while a STRUCT's fields can each have their own type. The values inside follow the same rules, so lists of dicts and dicts of lists work too.

To keep the rows whose value is in a Python list, send the list as one parameter and write IN ?::VARCHAR[], without brackets around the ?:

query = "SELECT id FROM orders WHERE customer IN ?::VARCHAR[] ORDER BY id"
cur.execute(query, [["bolt", "cato"]]).fetchall()     # [(2,), (4,)]
cur.execute(query, [[]]).fetchall()                   # []

::VARCHAR[] is a cast: it says the parameter is a list of text. Without it, an empty list raises InvalidInputError, since it does not say what type it holds. IN (?) would compare each value with the whole list, and fails with ConversionError.

numpy and pandas values

Dates, times and durations from numpy and pandas work as parameters: a numpy datetime64 or timedelta64, and a pandas Timestamp or Timedelta. A timestamp keeps its own unit, down to microseconds, and a pandas Timestamp with a time zone becomes a TIMESTAMP WITH TIME ZONE. A duration loses any nanoseconds, rounded toward zero. NaT is sent as NULL. A timedelta64 counting months or years is refused, since a month has no fixed length. For calendar months, write an INTERVAL in the SQL, such as placed + INTERVAL 1 MONTH, or placed + to_months(?) with a number.

Other numpy values are not converted for you. np.float64 and np.str_ work, since they are a Python float and str, but np.int64, np.float32, np.bool_ and numpy arrays are refused. Convert them first, with value.item() for a single value or array.tolist() for an array of numbers. For an array of datetime64 or timedelta64, tolist() can give plain integers (it does for nanoseconds), so pass list(array) instead: its items stay numpy dates and durations, which work as above. pandas' pd.NA is refused too: pass None.

what is refused

These raise InvalidInputError from execute:

  • A value of a type not listed above, such as a set. The message names the type.
  • A bytearray or memoryview: pass bytes(value), or dbapi.Binary(value).
  • An int wider than 128 bits, and a Decimal that is NaN or infinite.
  • A Decimal with more than 38 digits, counting those after the point, such as Decimal("1e-40").
  • Today, also a nonzero Decimal whose absolute value is below 0.000001, such as Decimal("0.0000001") or Decimal("-0.0000001"). Send it as text with a cast instead: cur.execute("SELECT ?::DECIMAL(10,9)", [format(value, "f")]).
  • A numpy or pandas timestamp with a part smaller than a microsecond, such as pd.Timestamp("2026-01-01 00:00:00.123456789"). It is refused rather than rounded. A timestamp stored in nanoseconds that holds whole microseconds works.
  • A time whose time zone needs a date to know its offset, such as one from zoneinfo. Use a fixed offset, datetime.timezone(...).
  • A list, or a dict with keys that are not strings, holding datetimes or times both with and without a time zone. Its values must share one type, and no one type holds both. The fields of a dict with string keys may differ: one field can hold a datetime with a time zone and another one without.
  • A list or dict that contains itself.

Details

  • None and empty lists inside a list or dict. A None, or an empty list, has no type of its own, and DuckDB needs one. Inside a list it takes the type of the values beside it, so [None, 1] is a BIGINT[] and [[], ["a"]] a VARCHAR[][]. In a list of dicts, a field takes its type from the field with exactly the same name in the other dicts.
  • When nothing beside it says, the type comes from where the parameter is used: inserting into a VARCHAR[] column, or comparing with one, makes it a VARCHAR[]. When nothing says at all, execute raises InvalidInputError and suggests a cast. Add the cast to give the type, here VARCHAR[], a list of text: 
    cur.execute("SELECT $tags::VARCHAR[]", {"tags": []}).fetchone()      # ([],)
    A plain None as a parameter always works: it is NULL, which fits any type.
  • The values in one list, and the keys and the values of a MAP, must fit one type. Integers and floats fit DOUBLE together, so [1, 2.5] is a DOUBLE[] and comes back as [1.0, 2.5], a large integer can change ([9007199254740993, 1.5] comes back as [9007199254740992.0, 1.5]), and {1: "one", 2.5: "two"} is a MAP(DOUBLE, VARCHAR). [1, "a"] fails with NotSupportedError, and so do {1: "one", "b": "two"} and {1: "one", 2: 2}. A MAP key cannot be None.
  • float("nan") is sent as the number NaN, not as NULL. To send a missing value, use None.
  • numpy datetime64 units carry over: days, weeks, months and years become DATE; hours, minutes and seconds TIMESTAMP_S; milliseconds TIMESTAMP_MS; microseconds and nanoseconds TIMESTAMP.

Reading rows

cur.execute("SELECT id, customer FROM orders ORDER BY id")
cur.fetchone()          # (1, 'acme')
cur.fetchmany(2)        # [(2, 'bolt'), (3, 'acme')]
cur.fetchall()          # [(4, 'cato'), (5, 'dune'), (6, 'eve'), (7, 'fay')]
cur.fetchone()          # None

Each row is a tuple. fetchone() returns the next row, fetchmany(n) the next n rows as a list, and fetchall() all the rows that are left. All three move through the same result, so each starts where the last one stopped. When no rows are left, fetchone() returns None, and the other two an empty list.

You can also loop over the cursor:

cur.execute("SELECT id, customer FROM orders WHERE total > 1000 ORDER BY id")
for order_id, customer in cur:
    print(order_id, customer)
# 1 acme
# 3 acme

fetchall() builds one Python list holding every row that is left, so a large result needs the memory for all of it at once. To work through a large result in parts, call fetchmany() until it returns an empty list. Here range(2500) is a DuckDB function that gives the numbers 0 to 2499:

cur.execute("SELECT * FROM range(2500)")
while True:
    rows = cur.fetchmany(1000)
    if not rows:
        break
    print(len(rows))
# 1000
# 1000
# 500

into a pandas DataFrame

import pandas as pd

cur.execute("SELECT id, customer FROM orders ORDER BY id")
rows = cur.fetchall()
df = pd.DataFrame.from_records(rows, columns=[column[0] for column in cur.description])
df.shape        # (7, 2)

cur.description lists the result's columns, with the name first (see Column names and row counts). Like fetchall(), this holds the whole result in memory. pandas picks each column's type from the values in the rows, so an integer column with a NULL in it becomes float, and an integer above 2**53 can then change in its last digits. To keep such a column exact, build it yourself: df["id"] = pd.array([row[0] for row in rows], dtype="Int64"). A plan from duckdb.frame gives a DataFrame directly, with to_pandas(con) on a frame connection: see Frames & Plans.

A Decimal holds a decimal number exactly, without the rounding a float has. It works with an int or another Decimal, but total * 0.1 raises TypeError. Write the other number as a Decimal, or call float(total) if a float is good enough:

from decimal import Decimal

total = cur.execute("SELECT total FROM orders WHERE id = 1").fetchone()[0]
total * Decimal("0.1")       # Decimal('140.000')

Details

  • A TIMESTAMP WITH TIME ZONE always comes back in UTC, whatever DuckDB's TimeZone setting is, with the standard library's datetime.timezone.utc. Call value.astimezone(...) for local time. You do not need pytz.
  • Python's datetime holds microseconds at most, so a TIMESTAMP_NS or TIME_NS loses its last three digits.
  • timedelta has no months, so an INTERVAL counts a month as 30 days: INTERVAL 1 MONTH comes back as timedelta(days=30).
  • A date or timestamp outside the years Python can hold, 1 to 9999, raises ConversionError naming the value. Cast it to VARCHAR in SQL if you want the text. DuckDB's infinity and -infinity come back as the largest and smallest values Python holds, such as date.max.
  • fetchmany(n) returns exactly n rows each time, until fewer are left. Without a number it uses cur.arraysize. A negative number raises ProgrammingError.
  • Fetching before any execute, or after a statement without a result, such as CREATE TABLE, INSERT or SET, raises InterfaceError. A SELECT that matches no rows still has a result: fetchall() returns [] and fetchone() returns None. A row holding a NULL is (None,).

One result at a time

A connection has one open result at a time. When you run a new statement, on any cursor of the connection, the result that was open ends. If another cursor was still reading it, that cursor's next fetch raises InterfaceError.

the second execute ends the first result
a, b = con.cursor(), con.cursor()
a.execute("SELECT id FROM orders")
b.execute("SELECT customer FROM orders")
a.fetchall()      # raises InterfaceError
read the rows first
a.execute("SELECT id FROM orders")
ids = a.fetchall()
b.execute("SELECT customer FROM orders")

So read the rows you need before you run the next statement. A second connection does not help: to the same file it is refused (see Connecting), and without a path it is a new, empty database. If you do not need the rows, end the result yourself:

  • cur.complete() runs the statement to its end without reading the rows, so everything the statement does gets done.
  • cur.abort() stops the statement where it is and drops the rows you have not read. DuckDB may have produced some of them already, since it works ahead of your fetches.

Both do nothing when the cursor has no open result. commit() and rollback() also end the open result, see Transactions.

Details

  • What happens to the result that ends. A SELECT (or EXPLAIN) stops where it is, and the rows not read yet are dropped. Any other statement that returns rows first runs to its end, and if that fails, the error is raised by the call that ended it. For an INSERT, UPDATE or DELETE with RETURNING, the change is already complete when execute returns, so dropping its rows does not undo it.
  • DuckDB cannot always tell that a SELECT changes something. One that calls nextval('name'), which takes the next number from a sequence (a counter kept in the database), counts as a read: if it ends early, it stops part way, and the open transaction fails. Call complete() on it first. The numbers it took stay taken, even after rollback().
  • What a stopped statement already did stays done. If abort() stops a statement part way through a change, the open transaction fails, and you need rollback().
  • Closing a cursor ends its result the same way a new statement does. commit() does too. rollback(), con.close(), and a ROLLBACK or ABORT statement stop the open result at once, since the transaction's changes are undone anyway.
  • A connection does one thing at a time. While one call is running, for example a fetch in another thread, the connection refuses a second statement, fetch, commit, rollback or close with ProgrammingError. It does not wait. con.interrupt() always goes through.

Column names and row counts

cur.execute("SELECT id, customer, total, placed FROM orders")
cur.description
# [('id', 'INTEGER', None, None, None, None, None),
#  ('customer', 'VARCHAR', None, None, None, None, None),
#  ('total', 'DECIMAL(6,2)', None, None, None, None, None),
#  ('placed', 'DATE', None, None, None, None, None)]

After a query, cur.description has one tuple per column. The standard asks for seven items in each. DuckDB fills in the first two: the column name, and its type as DuckDB writes it, such as 'DECIMAL(6,2)'. The other five are always None. A tool can compare the type with the type objects to learn what kind of column it is.

description is None before the first execute, and after a statement without a result, such as an INSERT. A SELECT that matches no rows still has its description.

rowcount

cur.execute("UPDATE orders SET total = total + 1 WHERE customer = 'acme'")
cur.rowcount        # 2
Afterrowcount
INSERT, UPDATE, DELETEthe number of rows changed
CREATE TABLE ... ASthe number of rows written
COPYthe number of rows written or read
other statements without a result, such as CREATE, DROP, ALTER or SET0
a query, or anything else that returns rows, RETURNING included-1
executemanythe total over all the sets; -1 if the statement returns rows, or the list was empty
a statement that raised an error-1

For a query, rowcount stays -1, even after you have fetched every row. Use len(rows) on the rows you fetched, or ask with SELECT count(*).

An execute that fails clears both: description is None and rowcount is -1, so neither keeps describing the statement before it. An error while you fetch, such as a date Python cannot hold, leaves both as they were.

Transactions

A transaction is a group of changes that is saved, or undone, as a whole. By default, the first statement you run opens one. Every statement after it runs inside it, reads included, on every cursor of the connection. con.commit() saves the changes and ends the transaction. con.rollback() undoes them. The next statement opens a new transaction.

cur = con.cursor()
cur.execute("INSERT INTO orders VALUES (9, 'hal', 1, '2026-04-04')")
con.rollback()
cur.execute("SELECT count(*) FROM orders").fetchone()     # (7,): the insert is gone

commit() and rollback() do nothing when no transaction is open. close() rolls back, so changes you did not commit are not saved in the file. A with con: block commits at its end, or rolls back if it raises, and either way that includes changes made before the block.

commit() and rollback() end the open result. A cursor part way through a result loses the rest, and its next fetch raises InterfaceError. Read the rows first.

after an error

Most errors fail the open transaction. After one, every statement on the connection raises TransactionError, with the message Current transaction is aborted (please ROLLBACK), until you call rollback(). That undoes everything since your last commit, not only the statement that failed. If you catch the error and call commit() instead, it saves nothing and raises nothing.

try:
    cur.execute("SELECT * FROM no_such_table")
    rows = cur.fetchall()
except dbapi.Error as error:
    con.rollback()                  # needed before the connection runs anything else
    print(type(error).__name__)     # CatalogError

Keep the fetch inside the try too, since an error can also come from a fetch (see Running SQL). dbapi.Error catches every error DuckDB reports; here it is a CatalogError, since the table does not exist. In a program, end the except block with raise after the rollback, so the failure is not hidden. A few errors leave the transaction as it was. These are a syntax error (ParserError), some refusals that happen before the statement starts, such as a parameter value of a type that cannot be sent, and a fetched value Python cannot hold, such as a date after the year 9999. When an error leaves a with con: block, the block rolls back for you.

autocommit

auto = dbapi.connect(autocommit=True)
ac = auto.cursor()
ac.execute("CREATE TABLE notes (text VARCHAR)")
ac.execute("INSERT INTO notes VALUES ('kept')")
auto.rollback()                                  # nothing to undo: each statement was saved as it ran
ac.execute("SELECT * FROM notes").fetchall()     # [('kept',)]

With autocommit=True, no transaction is opened for you. Each statement is saved as soon as it runs, and an error affects only the statement that raised it. commit() and rollback() save or undo nothing, but they still end the open result, as in the default mode. A with block on such a connection has nothing to commit or roll back.

Details

  • BEGIN, COMMIT and ROLLBACK as SQL. In the default mode, end transactions with commit() and rollback(), not with SQL. A BEGIN statement raises TransactionError, since a transaction is open already. A COMMIT or ROLLBACK statement ends the transaction without the connection knowing, and its later commit(), rollback() and close() then raise TransactionError. To recover, run cur.execute("BEGIN"), then con.rollback(); statements you ran before that were saved at once. With autocommit=True you can run BEGIN, COMMIT and ROLLBACK as SQL yourself; commit() and rollback() still save or undo nothing there.
  • Each transaction sees the database's tables as they were when it began, but not frozen copies of registered Python objects or files: a later query in the same transaction sees changes to those. While your connection can write to a DuckDB file, nothing else can write to it (see Connecting). So this only matters for data that other programs can change at the same time, such as a database you attach through an extension. To see their latest changes, end your transaction with commit() or rollback(), or use autocommit=True.

Querying Python data

import pandas as pd

discounts = pd.DataFrame({"customer": ["acme", "bolt"], "discount": [0.1, 0.2]})
con.register("discounts", discounts)
cur.execute("SELECT o.id, d.discount FROM orders o JOIN discounts d USING (customer) ORDER BY o.id").fetchall()
# [(1, 0.1), (2, 0.2), (3, 0.1)]

con.register(name, obj) lets SQL read a Python object as if it were a table called name, from every cursor of the connection. Nothing is copied: DuckDB reads the object each time a query uses it, so a query sees the object as it is at that moment.

The name stays tied to the object you passed. A change made to that object, such as discounts.loc[0, "discount"] = 0.15, shows in the next query; do not make one while a result from it is still being fetched, since that result can then mix old and new values. But a method that returns a DataFrame, such as assign(), makes a new one, so register the new one again:

discounts = discounts.assign(discount=[0.15, 0.25])
con.register("discounts", discounts)
cur.execute("SELECT discount FROM discounts ORDER BY customer").fetchall()     # [(0.15,), (0.25,)]

In SQL, double quotes mark a name and single quotes mark text. So a name with a space in it, such as a pandas column called order total, goes in double quotes; 'order total' would be just that text:

con.register("sales data", pd.DataFrame({"order total": [5, 7]}))
cur.execute('SELECT sum("order total") FROM "sales data"').fetchone()     # (12,)

SQL can read a registered object but not change it: an UPDATE of discounts raises ProgrammingError. Nothing is stored in the database either, so commit() does not save it. To keep the data, copy it into a table, then commit. con.unregister(name) removes the name again:

cur.execute("CREATE TABLE kept AS SELECT * FROM discounts")
con.commit()
con.unregister("discounts")
cur.execute("SELECT * FROM kept ORDER BY customer").fetchall()      # [('acme', 0.15), ('bolt', 0.25)]

You can register:

  • a pandas DataFrame (its index is left out) or Series;
  • a polars DataFrame, Series or LazyFrame;
  • a pyarrow Table, RecordBatch, Array, Dataset or Scanner;
  • a numpy array, or a dict, list or tuple of one-dimensional numpy arrays;
  • any other object that offers its data as Arrow, a standard layout for columns of data in memory that pandas, polars and pyarrow share.

How each kind of object is read, column types included, is described in Frames & Plans. Registering works the same way there.

Details

  • A pyarrow RecordBatchReader, or an Arrow stream capsule (the raw object an __arrow_c_stream__ method returns), is a stream: data that arrives in pieces and can be read only once. A second query over it fails with InvalidInputError. Registering the same reader again does not help: it stays used up, and reads as empty, without an error. Register a new reader made from the source data, or copy the data into a table first with CREATE TABLE ... AS SELECT * FROM name.
  • Registering a name again replaces the earlier object. A real table or view with the same name comes first.
  • A registration is not part of the transaction: rollback() does not remove it. It lasts until unregister() or until the connection closes. Registering does not end an open result; while a cursor still has one, register() and unregister() raise OperationalError, so read it to the end or end it with cur.abort() first.
  • A query reads only the columns it uses. A pyarrow Dataset and a polars LazyFrame also get the query's simple conditions, such as comparisons, IN and IS NULL, so they read less.
  • Reading a pandas DataFrame does not need pyarrow installed. A column of Python objects of different kinds, such as numbers mixed with text, is read as text (VARCHAR).
  • A pyarrow Array or a pandas Series is one column named value. A polars Series keeps its own name, or is named value if it has none. A struct Array or struct polars Series gives one column per field instead. A numpy array gives columns named column0, column1 and so on; a dict of arrays uses its keys as the column names.
  • An object offers its data as Arrow through the __arrow_c_stream__ or __arrow_c_array__ method. A name that is not a string, or an object of a kind not listed, raises TypeError. unregister() of a name nothing is registered under raises ProgrammingError.

Stopping a query

Press Ctrl‑C while execute or a fetch is running, and the query stops with KeyboardInterrupt, as anywhere in Python, unless it is calling a Python function of yours: then it fails with InvalidInputError. From another thread, con.interrupt() stops whatever the connection is running. The call that was running then fails with InterruptError. con.interrupt() stops a long query or a long fetch promptly; Ctrl‑C can take much longer to stop some queries, such as the cross join below.

import threading
from duckdb import exceptions

threading.Timer(0.5, con.interrupt).start()
try:
    cur.execute("SELECT sum(a.range * b.range) FROM range(1000000) a, range(1000000) b")
except exceptions.InterruptError:
    print("stopped")          # stopped
    con.rollback()

InterruptError fails the open transaction like most errors, so call rollback() next. interrupt() does nothing when the connection is not running anything.

Errors

Warning
Error
├── InterfaceError
└── DatabaseError
    ├── DataError            ConversionError
    ├── OperationalError     IOError, OutOfMemoryError, ConnectionError, TransactionError, InterruptError
    ├── IntegrityError       ConstraintError

The tree on the left is the standard's list of error classes, and dbapi exports those names. The names on the right are more exact kinds of each, and live in duckdb.exceptions. They are the same classes everywhere: dbapi.Error is duckdb.exceptions.Error, and except dbapi.ProgrammingError also catches a CatalogError.

cur.execute("CREATE OR REPLACE TABLE users (id INTEGER PRIMARY KEY)")
cur.execute("INSERT INTO users VALUES (1)")
con.commit()
try:
    cur.execute("INSERT INTO users VALUES (1)")
except dbapi.IntegrityError as error:
    print(type(error).__name__)       # ConstraintError
    con.rollback()

InterfaceError means the package was used in a way it does not allow, such as a closed cursor or connection, or a fetch with no result. Everything else DuckDB reports is a DatabaseError, of the kind DuckDB gives it, with DuckDB's own message:

  • a table, view or function that does not exist: CatalogError;
  • a column that does not exist, or a function given the wrong types: ProgrammingError, with a message starting Binder Error:;
  • a value that does not convert, such as 'abc'::INTEGER: ConversionError;
  • a duplicate key or a broken NOT NULL or CHECK rule: ConstraintError;
  • the wrong number of parameters: InvalidInputError.

Details

  • Warning is exported because the standard lists it, but nothing raises it. It is not an Error, so except Error does not catch it.
  • An error kind this package does not know, from a newer DuckDB, comes through as a plain DatabaseError.
  • Ctrl‑C raises KeyboardInterrupt, which is not an Error either, or InvalidInputError if the query was calling a Python function of yours. A query stopped by con.interrupt() raises InterruptError, a kind of OperationalError.
  • A few mistakes are caught in Python and raise TypeError: SQL that is not a string, a register() name or object it cannot use, and a plan from duckdb.frame run on a dbapi connection.

type objects

cur.execute("SELECT id, customer, placed FROM orders")

A type object stands for a group of DuckDB types. It is equal to the type in description of every type in its group. Anything in brackets after the type name is ignored, so DECIMAL(18,3) is a NUMBER and ENUM('x', 'y') a STRING.

constructors

dbapi.Date(2026, 1, 1)                  # datetime.date(2026, 1, 1)
dbapi.Time(12, 30)                      # datetime.time(12, 30)
dbapi.Timestamp(2026, 1, 1, 12, 30)     # datetime.datetime(2026, 1, 1, 12, 30)
dbapi.DateFromTicks(1767225600)         # datetime.date(2026, 1, 1)
dbapi.TimeFromTicks(1767225600)         # datetime.time(0, 0)
dbapi.TimestampFromTicks(1767225600)    # datetime.datetime(2026, 1, 1, 0, 0, tzinfo=datetime.timezone.utc)
dbapi.Binary(bytearray(b"\x00\x01"))    # b'\x00\x01'

The standard asks for these so that tools can build values without knowing the driver. Date, Time and Timestamp are Python's own datetime classes. The three FromTicks functions take a Unix timestamp, in seconds since 1970, and read it as UTC, so DateFromTicks(0) is 1970‑01‑01 wherever the program runs. TimestampFromTicks gives a datetime in UTC, so a TIMESTAMP column, which has no time zone, stores it in DuckDB's TimeZone setting, your local time by default: the example above is stored as 2025‑12‑31 19:00 in New York. Binary turns a bytearray or memoryview into bytes, which is what a BLOB parameter needs.
