The DB-API

duckdb.dbapi is DuckDB behind PEP 249: connect, a cursor, execute, the fetch family, commit and rollback. It is here because other tools ask for exactly that. It follows the specification strictly and adds nothing to it.

What this module is

PEP 249 is the interface Python tooling expects from a database driver: ORMs, notebook SQL cells, migration tools, connection pools. duckdb.dbapi is that interface over DuckDB, and nothing more.

The execute, fetch and cursor vocabulary exists because PEP 249 asks for it, not because it is the natural way to use DuckDB. So it lives in its own module, apart from the rest of the package. Use it when something else needs a DB-API driver. For code you write yourself, build plans; that is Frames & Plans. A plan does not run on a dbapi connection, but its SQL does: cur.execute(plan.render()).

from duckdb import dbapi

con = dbapi.connect("shop.db")
cur = con.cursor()
cur.execute("SELECT customer, total FROM orders WHERE total > ?", [1000])
cur.fetchall()        # [('acme', Decimal('1400.00')), ('acme', Decimal('2600.00'))]
con.commit()
con.close()

Everything on this page follows that example. What DuckDB adds is in the details: real row counts, one transaction shared by every cursor, and errors typed by the engine's own error codes.

Connecting

con = dbapi.connect()                                                # in memory
con = dbapi.connect("shop.db")                                       # a file, created if it does not exist
con = dbapi.connect("shop.db", access_mode="READ_ONLY", threads=4)
con = dbapi.connect("shop.db", autocommit=True)

database is a path, as a string, or ":memory:", the default. Every other keyword is a DuckDB setting under its own name, applied as the database opens. The value is sent as text, so threads=4 and threads="4" are the same. Some settings, access_mode among them, can only be chosen here, before the database exists. A name the engine does not know is refused with InvalidInputError, and so is a value it cannot read.

autocommit is the one keyword that is not a setting. Left False, the first statement opens a transaction that commit() ends and close() rolls back. Set True, no transaction is opened and every statement stands on its own. The details are under Transactions.

one file, one open

A database file is open once at a time within a process. A second connect() to a file that is already open raises ProgrammingError, naming the file handle conflict. Open it once and take cursors from that connection; close it and it can be opened again.

the connection as a context manager

with con:
    con.cursor().execute("INSERT INTO orders VALUES (4, 'cato', 90, '2026-03-05')")
# committed; con is still open

The block is a transaction: COMMIT when it ends, ROLLBACK if it raises. The connection stays open afterwards. PEP 249 leaves this to the driver, and this is what sqlite3 does and what a caller means by with connection:. Closing is close().

closing

close() rolls back whatever was not committed, then releases the engine connection. Calling it again does nothing. After it, cursor() raises InterfaceError, and so does execute on any cursor the connection made.

Cursors

con.cursor() gives a cursor: where statements run and rows come out. Make as many as you like. Every cursor shares the connection's engine connection, so every cursor shares its transaction. What one cursor writes, a sibling reads before any commit. PEP 249 requires this, and the old client could not do it.

writer, reader = con.cursor(), con.cursor()
writer.execute("INSERT INTO orders VALUES (5, 'dune', 700, '2026-03-06')")
reader.execute("SELECT count(*) FROM orders")
reader.fetchone()      # (5,): the same transaction, so the insert is visible

One result at a time. The engine keeps one live result per connection, and cursors share theirs. An execute on any cursor releases whatever result is open, including one a sibling cursor is still reading; that sibling's next fetch raises InterfaceError. PEP 249 permits this; it is what ODBC does without MARS. Read a result out before running the next statement on the connection.

the second execute discards the first result
a.execute("SELECT id FROM orders")
b.execute("SELECT customer FROM orders")
a.fetchall()      # InterfaceError: no result set
read it out first
a.execute("SELECT id FROM orders")
ids = a.fetchall()
b.execute("SELECT customer FROM orders")

lifecycle

with con.cursor() as cur:
    cur.execute("SELECT 1")
    cur.fetchone()
# cur is closed

close() releases the cursor's result and is idempotent. A closed cursor refuses every execute and every fetch with InterfaceError. cur.connection is the connection it came from. cur.arraysize is how many rows fetchmany() returns when not told; it starts at 1.

Executing

cur.execute("SELECT customer FROM orders WHERE placed < ?", [dbapi.Date(2026, 2, 1)])
cur.execute("INSERT INTO orders VALUES (?, ?, ?, ?)", (6, "eve", 10, "2026-04-01"))

execute(operation, parameters=None) runs one statement and returns the cursor, so cur.execute(...).fetchall() chains. parameters is a sequence for positional placeholders or a mapping for named ones.

parameter style

cur.execute("SELECT ? + ?", [2, 3])                      # qmark: what paramstyle says
cur.execute("SELECT $1 + $2", [2, 3])                    # DuckDB's own positional form
cur.execute("SELECT $a + $b", {"a": 2, "b": 3})          # DuckDB's named form

paramstyle is "qmark". DuckDB itself also reads $1 and $name, and a cursor passes those through, because they are the engine's syntax and the engine binds them. PEP 249 wants one answer, and qmark is the one every DB-API consumer can produce. :name, %s and %(name)s are not SQL to DuckDB and fail with ParserError. Too many or too few values is InvalidInputError, and the message names the parameters concerned.

A value never becomes part of the SQL text; it is sent to the engine separately. None, bool, int of any width, float, str, bytes, Decimal at its own scale, date, time, datetime, timedelta and UUID all bind, and an aware datetime or time keeps its offset. A list binds as a list; a dict with string keys as a STRUCT, with any other keys as a MAP. In a mapping of parameters the names must be strings.

what execute does

A query is prepared and its result opened; nothing is read until you fetch. description is known at once, since the column names and types arrive when the result opens, and the rows are produced as you fetch them. So an error inside a row, a value that will not cast, is raised by the fetch that reaches it, not by execute.

cur.execute("SELECT 'abc'::INTEGER AS n")   # fine: the statement binds
cur.description                             # [('n', 'INTEGER', None, None, None, None, None)]
cur.fetchone()                              # ConversionError

Any other statement runs to completion inside execute. Its effect has landed when the call returns, and rowcount says how many rows it changed.

One statement per call. "CREATE TABLE t (v INTEGER); INSERT INTO t VALUES (1)" is refused with InvalidInputError; run each on its own.

executemany

cur.executemany("INSERT INTO orders VALUES (?, ?, ?, ?)", [
    (6, "eve", 10, "2026-04-01"),
    (7, "fay", 20, "2026-04-02"),
])
cur.rowcount        # 2

DuckDB has no batched bind, so the sets run one after another, in order. rowcount is the total across them, as sqlite3 reports it. It is -1 when the statement produced rows, or when the sequence was empty.

Fetching

cur.execute("SELECT id, customer FROM orders ORDER BY id")
cur.fetchone()          # (1, 'acme')
cur.fetchmany(2)        # [(2, 'bolt'), (3, 'acme')]
cur.fetchall()          # [(4, 'cato'), (6, 'eve'), (7, 'fay')]
cur.fetchone()          # None

The three share one position. A row is a tuple. fetchone gives None at the end; the other two give an empty list. fetchmany() with no size uses arraysize; a negative size is ProgrammingError. The cursor is its own iterator:

cur.execute("SELECT id, customer FROM orders ORDER BY id")
for order_id, customer in cur:
    ...

The result streams from the engine in chunks; a fetchmany(700) loop over five thousand rows crosses chunk boundaries without noticing. Fetching before execute, or after a statement that produced no rows, raises InterfaceError.

stopping

Ctrl‑C while execute or a fetch is inside the engine raises KeyboardInterrupt, as any Python program expects. The interrupt lands between batches of rows, so it is prompt on a long fetch.

description and rowcount

cur.execute("SELECT id, customer, total, placed FROM orders")
cur.description
# [('id',       'INTEGER',      None, None, None, None, None),
#  ('customer', 'VARCHAR',      None, None, None, None, None),
#  ('total',    'DECIMAL(6,2)', None, None, None, None, None),
#  ('placed',   'DATE',         None, None, None, None, None)]

One seven-tuple per column, laid out as PEP 249 says: name, type_code, display_size, internal_size, precision, scale, null_ok. The name and the type code are filled in. The type code is the engine's own text for the type, parameters included, and it is what the type objects compare against. The other five are None. description is None before the first execute, after a statement that produced no rows, and after one that failed.

rowcount

Afterrowcount

SELECT, and anything else that returns rows, RETURNING included-1

A query's count is -1 because its result streams, and the number of rows is not known until they have been read. Every other count is real. The old client reported -1 for everything.

A statement that raises leaves nothing behind: description is None and rowcount is -1, not the previous statement's values. Keeping those would describe a statement that never ran.

Transactions

On a connection opened with the default autocommit=False, the first statement opens a transaction, and every cursor works inside it. commit() ends it; rollback() discards it; either does nothing when no transaction is open. The next statement opens a fresh one.

cur = con.cursor()
cur.execute("INSERT INTO orders VALUES (9, 'hal', 1, '2026-04-04')")
con.rollback()
cur.execute("SELECT count(*) FROM orders")     # the insert is gone

close() rolls back, as PEP 249 requires: work not committed before the connection closes is not in the file. The context manager commits at the end of the block and rolls back if the block raises.

after an error

Most errors abort the open transaction. After one, every statement on the connection raises TransactionError until rollback() is called, and the message says so: Current transaction is aborted (please ROLLBACK). A syntax error is the exception, since the parser refuses it before the transaction is touched.

try:
    cur.execute("SELECT * FROM no_such_table")
except dbapi.ProgrammingError:
    con.rollback()                              # nothing else runs until this

Inside with con: the rollback is automatic, since the block rolls back on any exception.

commit() and rollback() release the open result. A cursor part way through a result loses the rest, and its next fetch raises InterfaceError. Read the rows out first.

autocommit

auto = dbapi.connect("shop.db", autocommit=True)
cur = auto.cursor()
cur.execute("INSERT INTO orders VALUES (10, 'ivy', 2, '2026-04-05')")
auto.rollback()                                 # nothing to undo: the insert stands

With autocommit=True no transaction is opened. Each statement commits itself, commit() and rollback() do nothing, and an error affects only the statement that raised it.

type objects

cur.execute("SELECT id, customer, placed FROM orders")
[column[1] == dbapi.NUMBER for column in cur.description]     # [True, False, False]

Each type object compares equal to the type code of every engine type it covers. A parameterised type is judged on its head, so DECIMAL(18,3) is a NUMBER and ENUM('x', 'y') a STRING.

constructors

dbapi.Date(2026, 1, 1)                  # datetime.date
dbapi.Time(12, 30)                      # datetime.time
dbapi.Timestamp(2026, 1, 1, 12, 30)     # datetime.datetime
dbapi.DateFromTicks(1767225600)         # date(2026, 1, 1)
dbapi.TimeFromTicks(1767225600)         # time(0, 0)
dbapi.TimestampFromTicks(1767225600)    # datetime(2026, 1, 1, tzinfo=timezone.utc)

Date, Time and Timestamp are the standard library classes themselves. The three FromTicks constructors read the tick count as UTC, so DateFromTicks(0) is 1970‑01‑01 wherever the program runs. Binary gives bytes, which binds as a BLOB.

Errors

Warning
Error
├── InterfaceError
└── DatabaseError
    ├── DataError            ConversionError
    ├── OperationalError     IOError, OutOfMemoryError, ConnectionError, TransactionError, InterruptError
    ├── IntegrityError       ConstraintError
    ├── InternalError        FatalError
    ├── ProgrammingError     ParserError, CatalogError, InvalidInputError, ConfigurationError
    └── NotSupportedError

The left column is PEP 249's hierarchy, and dbapi exports those names. The right column is the leaves, which live in duckdb.exceptions. They are the same classes: dbapi.Error is duckdb.exceptions.Error, so except dbapi.ProgrammingError catches a CatalogError.

InterfaceError is misuse of this package: a closed cursor or connection, a fetch with no result. Everything the engine reports is a DatabaseError, and the leaf is chosen by the engine's error code. A missing table is CatalogError, a value that will not convert ConversionError, a duplicate key ConstraintError, a mismatched parameter count InvalidInputError. A code this build has never seen, from a newer engine, comes through as a plain DatabaseError rather than being lost.

try:
    cur.execute("INSERT INTO u VALUES (1)")
except dbapi.IntegrityError as error:        # a ConstraintError
    con.rollback()

The message is the one DuckDB gives any client. Warning is exported because PEP 249 lists it; nothing in this package raises it. It is not an Error, so except Error does not swallow it.

Ctrl‑C is not an Error either: it raises KeyboardInterrupt.

Changes from the old client

For someone arriving from the old duckdb package. Each row is a deliberate difference, logged in compat/BEHAVIOR.md. Code that needs the old client as it was runs on duckdb.compat; that is Compat.

Old clientNow
duckdb.connect() returned an object carrying execute, the fetch family, description and rowcount.duckdb.connect() carries none of that. The DB-API vocabulary lives in duckdb.dbapi, strictly PEP 249, and in duckdb.compat, as the old client had it.
cursor() handed back an independent duplicate connection with its own transaction, closed along with its parent.Cursors share their connection's transaction, as PEP 249 requires. duckdb.compat keeps the old semantics.
rowcount was always -1.Real counts for INSERT, UPDATE, DELETE and CREATE TABLE AS; -1 only for a row-producing statement. duckdb.compat still reports -1.
Exception classes had their own names: CatalogException, ConnectionException, BinderException and so on.Classes follow the engine's error codes, rooted in PEP 249, in duckdb.exceptions. The old names exist as aliases in duckdb.compat only; ConnectionException there is InterfaceError.
Ctrl‑C during a query was converted to RuntimeError.It raises KeyboardInterrupt.
A parameter mapping accepted any key and stringified it.Keys must be strings; anything else is InvalidInputError. The leniency lives in duckdb.compat alone.
Opening one file twice shared a single database instance per path.A second open of a file already open is refused with ProgrammingError. duckdb.compat reproduces the shared instance.
execute("a; b; c") ran all three and returned the last result.One statement per call; more is InvalidInputError. Multi-statement execute is pending.
A temporal value beyond Python's datetime range came back silently as text.It raises ConversionError naming the value.
A MAP whose keys Python cannot hash came back as a {'key': [...], 'value': [...]} dict of lists.It comes back as a list of (key, value) pairs.
Aware values carried pytz zones, and TIMESTAMPTZ was converted into the session time zone.Aware values carry the standard library's datetime.timezone; TIMESTAMPTZ comes back in UTC.
In duckdb.compat, as on duckdb.connect(), a connection closes when its with block ends.A dbapi connection's with block is a transaction: commit or roll back, and stay open.

If a table does not exist or a value will not convert, the error comes from DuckDB, with the message it would give any client. The specification this module follows is PEP 249.
