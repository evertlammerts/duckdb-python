Building and running queries

This page shows how to build a query in Python with duckdb.frame, run it, and get the results back: as rows, or as a pandas or polars DataFrame, numpy arrays or an Arrow table. It also covers reading files and Python data, and saving results to tables and files.

Start here

from duckdb import frame
from duckdb.frame import col, table

con = frame.connect()
con.run("CREATE TABLE orders (id INTEGER, customer VARCHAR, region VARCHAR, placed DATE, total DECIMAL(8,2))")
con.run("""
    INSERT INTO orders VALUES
        (1, 'acme', 'emea', '2026-01-11', 1400),
        (2, 'bolt', 'amer', '2026-01-20', 320),
        (3, 'acme', 'emea', '2026-02-02', 2600),
        (4, 'cora', 'apac', '2026-02-14', 900),
        (5, 'bolt', 'amer', '2026-03-01', 1150)
""")

orders = table("orders")
big = orders.filter(col("total") > 1000).select("customer", "total")
print(big.rows(con))
# [('acme', Decimal('1400.00')), ('acme', Decimal('2600.00')), ('bolt', Decimal('1150.00'))]

orders and big are plans: descriptions of a query that has not run yet. col("total") > 1000 is an expression, a piece of a query. Each method, such as filter or select, gives you a new plan and leaves the old one as it was.

Nothing runs until a method gets a connection. Here rows(con) runs the query on con and returns the rows as a list of tuples. A plan does not belong to a connection, so you can run the same plan on any database that has the tables it reads.

DECIMAL(8,2) is an exact number with 2 digits after the point, and Python gets it as a decimal.Decimal (see Start here on the main page). Adding a float to one raises TypeError; add another Decimal instead: after from decimal import Decimal, big.first(con)[1] + Decimal("0.10") gives Decimal('1400.10').

frame.connect() opens a new database in memory. It lasts until the last connection to it closes (a connection from con.duplicate() counts too), and then its tables are gone. To keep them, open a database file instead; see Connecting. The examples on this page build on each other: run them in order, on one fresh connection, in an empty folder, since some of them write files. The comments show what the Python prompt or a notebook shows; in a script, wrap a line in print(...) to see its result.

To look at some rows while you work, use show:

orders.head(3).show(con)

│ id      │ customer │ region  │ placed     │ total        │
│ INTEGER │ VARCHAR  │ VARCHAR │ DATE       │ DECIMAL(8,2) │
├─────────┼──────────┼─────────┼────────────┼──────────────┤
│ 1       │ acme     │ emea    │ 2026-01-11 │ 1400.00      │
│ 2       │ bolt     │ amer    │ 2026-01-20 │ 320.00       │
│ 3       │ acme     │ emea    │ 2026-02-02 │ 2600.00      │
└─────────┴──────────┴─────────┴────────────┴──────────────┘

If you run several things on one connection, attach it once with on(con). The methods then need no connection:

emea = orders.filter(col("region") == "emea").on(con)
emea.count()    # 2
emea.first()    # (1, 'acme', 'emea', datetime.date(2026, 1, 11), Decimal('1400.00'))

Attach the connection last. An attached plan has only the methods that run it or look at it, so orders.on(con).filter(...) raises AttributeError. Build the plan first, then call on(con).

Printing a plan shows the SQL it stands for:

print(orders)    # <Frame SELECT * FROM "orders">

Where a plan starts

A plan starts from a table, a piece of SQL, rows you type in, a file, a table function, or Python data you have registered.

A table or view

from duckdb.frame import sql, table

table("orders").count(con)              # 5
table(("main", "orders")).count(con)    # 5: a name with its schema, as a tuple

sql("SHOW TABLES").rows(con)           # [('orders',)]
table("orders").schema(con)
# [('id', 'INTEGER'), ('customer', 'VARCHAR'), ('region', 'VARCHAR'), ('placed', 'DATE'), ('total', 'DECIMAL(8,2)')]

A schema of a database is a named group of tables in it; main is the one you get by default. To find your way in a database someone gives you, list its tables with SHOW TABLES (SHOW ALL TABLES also lists those in other schemas), then ask a table for its columns with schema(con). In that method the word means something else: the column names and their types.

SQL

from duckdb.frame import sql

from_sql = sql("SELECT * FROM orders WHERE region = 'emea'")
from_sql.filter(col("total") > 2000).rows(con)
# [(3, 'acme', 'emea', datetime.date(2026, 2, 2), Decimal('2600.00'))]

sql() takes any query, written as SQL. You can carry on from it with every method on this page.

The SQL text cannot hold placeholders such as $region or ?: running it with parameters= raises ValueError. Put the value in a later step instead, as sql("SELECT * FROM orders").filter(col("region") == param("region")) does (see Values given when it runs). For a query with placeholders, use the DB-API module.

That rule is for sql() plans. con.run() takes placeholders, ? with a list of values or $name with a dict, and returns only the number of rows changed. A statement with RETURNING still makes its change, but run() returns 0 for it; use sql(...).rows(con) to get the returned rows.

con.run("UPDATE orders SET region = ? WHERE id = ?", ["apac", 4])                                # 1
con.run("UPDATE orders SET region = $region WHERE id = $id", {"region": "apac", "id": 4})    # 1

Rows you type in

from duckdb.frame import values

regions = values([("emea", "Europe"), ("amer", "Americas")], columns=["region", "name"])
regions.rows(con)    # [('emea', 'Europe'), ('amer', 'Americas')]

rates = values([("eur", 1.08)], columns=[("currency", "VARCHAR"), ("rate", "DECIMAL(4,2)")])
rates.types()        # ['VARCHAR', 'DECIMAL(4,2)']

values() needs no table, so you can try out a plan before any database exists. A column given as a (name, type) pair is converted to that type. When every column has a type, the plan knows its columns and types without a connection, as rates.types() shows. With no rows, give every column a type: values([], columns=[("code", "VARCHAR")]).

Files

First, a few files to read. Saving results explains how these are written.

from datetime import date
from duckdb.frame import read_csv, read_json, read_parquet

orders.to_csv(con, "orders.csv")
orders.to_json(con, "orders.json")
orders.filter(col("placed") < date(2026, 2, 1)).to_parquet(con, "early.parquet")
orders.filter(col("placed") >= date(2026, 2, 1)).to_parquet(con, "later.parquet")

Now read them back:

read_csv("orders.csv").count(con)                          # 5
read_parquet(["early.parquet", "later.parquet"]).count(con)  # 5
read_parquet("*.parquet").count(con)                       # 5: every file the pattern matches
read_json("orders.json").columns(con)                      # ['id', 'customer', 'region', 'placed', 'total']
table("orders.csv").count(con)                             # 5: a file name in table() reads the file

read_csv("orders.csv", header=True, types={"total": "DOUBLE"}).types(con)
# ['BIGINT', 'VARCHAR', 'VARCHAR', 'DATE', 'DOUBLE']

Each reader takes one file, a list of files, or a pattern with * in it. Keyword arguments are the reader's own options, named as in DuckDB's pages on reading CSV, JSON and Parquet. For example, dateformat="%d/%m/%Y" reads dates written as 11/01/2026, union_by_name=True reads files whose columns differ by matching the columns by name, and filename=True adds a column with the file each row came from. A Python list becomes a SQL list. A dict becomes a struct, DuckDB's record type with named fields, which Python sees as a dict; that is what types= takes here.

To load a file into a table, end the plan with create(con, name), or with insert_into(con, name) for a table that already exists. Both return the number of rows written. The last line does what the second does, written in SQL, so running both adds the file's rows twice:

read_csv("orders.csv").filter(col("total") > 1000).create(con, "big_from_csv")    # 3
read_csv("orders.csv").insert_into(con, "big_from_csv")                           # 5: now 8 rows
con.run("COPY big_from_csv FROM 'orders.csv' (HEADER)")                           # 5: now 13 rows

Table functions

from duckdb.frame import table_function

table_function("range", 3).rows(con)                    # [(0,), (1,), (2,)]
table_function("generate_series", 1, 9, 4).rows(con)    # [(1,), (5,), (9,)]

table_function() calls any function that returns a table, also one an extension adds once you have loaded it, such as table_function("read_xlsx", "book.xlsx", sheet="Q1"). Keyword arguments are passed by name.

Python data

import pandas as pd

targets = pd.DataFrame({"region": ["emea", "amer", "apac"], "target": [3000, 1500, 1000]})
con.register("targets", targets)
table("targets").count(con)     # 3

This example needs pandas. con.register(name, data) gives a pandas or polars DataFrame, an Arrow table or numpy arrays a name, so plans and SQL can read it like a table. Querying Python data lists what you can register and what each turns into.

Details

  • A string is always one name. table("a.b") is the table called a.b, not table b in schema a. For a name with its schema or database, pass a tuple, as long as you need: table(("shop", "main", "orders")). table_function() takes a tuple the same way.
  • In table(), a name that is a file or a pattern such as data/*.parquet reads the files, as FROM 'data/*.parquet' does in SQL.
  • An argument of a reader or table function cannot be a param() (see Running a plan). DuckDB needs the arguments to work out the plan's columns, before any parameter value arrives. It raises TypeError.
  • Asking for the columns of a file, as read_json(...).columns(con) does, makes DuckDB read the start of the file.
  • In values(), every row needs one value per column, or it raises ValueError. With no rows and a column without a type, it raises ValueError too. The values are sent to DuckDB when the plan runs; see Values, names and SQL text.

Choosing rows and columns

Each method returns a new plan, so you can keep a plan in a variable and build several others from it:

from duckdb.frame import lit, sql_expr

recent = orders.filter(col("placed") >= date(2026, 2, 1))

recent.select("customer", "total").sort(col("total").desc()).rows(con)
# [('acme', Decimal('2600.00')), ('bolt', Decimal('1150.00')), ('cora', Decimal('900.00'))]
recent.with_columns(half=col("total") / 2).select("id", "half").head(2).rows(con)
# [(3, 1300.0), (4, 450.0)]
MethodWhat it does
.filter(condition)Keep the rows where the condition is true.
.select(*columns)Keep these columns or expressions, in this order. Give each as its own argument, select("id", "customer"); for a list names, write select(*names).
.with_columns(name=expression)Add a column, or replace the one with that name.
.drop(*names)Remove columns.
.rename(old="new")Rename columns. For a name that is not a Python name, pass a dict from old to new names: rename(**{"Order Total": "total"}).
.sort(*columns)Order the rows. Use .desc() or .nulls_last() on a column.
.head(n), .limit(n, offset), .offset(n)Keep the first n rows, or skip some.
.distinct(), .distinct(on=...)Remove duplicate rows, or keep one row for each value of on.
.sample(n), .sample(percent=...)A random selection of rows. seed= gives the same selection every time.

In these methods, a string names a column. select("customer", "total") picks two columns, and with_columns(copy="total") adds a copy of the column total. For a value, use lit(): with_columns(source=lit("web"), one=lit(1)). See How strings are read.

filter() takes an expression, not text. filter("total > 1000") raises TypeError. Write filter(col("total") > 1000), or filter(sql_expr("total > 1000")) to write the condition as SQL.

Without sort(), the order of the rows is not fixed, and neither is which rows head() keeps. Sort first when it matters: orders.sort(col("placed").desc()).head(2) gives the two newest orders. distinct(on="customer") keeps one row per customer. Straight after a sort(), it keeps the first row of each customer in that order, so this keeps each customer's newest order:

orders.sort(col("placed").desc(), col("id").desc()).distinct(on="customer").select("customer", "id").sort("customer").rows(con)
# [('acme', 3), ('bolt', 5), ('cora', 4)]

With any other step between the sort() and the distinct(), such as a filter(), which row it keeps is not fixed. A window function does the same job anywhere: number each customer's orders from new to old and keep number 1:

from duckdb.frame import row_number

newest_first = row_number().over(partition_by=col("customer"), order_by=[col("placed").desc(), col("id").desc()])
orders.with_columns(n=newest_first).filter(col("n") == 1).select("customer", "id").sort("customer").rows(con)
# [('acme', 3), ('bolt', 5), ('cora', 4)]

The second column in order_by, id, decides between two orders placed on the same day.

Lists and wide tables

baskets = values([("acme", ["pen", "ink"]), ("bolt", ["pad"])], columns=["customer", "items"])
baskets.unnest("items").rows(con)
# [('acme', 'pen'), ('acme', 'ink'), ('bolt', 'pad')]

quarters = values([("acme", 10, 20)], columns=["customer", "q1", "q2"])
quarters.unpivot("q1", "q2", name="quarter", value="sales").rows(con)
# [('acme', 'q1', 10), ('acme', 'q2', 20)]

orders.describe().select("column_name", "min", "max").head(2).rows(con)
# [('id', '1', '5'), ('customer', 'acme', 'cora')]

unnest() gives one row per element of a list column. unpivot() turns columns into rows; the other columns repeat, and name and value name the two new columns. describe() gives one row of statistics per column: min, max, avg, std, quartiles, count and more. It reads every row.

Details

  • with_columns() keeps a replaced column in its place. New columns go at the end.
  • Inside one with_columns() call, every expression sees the columns as they were before it: with_columns(total=col("total") + 1, copy=col("total")) copies the old total. To use the new value, make a second with_columns() call.
  • drop() and rename() of a column that is not there raise ValueError, naming the column.
  • A step that would produce two columns of the same name, such as select("id", "id"), raises ValueError. Names are compared the way DuckDB compares them: Total and total are the same name. The SQL inside sql() is not checked for this; see the Details of Running a plan.
  • These ValueErrors, and the ones from joins below, need the plan's columns, so they come when the plan runs or when you ask for its columns. Building the plan works: bad = orders.drop("missing") succeeds, and bad.rows(con) raises. A wrong kind of argument, such as text in filter(), raises TypeError at once.
  • head() without a number keeps 5 rows.
  • sample(n) gives exactly n rows when there are that many; sample(percent=10) gives about 10 percent. method= picks DuckDB's sampling method by name: "reservoir" is the default with n, "bernoulli" with percent. Passing both n and percent raises TypeError.
  • unnest() leaves out a row whose list is empty or NULL. A NULL inside a list gives a row with NULL.
  • unnest() of two list columns reads them side by side, element by element, and fills the shorter list up with NULL. It does not give every combination.
  • unpivot() leaves out NULL values, so a row with NULL in every column you unpivot disappears. To keep them, write it in SQL with INCLUDE NULLS. For a table quarterly with columns q1 and q2: sql("FROM quarterly UNPIVOT INCLUDE NULLS (sales FOR quarter IN (q1, q2))").
  • plan["customer"] is the plan with only that column, the same as plan.select("customer").

Expressions

An expression is a piece of a query: a column, a value, or a calculation on them. You build one with col() and ordinary Python operators, and use it in filter, select, with_columns, sort and the other methods. .alias(name) names the column it makes.

from duckdb.frame import col, lit

orders.select(
    "id",
    (col("total") * 2).alias("double"),
    (col("total") > 1000).alias("big"),
    col("customer").concat("/", col("region")).alias("label"),
).first(con)
# (1, Decimal('2800.00'), True, 'acme/emea')

The operators are Python's: + - * / // % ** for arithmetic, == != < <= > >= for comparisons, and &, | and ~ for AND, OR and NOT. DuckDB does the arithmetic by its own rules, the same as in SQL, and these differ from Python's:

  • // on whole numbers drops the fraction, rounding toward zero: -5 // 2 is -2, where Python gives -3. On DOUBLE and DECIMAL values, // is plain division: 5.0 // 2.0 is 2.5, where Python gives 2.0.
  • % takes the sign of the left side: -5 % 2 is -1, where Python gives 1.
  • Dividing by zero with / gives inf, or nan for 0 divided by 0, where Python raises ZeroDivisionError. With //, and with % on whole numbers and decimals, the query fails with InvalidInputError.

For Python's rounding and remainder sign, use fn("fdiv", a, b) and fn("fmod", a, b) (see "Any function by name" below), which give a DOUBLE. By zero they give inf and nan, not an error.

Combine conditions with &, | and ~, each part in parentheses: (col("a") > 1) & (col("b") < 9). Python's and, or and not do not work on expressions; using one raises TypeError.

Inside an expression, a string is a value. col("state") == "active" compares with the text active. For the column called active, write col("active"). See How strings are read.

Join text with .concat(). + on two text values fails with an error from DuckDB. If any part is NULL, the whole result is NULL; to treat a missing part as empty text, write col("first").concat(" ", coalesce(col("last"), "")).

NULL

from duckdb.frame import coalesce

scores = values([("a", 3), ("b", None)], columns=["name", "score"])
scores.select(
    "name",
    col("score").is_null().alias("missing"),
    coalesce(col("score"), 0).alias("score_or_0"),
).rows(con)
# [('a', False, 3), ('b', True, 0)]
scores.filter(col("score") == None).count(con)    # 0: in SQL, a comparison with NULL is never true
scores.filter(col("score") != 3).count(con)       # 0: not even !=
scores.filter((col("score") != 3) | col("score").is_null()).count(con)    # 1

NULL is SQL's missing value, and Python gets it as None. A comparison with NULL gives NULL, an unknown answer, and filter() keeps only the rows where the condition is true. So col("score") != 3 drops the row whose score is missing; to keep it, ask for it with .is_null(), as the last line does. Test for NULL with .is_null() and .is_not_null(). coalesce() gives the first of its arguments that is not NULL.

Tests and conversions

orders.filter(col("total").between(500, 1500)).count(con)        # 3
orders.filter(col("region").isin(["emea", "apac"])).count(con)   # 3
orders.filter(col("customer").like("a%")).count(con)             # 2
orders.select(col("total").cast("INTEGER")).head(2).rows(con)    # [(1400,), (320,)]
values([(1.9,)], columns=["x"]).select(col("x").cast("INTEGER")).rows(con)    # [(2,)]: rounded, where int(1.9) is 1

codes = values([("12",), ("x",)], columns=["code"])
codes.select(col("code").try_cast("INTEGER")).rows(con)          # [(12,), (None,)]

between includes both ends. In like, % matches any run of characters and _ any one character; ilike also ignores case. cast fails the query with ConversionError when a value does not convert; try_cast gives NULL instead. A cast to a whole-number type such as INTEGER rounds to the nearest whole number. To drop the fraction, as Python's int() does, use fn("trunc", col("x")).cast("INTEGER").

Choosing a value

from duckdb.frame import when

size = (when(col("total") > 2000).then("large")
        .when(col("total") > 1000).then("medium")
        .otherwise("small"))
orders.select("id", size.alias("size")).rows(con)
# [(1, 'medium'), (2, 'small'), (3, 'large'), (4, 'small'), (5, 'medium')]

This is SQL's CASE. The first condition that is true picks the value. End with .end() instead of .otherwise(...), and rows that match no condition get NULL.

Text, dates, lists and JSON

DuckDB has hundreds of functions, grouped by the kind of value they work on. Say which kind you mean, and that group's functions appear as methods: .str() for text, .dt() for dates and times, .list() for lists and .json() for JSON text. To see a group's methods, run help(col("x").str()): it lists each method with a short description and the DuckDB function it calls, whose page in DuckDB's documentation gives all its arguments.

orders.select(
    col("customer").str().upper(),
    col("placed").dt().month(),
    col("placed").dt().trunc("month"),
).first(con)
# ('ACME', 1, datetime.datetime(2026, 1, 1, 0, 0))

events = values([(["vip", "early"], '{"id": 7}')], columns=["labels", "payload"])
events.select(
    col("labels").list().contains("vip"),
    col("labels").list().sort(),
    col("payload").json().extract("$.id"),
).rows(con)
# [(True, ['early', 'vip'], '7')]

In "$.id", $ stands for the whole JSON value and .id for its field id. extract gives JSON text, so the result is '7', not 7: add .cast("INTEGER") for the number, or use extract_string for text without JSON's quotes. A method's result keeps the methods that fit it, so you can keep chaining:

col("customer").str().lower().trim()           # text gives text, so text methods follow
col("payload").json().keys().contains("id")    # keys() gives a list, so list methods follow

Any function by name

from duckdb.frame import fn

orders.select(
    fn("regexp_extract", col("customer"), "^(..)", 1),
    fn("round", col("total") / 7, precision=1),
).first(con)
# ('ac', 200.0)

fn(name, *arguments) calls any DuckDB function. A keyword argument is passed by name, as SQL's := does: fn("round", x, precision=1) is round(x, precision := 1). That works for every function whose parameters have names, including your own Python functions and macros.

Reaching inside a value

places = values([({"city": "Utrecht", "geo": {"lat": 52.1}}, ["a", "b"])], columns=["address", "tags"])
places.select(
    col("address")["city"],
    col("address")["geo"]["lat"],
    col("tags")[1],
).rows(con)
# [('Utrecht', 52.1, 'a')]

Square brackets reach into a struct field or a map entry by name, and into a list element by position. Positions start at 1, as in SQL. A name in brackets is one name: col("payload")["user.id"] is the field called user.id. On a plan, brackets mean something else: plan["customer"] is the plan with only that column.

Lists and dicts as values

orders.with_columns(tags=lit(["new"]), extra=lit({"source": "web"})).select("tags", "extra").first(con)
# (['new'], {'source': 'web'})

Next to an operator, a plain Python value is fine: col("total") > 1000. On the left of **, % or // it raises TypeError; write lit(2) ** col("x"). Where a method expects a column, wrap a value in lit(). A list becomes a SQL list and a dict a struct.

Small functions for list methods

Some list methods take a function: keep some elements, change each one, or combine them into one value. Write it as a Python lambda:

prices = values([([10.0, -2.0, 5.0],)], columns=["prices"])
prices.select(
    col("prices").list().transform(lambda p: p * 2),
    col("prices").list().filter(lambda p: p > 0),
    col("prices").list().reduce(lambda total, p: total + p),
).rows(con)
# [([20.0, -4.0, 10.0], [10.0, 5.0], 13.0)]

Python calls your function once, while you build the expression, not once per element. It gets a stand-in for an element, and what it returns is a recipe: DuckDB applies that recipe to every element when the query runs. So the function returns an expression, which every operator and method on this page builds, or a plain value such as 1. Anything that depends on the element must be built from expressions. That is why Python's if does not work inside it. Use when() instead:

col("prices").list().transform(lambda p: 0 if p < 0 else p)    # raises TypeError: an expression has no truth value
col("prices").list().transform(lambda p: when(p < 0).then(0).otherwise(p))    # works: SQL decides for each element

Details

  • Column names are matched the way DuckDB matches them, ignoring case: col("TOTAL") finds total.
  • .str(), .dt(), .list() and .json() check and convert nothing in Python; DuckDB checks each call when the query runs. The groups keep the list after each dot short, and let short names mean different things: .list().min() is the smallest element of each list, while .min() is the smallest value over the rows. .json() also has the text methods.
  • isin() takes a list of values, a plan with one column (see Plans inside plans), or an expression that is a list, such as col("x").isin(col("xs")). With a NULL among the values, a Python list and a list expression answer differently when nothing matches. Where x is 5, col("x").isin([1, None]) gives NULL, while col("x").isin(lit([1, None])) gives False. So a filter on ~ of the first drops that row, and on ~ of the second keeps it. Where x is NULL, both give NULL. An empty Python list matches nothing, even a NULL: isin([]) is always False. An empty list expression, isin(lit([])), gives False too, but NULL where x is NULL. A string as the argument raises TypeError: use == for one value.
  • coalesce() is SQL's COALESCE, which is part of SQL's grammar rather than a function, so fn("coalesce", ...) fails with CatalogError.
  • ** is DuckDB's pow and gives a DOUBLE.
  • A tuple names a function in a schema: fn(("main", "my_function"), 1). Keyword arguments come after the positional ones in the SQL.
  • In a list method's function, your parameter's name becomes the name of SQL's lambda variable, so lambda p: ... is lambda p: ... in SQL. Inside it, p hides a column of the same name, as in SQL.
  • The function may return a plain value: lambda x: 1 is fine. Returning anything that is neither an expression nor a plain value raises TypeError.
  • Only plain positional parameters work, since each becomes a SQL variable. A default (lambda x, y=1: ...) would not act as a default in SQL; it would be a second variable, so it raises TypeError, as do *args and keyword-only parameters. A function with no parameters raises TypeError too. That is often a call you forgot to make, as in col("amount") > threshold where you meant threshold().
  • The function's result cannot hold a subquery or an unnest: DuckDB refuses those, with its own message.
  • Any Python function where an expression is expected becomes a SQL lambda. Where DuckDB cannot take a lambda, the query fails when it runs.

Grouping and aggregating

group_by() picks the columns to group by, and agg() says what to compute for each group. The group columns come first in the result. Rows whose group columns hold NULL form one group of their own; they are not dropped.

from duckdb.frame import count_all

by_region = orders.group_by("region").agg(
    col("total").sum().alias("spent"),
    count_all().alias("orders"),
)
by_region.sort("region").rows(con)
# [('amer', Decimal('1470.00'), 2), ('apac', Decimal('900.00'), 1), ('emea', Decimal('4000.00'), 2)]
by_region.filter(col("spent") > 1000).sort("region").rows(con)
# [('amer', Decimal('1470.00'), 2), ('emea', Decimal('4000.00'), 2)]

A filter after agg() works on the groups, like SQL's HAVING. aggregate() does the same in one call. Without group_by=, it gives one row for the whole plan:

orders.aggregate(col("total").mean().alias("average")).rows(con)    # [(1274.0,)]
orders.aggregate(col("total").max(), group_by="customer").sort("customer").rows(con)
# [('acme', Decimal('2600.00')), ('bolt', Decimal('1150.00')), ('cora', Decimal('900.00'))]

To aggregate only some rows, add .where():

orders.aggregate(
    col("total").sum().where(col("region") == "emea").alias("emea"),
    count_all().where(col("total") > 1000).alias("big"),
).rows(con)
# [(Decimal('4000.00'), 3)]

The aggregates are methods on an expression: sum, mean (or avg), min, max, count, median, std, var, quantile(q), mode, first, last, any_value, n_unique, string_agg(separator), array_agg, product, bool_and, bool_or, bit_and, bit_or, arg_min(other), arg_max(other), skewness, kurtosis and entropy. For any other, use fn("name", ...).

arg_max(other) gives the value from the row where other is largest: col("customer").arg_max(col("total")) is 'acme', the customer of the biggest order. arg_min takes the row where it is smallest.

sum, mean, min, max, median and most other aggregates skip NULL values. When every value is NULL, or there are no rows, they give None. For 0 instead, wrap the aggregate in coalesce(): coalesce(col("total").sum(), 0). The exceptions:

  • count and n_unique give 0 when there is nothing to count, and count_all() counts every row, NULL or not.
  • array_agg, first and last keep NULL values: array_agg of None and 3 is [None, 3]. With no rows, array_agg gives None, not an empty list.

Window functions

A window function computes a value for each row from the rows around it, without merging them into groups. Add .over() to any aggregate, or use row_number, rank, dense_rank, ntile, lag, lead, first_value or last_value:

from duckdb.frame import lag, row_number

orders.select(
    "id",
    row_number().over(partition_by=col("region"), order_by=col("total").desc()).alias("rank"),
    col("total").sum().over(order_by=col("placed"), rows=(None, 0)).alias("running"),
    lag(col("total")).over(order_by=col("placed")).alias("previous"),
).sort("id").head(3).rows(con)
# [(1, 2, Decimal('1400.00'), None), (2, 2, Decimal('1720.00'), Decimal('1400.00')), (3, 1, Decimal('4320.00'), Decimal('320.00'))]

partition_by splits the rows into groups that are computed separately, and order_by orders the rows inside each. rows=(start, end) says which rows around the current one count: a negative number is that many rows before it, a positive number that many after, 0 is the current row and None means no limit. So rows=(None, 0) is a running total, and rows=(-2, 0) covers the current row and the two before it. range=(start, end) works the same way, but by the values in order_by instead of by counting rows, in that column's own units: on a DATE column, range=(-30, 0) covers the current row's date and the 30 days before it.

In .over(), give columns with col(). Write partition_by=col("customer"). A plain string, partition_by="customer", raises TypeError: as a text value it would be the same for every row and put all rows in one group. lag(), lead(), first_value() and last_value() work the same way: write lag(col("total")).

Without order_by, an aggregate covers its whole partition: col("total").sum().over(partition_by=col("region")) gives each order its region's total, and a bare .over() gives every row the total of all rows. Without rows= or range=, an aggregate with order_by covers every row up to the current one, and also the rows that tie with it in order_by:

sales = values([(1, 10), (1, 20), (2, 30)], columns=["day", "amount"])
sales.select(
    "day",
    "amount",
    col("amount").sum().over(order_by=col("day")).alias("default"),
    col("amount").sum().over(order_by=[col("day"), col("amount")], rows=(None, 0)).alias("by_row"),
).sort("day", "amount").rows(con)
# [(1, 10, 30, 10), (1, 20, 30, 30), (2, 30, 60, 60)]

The two sales of day 1 tie, so the default counts both on each of them. rows=(None, 0) counts row by row, and the second column in order_by fixes the order of the tied rows.

Details

  • col("x").count() counts the values that are not NULL. count_all() counts rows, like SQL's count(*).
  • n_unique() counts the different values, leaving out NULL.
  • quantile(0.9) interpolates between the two nearest values.
  • .where() works on aggregates, count_all() included. Put it before .over(). On any other function, such as fn("upper", ...), DuckDB refuses the query with InvalidInputError when it runs.
  • .ignore_nulls() makes first_value, last_value, lag and lead skip NULL values: last_value(col("total")).ignore_nulls().over(order_by=col("placed")). On anything that is not a function call it raises TypeError.
  • Passing both rows= and range= raises TypeError.
  • On a TIMESTAMP column, range= with numbers fails with ProgrammingError, and with a timedelta it raises TypeError. Write such a window in SQL with sql_expr(): sql_expr("sum(amount) OVER (ORDER BY ts RANGE BETWEEN INTERVAL 1 DAY PRECEDING AND CURRENT ROW)") sums the amounts of the 24 hours up to each row's time.

Joining and combining plans

customers = values(
    [("acme", "Netherlands"), ("bolt", "United States"), ("dune", "Germany")],
    columns=["customer", "country"],
)
orders.join(customers, on="customer").select("id", "country").sort("id").rows(con)
# [(1, 'Netherlands'), (2, 'United States'), (3, 'Netherlands'), (5, 'United States')]
orders.join(customers, on="customer", how="left").select("id", "country").sort("id").rows(con)
# [(1, 'Netherlands'), (2, 'United States'), (3, 'Netherlands'), (4, None), (5, 'United States')]

on="customer" joins on a column both sides have, and that column appears once in the result. For several columns, pass a list: on=["region", "year"]. how picks the kind of join:

howKeeps
"inner" (the default)Rows that have a match on both sides.
"left", "right"Every row of that side, with NULL where the other side has no match.
"outer" or "full"Every row of both sides.
"semi"The left rows that have a match. No columns are added.
"anti"The left rows that have no match. No columns are added.
"cross"Every combination of rows. No on. .cross(other) does the same.
"positional"The first row of each side together, then the second, and so on, with NULL where one side runs out. No on.
"natural"Joins on every column name the two sides share. No on. See the Details below.
"asof"For each left row, the nearest right row that meets a condition with >=, >, <= or <. Left rows without one are left out.

A join gives one row for every pair of rows that match. So a key that appears twice on each side gives four rows, and a NULL key matches nothing, not even another NULL:

left = values([("a", 1), ("a", 2), (None, 3)], columns=["key", "l"])
right = values([("a", "x"), ("a", "y"), (None, "z")], columns=["key", "r"])
left.join(right, on="key").count(con)    # 4

For any other condition, pass a function of the two sides:

bands = values([(0, 1000, "small"), (1000, 100000, "large")], columns=["low", "high", "band"])
orders.join(
    bands,
    on=lambda order, band: (order["total"] >= band["low"]) & (order["total"] < band["high"]),
).select("id", "band").sort("id").rows(con)
# [(1, 'large'), (2, 'small'), (3, 'large'), (4, 'small'), (5, 'large')]

The function's first argument is the left side, the plan you call join on, and the second is the right side. The names are yours to choose. order["total"] is the column total of that side. The function runs once, when you build the join, and must return an expression.

When both sides have a column of the same name, pass suffix= and the right side's copy is renamed. Without it, the join raises ValueError, since the result would have two columns called total. A column named in on="..." is merged into one, so it needs no suffix.

refunds = values([(3, 200)], columns=["id", "total"])
orders.join(refunds, on="id", how="left", suffix="_refund").select("id", "total", "total_refund").sort("id").head(3).rows(con)
# [(1, Decimal('1400.00'), None), (2, Decimal('320.00'), None), (3, Decimal('2600.00'), 200)]

Combining the rows of two plans

early = orders.filter(col("placed") < date(2026, 2, 1)).select("customer")
later = orders.filter(col("placed") >= date(2026, 2, 1)).select("customer")

early.union(later).count(con)                              # 5: union keeps duplicates
early.union(later, all=False).sort("customer").rows(con)   # [('acme',), ('bolt',), ('cora',)]
early.intersect(later).sort("customer").rows(con)          # [('acme',), ('bolt',)]
later.except_(early).rows(con)                             # [('cora',)]

union() matches columns by position, and union_by_name() by name, with NULL where one side lacks a column. Both keep duplicates unless you pass all=False. intersect() keeps the rows found in both plans, and except_() the rows of the first that are not in the second. Both remove duplicates. except_ ends in an underscore because except is a Python keyword.

Details

  • After the join there is one plan with one set of columns. Refer to them by name with col().
  • In a join condition, a struct field is a second bracket: order["shipping"]["zip"].
  • With a condition function, both sides keep their own key columns, so suffix= renames the right one too: on=lambda a, b: a["id"] == b["id"], suffix="_r" gives id and id_r.
  • The renamed column must not clash either; if it does, the join raises ValueError. Two names that differ only in case count as the same name.
  • how="asof" takes a condition function with one inequality, and optionally == conditions joined to it with &. With a table of exchange rates, on=lambda o, r: o["placed"] >= r["since"] gives each order the latest rate that started on or before its date.
  • how="natural" raises ValueError for the shared columns unless you pass suffix=, and then keeps both copies of them. An inner join with on= the shared names gives the same rows with one copy.
  • An unknown how raises ValueError. A join that needs on but has none raises TypeError, and so do an on given to a cross, positional or natural join and a condition function that returns something other than an expression.
  • For type annotations, the sides are Side objects: def condition(left: Side, right: Side) -> Expr, with Side and Expr imported from duckdb.frame.

Transactions

con.run("CREATE TABLE daily (day DATE, total DECIMAL(10,2))")
with con.transaction():
    orders.group_by("placed").agg(col("total").sum()).insert_into(con, "daily")
    con.run("DELETE FROM daily WHERE total < 500")
table("daily").count(con)    # 4

The with block is one transaction. DuckDB commits it when the block ends, and rolls it back if an exception leaves the block, Ctrl‑C included. An exception you catch inside the block undoes nothing, except that a DuckDB error from a statement that ran, such as a ConversionError or a missing table, spoils the transaction: later statements in it fail with TransactionError, and nothing in it is saved, without an error when the block ends. A ParserError, or an error found while only looking up a plan's columns, leaves it working. A file written inside the block is not undone. Close any reader or iter_rows iterator before the block ends: while one is open, the block can neither commit nor roll back, and the connection stays inside the unfinished transaction. Plans and statements inside run on the connection as usual.

try:
    with con.transaction():
        con.run("DELETE FROM daily")
        raise RuntimeError("changed my mind")
except RuntimeError:
    pass
table("daily").count(con)    # 4: the DELETE was rolled back

Stopping a query

Press Ctrl‑C while a query runs, and DuckDB stops it and Python raises KeyboardInterrupt, unless the query is calling a Python function of yours: then it fails with InvalidInputError (see Python Functions). From another thread, con.interrupt() stops whatever that connection is running; the query then fails with InterruptError. Ctrl‑C also works while to_arrow, to_polars or a reader wait for the first rows of a big sort or aggregate.

Details

  • While rows are still to come from iter_rows, the connection is busy, and another query on it raises OperationalError. A small result may already have arrived in full, so the error does not always show. Finish the loop, or leave it with break when the loop made the iterator itself. If you kept the iterator in a variable, call its close(), or use with contextlib.closing(plan.iter_rows(con)) as rows:.
  • A sql() plan can have two columns of the same name, as in sql("SELECT 1 AS a, 2 AS a"). rows() gives both values, (1, 2), but to_dicts() gives {'a': 2} and to_numpy() keeps only the array of the last a, without an error. to_pandas() renames the second to a_1, and to_polars() raises DuplicateError. Give each column its own name in the SQL.
  • A plan runs only on a duckdb.frame connection. Given a duckdb.dbapi connection, it raises TypeError; see Writing SQL yourself.
  • On a closed connection, running a plan raises InterfaceError. The plan itself is not affected.
  • show(con, limit=3) shows 3 rows and adds a line saying when there are more.

numpy arrays and NULL

In to_numpy, a column holding NULLs comes back as a numpy masked array, whose mask is True where the value is NULL. A column without NULLs is a plain array.

import numpy as np

x = values([(1.5,), (None,), (3.0,)], columns=["x"]).to_numpy(con)["x"]
filled = np.ma.filled(x, 0.0)    # array([1.5, 0. , 3. ]): NULL replaced by 0.0
missing = np.ma.getmaskarray(x)  # array([False,  True, False]): where x was NULL

For PyTorch or TensorFlow, start from to_numpy: torch.from_numpy(filled) or tf.convert_to_tensor(filled). Decide first what a NULL becomes, as above. Both libraries take a masked array's values and drop its mask, so a NULL would quietly turn into whatever value happens to sit under it. Keep the mask as a tensor of its own if you need it. Details: polars

  • Errors from DuckDB raise DuckDB's own error classes. What polars itself refuses is different: repeated column names raise polars' DuplicateError, and a type polars does not have, such as INTERVAL or a UNION, raises NotSupportedError from duckdb.exceptions. to_arrow handles both.
  • to_polars keeps DuckDB's batches as the DataFrame's pieces in memory. Call rechunk() on the result if you need each column in one piece.
  • For a LazyFrame, DuckDB applies these parts of a polars filter: a comparison of a column with a value of the column's own type, is_between, is_in with no null in the list, the null checks, and &, | and ~ of those, on boolean, integer, float, string, date and timestamp columns. Strings are compared byte by byte, as polars does. polars applies every other part, and every filter on other column types, to the rows DuckDB returns.
  • A LazyFrame's column names are the plan's. A repeated name raises DuplicateError when you call to_polars, and names that differ only in case stay separate, as in polars.
  • The column types are read when you make the LazyFrame, so a plan polars cannot hold fails then, and so does a plan that reads a registered stream, with InvalidInputError, leaving the stream used up. If the plan's columns change later, because a table changed or a setting such as TimeZone did, collect() fails: make a new LazyFrame.
  • A connection runs one query at a time, and polars reads all the inputs of one query at once. So a polars query that combines two LazyFrames of one connection, or one LazyFrame filtered two different ways, fails with a "Resource In Use" error. Give each its own connection, such as one from con.duplicate().
  • A LazyFrame used twice in the same way in one query, as in a self-join, is read once. polars 2.0's streaming engine, its default there, reads it once per use instead: collect with engine="in-memory", or call cache() on the LazyFrame first, which reads it once but leaves the filter and the column choice to polars.
  • When a collect() fails in DuckDB, polars 2.0 raises DuckDB's own error class. Older versions raise a polars ComputeError that carries DuckDB's message.
  • A LazyFrame holds on to its connection, so Python does not free the connection while the LazyFrame exists.

Details: Arrow

  • A reader hands you batches as DuckDB produces them, each with at most batch_size rows: 131072 unless you say otherwise. batch_size must be positive, or it raises InvalidInputError.
  • While a reader is open, its query keeps the connection busy: another query there raises OperationalError. Read the reader to the end, or call close() on it. to_arrow reads to the end for you.
  • Closing the connection ends an open reader: the next read raises OSError with "result is closed". Close readers you do not read to the end.
  • If reading from a reader fails, pyarrow raises its own error, an OSError, with DuckDB's message.
  • Each time an Arrow library reads an attached plan, the plan runs again, and each such stream can be read once, from start to end.
  • By default, HUGEINT becomes decimal128 and UUID becomes text. After con.run("SET arrow_lossless_conversion = true"), both use Arrow extension types instead.

Saving results

large = orders.filter(col("total") > 1000)

large.create(con, "large_orders")                  # 3: the number of rows written
large.create(con, "large_orders", replace=True)    # 3: replaces the table
large.create(con, "scratch", temporary=True)       # 3: gone when the connection closes
large.insert_into(con, "large_orders")             # 3: added to the table

DuckDB writes the rows itself; they do not pass through Python. create() makes a new table and insert_into() adds to one that exists. Both return the number of rows written.

The database on this page is in memory, so every table in it, not only the temporary one, is gone when its last connection closes. In a database file, the tables stay, and only a temporary table is gone when the connection closes.

insert_into() matches columns by position, not by name, as SQL's INSERT does. A plan with region, customer put into a table with customer, region stores each region as a customer, without an error. Select the columns in the table's order first.

# [(5, ['by_region/region=amer/data_0.parquet', 'by_region/region=apac/data_0.parquet', 'by_region/region=emea/data_0.parquet'])]

partition_by= writes one folder for each value. When the folder you name is not empty, the write raises IOError: pass overwrite=True to replace what is in it, or append=True to add new files next to the old ones. A single file has no such choice: with append=True it is still replaced. Each method returns the rows COPY returns: the row count; the row count and the file names, with return_files=True; or one row of figures per file, with return_stats=True.

Details

  • An option DuckDB does not know raises NotSupportedError, naming it. An option name that is not a plain word raises ValueError.
  • Option values are written into the COPY statement itself, so an option cannot be a param(): that raises TypeError. A param() inside the plan is fine; pass parameters= as usual.
  • create() on a table that exists raises CatalogError, unless you pass replace=True. A tuple names a table in a schema: create(con, ("shop", "daily")).
  • For other statements, use SQL: sql("EXPORT DATABASE 'backup' (FORMAT parquet)").rows(con), or con.run("COPY FROM DATABASE a TO b"). con.run() returns the number of rows a statement changed.

Querying Python data

con.register(name, data) makes Python data readable as a table called name. Here the pandas DataFrame targets, registered in Where a plan starts, is joined to the orders:

spent = orders.group_by("region").agg(col("total").sum().alias("spent"))
spent.join(table("targets"), on="region").filter(col("spent") >= col("target")).rows(con)
# [('emea', Decimal('4000.00'), 3000)]

polars, pyarrow and numpy data work the same way; each example needs only its own library:

import polars as pl

table("visits").count(con)                           # 2
import pyarrow as pa

con.register("prices", pa.table({"sku": ["a", "b"], "price": [9.5, 3.0]}))
table("prices").filter(col("price") > 5).rows(con)    # [('a', 9.5)]
import numpy as np

con.unregister("readings")

DuckDB reads the data where it is: nothing is copied into the database, and a query reads only the columns it uses. A NaN in numpy or pandas data is read as NULL; in Arrow and polars data it stays NaN. It reads the data again for every query, so a change you make to that object, as with df.loc[...] = ..., shows in the next query. A new object under the same variable name, as after df = df.assign(...), does not: register it again. Several threads can share the reading, and the rows keep their order. Anything else, such as a plain list of numbers, raises TypeError when you register it.

A registered name works like a table name on every connection to the same database, such as one from con.duplicate(). Case does not matter: register("Targets", df) answers to targets. A real table or view of the same name comes first, and a file name still reads the file. Registering a name again replaces the data. con.unregister(name) removes it, and raises InvalidInputError if nothing has that name.

Data you can read only once

import pyarrow as pa

con.register("once", pa.table({"n": [1, 2, 3]}).to_reader())
table("once").create(con, "kept")    # 3: now a table you can query as often as you like
table("once").count(con)             # raises InvalidInputError: the reader has been read already

A pyarrow RecordBatchReader and an Arrow stream capsule (the raw Arrow stream object some libraries hand around) are streams, so DuckDB can read them only once. A second query fails with InvalidInputError and says why. To read the data again, make a new reader from where it came from and register that, as in con.register("once", pa.table(...).to_reader()). Registering the used-up reader again does not rewind it: queries then give no rows, without an error. Or load the data into a table on its first read, as above.

One plan may read a stream more than once through table("once") steps, as in table("once").join(table("once"), on="n"): DuckDB still reads it only once. A stream named twice inside SQL text, as in sql("SELECT * FROM once a JOIN once b USING (n)"), or once in SQL and once through table(), fails with InvalidInputError. For such queries, load the data into a table first.

Details: pandas

  • Each column is read by its own dtype. A column backed by numpy is read without pyarrow. A column backed by pyarrow, such as a string column when pyarrow is installed, is read as Arrow data and gets the type any Arrow data of that kind gets. pandas' nullable dtypes, such as Int64, give NULL where pandas has a missing value.
  • For an object column, DuckDB looks at up to 1000 values spread over the column to choose a type. If they are of different kinds, such as numbers and text, the column is read as text. If a value elsewhere in the column does not fit the chosen type, the query fails with InvalidInputError.
  • A timestamp keeps its own unit, down to nanoseconds, and whether it has a time zone: in a timestamp column, and as a Python, pandas or numpy value in an object column alike.
  • A timestamp DuckDB cannot hold as an ordinary point in time, such as pandas' Timestamp.max, makes the query fail with InvalidInputError. It is not read as infinity.
  • If the values DuckDB looks at in an object column include timestamps both with and without a time zone, the column is read as text. If only a value elsewhere is of the other kind, the query fails with InvalidInputError, because reading it would mean guessing a time zone.
  • A categorical column of strings becomes an ENUM. Any other categorical is read as its categories would be on their own, so categories of two kinds give text. A period column makes the query fail with InvalidInputError.

Details: polars

  • A DataFrame is read in pieces, so several threads can share the work.
  • A LazyFrame is computed again for each query, so each query sees the data as it is then. DuckDB passes simple filters to polars: a comparison of a column with a value, a range test, IN, the null checks, and AND, OR and NOT of those, on boolean, integer, float, string, decimal, date, time and timestamp-without-time-zone columns.
  • polars cannot give a column of Python objects (pl.Object) as Arrow data. A DataFrame with one raises TypeError when you register it; a LazyFrame with one makes the query fail with InvalidInputError.

Details: pyarrow

  • A Table is read in pieces, so several threads can share the work.
  • For a Dataset, DuckDB passes these filters to the dataset, which then reads only the files and parts of files it needs: a comparison of a column with a value, a range test, IN, the null checks, and AND, OR and NOT of those, on boolean, integer, float, string, date and timestamp-without-time-zone columns. DuckDB applies every other filter itself.
  • A Scanner keeps its own filter and columns, and is read in full each time.

Details: numpy

  • A masked array's mask marks the NULLs.
  • Fixed-width U strings become VARCHAR and S bytes become BLOB. A datetime64 of days, weeks, months or years becomes DATE. A finer one becomes a TIMESTAMP in seconds, milliseconds, microseconds or nanoseconds, whichever matches; hours and minutes become seconds. timedelta64 becomes INTERVAL, except in months or years, which have no fixed length and raise TypeError.
  • A dtype DuckDB has no type for, such as complex numbers, raises TypeError when you register it.
  • All arrays of a dict, list or tuple must have the same length, or register raises ValueError.

Looking at a plan

plan = orders.filter(col("region") == "emea").select("id", "total")

plan.columns(con)     # ['id', 'total']
plan.types(con)       # ['INTEGER', 'DECIMAL(8,2)']
plan.schema(con)      # [('id', 'INTEGER'), ('total', 'DECIMAL(8,2)')]
print(plan.render())
WITH "_s0" AS (
SELECT * FROM "orders"
),
"_s1" AS (
SELECT * FROM "_s0" WHERE ("region" = 'emea')
)
SELECT "id", "total" FROM "_s1"
sql_text, sent = plan.render_parameterized(con)
sent                     # ['emea']
print(plan.explain(con)) # how DuckDB will run the query, drawn as boxes

columns, types and schema give the result's column names, their types, or both as pairs. render() gives the SQL with the values written in, for you to read; it needs no connection. render_parameterized(con) gives what is really sent to DuckDB: the SQL with $1, $2 placeholders, and the values in order. None of these fetch rows.

explain(con) shows the steps DuckDB plans to take, such as reading a table with a filter, without running the query. A row count with ~ in front is DuckDB's guess. explain(con, analyze=True) does run the query, and shows the real row count and the time of each step.

Details

  • Without a connection, only a plan that starts from values() can list its columns. Any other plan raises NeedsConnection, a kind of ValueError. For types() without a connection, every values() column needs a type.
  • render() without a connection does not check names, and a column that with_columns replaced moves to the end. render(con) keeps it in place, as running the plan does.
  • A join with suffix= cannot render without a connection, because which columns get renamed depends on both sides: render() raises NeedsConnection. Printing the plan still works and says so.
  • In render(), a param() shows as NULL, so running that SQL somewhere else quietly runs the query without its values. render_parameterized(con, parameters={...}) gives a placeholder and the value instead; every param() needs a value there.

Plans inside plans

A plan can stand in for a value inside an expression:

average = orders.aggregate(col("total").mean())
orders.filter(col("total") > average.scalar()).select("id").rows(con)    # [(1,), (3,)]

acme = orders.filter(col("customer") == "acme").select("region")
orders.filter(col("region").isin(acme)).select("id").rows(con)           # [(1,), (3,)]
orders.filter(~col("region").isin(acme)).select("id").rows(con)          # [(2,), (4,), (5,)]

scalar() makes an expression from a plan with one column, to use as a single value inside another plan. It runs nothing by itself. When the outer plan runs, more than one row makes it fail with InvalidInputError, and no rows give NULL. To get the value in Python, run the plan: average.first(con)[0] is 1274.0. isin() takes a plan with one column and any number of rows. DuckDB computes the inner plan once, however often you use it.

The inner plan cannot refer to the row of the outer one. For that kind of question, use a join instead, or write the query in SQL (see Writing SQL yourself):

orders.join(acme, on="region", how="semi").count(con)    # 2: SQL's EXISTS

averages = orders.group_by("customer").agg(col("total").mean().alias("customer_average"))
orders.join(averages, on="customer").filter(col("total") > col("customer_average")).select("id").sort("id").rows(con)
# [(3,), (5,)]: each order above its customer's average

Reusing plans

A plan holds no connection, so you can build it once and run it wherever its tables exist. Each connection reads its own tables, so the same plan works on both, even when their columns differ. Closing a connection does not affect the plans you ran on it.

report = table("orders").filter(col("total") > 1000).select("id")
other = frame.connect()
other.run("CREATE TABLE orders AS SELECT 7 AS id, 5000 AS total")

report.rows(con)      # [(1,), (3,), (5,)]
report.rows(other)    # [(7,)]

The same steps on different data

To apply the same steps to different starting points, write a function that takes a plan:

def recent(plan):
    return plan.filter(col("placed") >= date(2026, 2, 1)).select("id", "total")

recent(table("orders")).count(con)        # 3
recent(read_csv("orders.csv")).count(con) # 3
recent(values([(9, date(2026, 5, 1), 10)], columns=["id", "placed", "total"])).rows(con)    # [(9, 10)]

As a macro

A macro is a piece of SQL stored in the database under a name, so SQL can call it like a function. A plan's SQL can be the body of a macro:

body = sql('SELECT unnest("ids") AS id').filter(col("id") > 2)
con.run("CREATE MACRO big_ids(ids) AS TABLE " + body.render())
sql("SELECT * FROM big_ids([1, 3, 9])").rows(con)    # [(3,), (9,)]

Or let the connection write the statement. An expression makes a macro that returns a value, and a plan one that returns a table. Parameters are names, or (name, default) pairs, and col(name) in the body refers to one:

con.create_macro("add_up", ["a", ("b", 1)], col("a") + col("b"))
con.create_macro("orders_over", ["floor"], table("orders").filter(col("total") > col("floor")).select("id"))
sql("SELECT add_up(2) AS three, * FROM orders_over(2000)").rows(con)    # [(3, 3)]

DuckDB checks the body when you create the macro: a table or column it cannot find makes CREATE MACRO or create_macro fail. Problems that depend on the arguments' types show at the first call. A macro gets its values from its arguments, never from param(): in create_macro a param() raises TypeError, and through render() it would quietly become NULL. Macros & Extensions has more on macros.

How strings are read

A Python string you pass to a method means one thing, and each argument always reads it the same way. These are the ones you meet most:

  • A column name in the methods that choose columns: select, sort, group_by, aggregate, distinct(on=...), drop, unnest, unpivot, join(on=...), star(exclude=...) and plan["name"]. In with_columns(copy="total"), the string is the column to copy.
  • A new name where you name something: .alias(), the new names in rename(), unpivot(name=..., value=...), the columns of values(), param() and the parameters of a macro.
  • A value inside an expression: col("state") == "active" compares with the text active. The same goes for lit(), isin(), like(), between(), concat(), .then() and the arguments of functions such as .str().replace("a", "b").
  • SQL text in sql(), sql_expr(), con.run() and type names such as cast("INTEGER"). It is used exactly as you write it.

A name is always one name. It is never split at a dot, and where a list of names is allowed, a single string is one name, not a list of its letters: star(exclude="placed") leaves out the column placed. A table or function name is one name too, and a tuple adds its schema (see Values, names and SQL text).

from duckdb.frame import lag, star

orders.select(star(exclude="placed")).columns(con)    # ['id', 'customer', 'region', 'total']
orders.select(lag("total").over(order_by=col("placed")))
# TypeError: lag takes an expression, not the string 'total'; name a column with col() or write SQL with sql_expr()

Where a string makes no sense, it raises TypeError, and the message says what to write instead:

  • A condition, in filter(), when() and .where(), is an expression: col("paid") for a column, or sql_expr("total > 100") for SQL. A plain True raises too; write lit(True).
  • The columns of .over(), and the column that lag(), lead(), first_value() and last_value() read, are expressions: partition_by=col("region"), lag(col("total")). For a fixed text, write lag(lit("x")).
  • Where a method takes a list of values, a single string is not such a list: the rows of values(), isin(), and parameters of con.run() and of a plan. For one value, put it in a list: con.run(sql, ["x"]).

To annotate your own functions that pass arguments on to these methods, import the types from duckdb.frame.typing. Each type names how its argument reads a string: ColumnOrExpr is a column name or an expression, ValueOrExpr a value or an expression, Exprs one expression or a list of them, and SqlText SQL.

Values, names and SQL text

Text, bytes, lists, tuples and dicts that you put in a plan, in an expression or in values(), are never pasted into the SQL that runs. They are sent to DuckDB separately, as parameters, so a value cannot change what the query does. Dates, times, intervals, decimals and UUIDs are sent the same way, so they arrive exactly as they are, with the limits listed under "what is refused" on DB-API 2.0: for example a timestamp with nanoseconds is refused. A Decimal wider than 38 digits raises TypeError here. Numbers, booleans and None are written into the SQL; a Python float is written as a DOUBLE, never a DECIMAL. A numpy bool, integer or float, such as np.int64(3) or np.float32(0.5), counts as the Python value its .item() gives, and so does one passed to a plan with parameters=. A DB-API cursor's execute() does not convert them: there np.int64 is refused (see DB-API 2.0). A value an expression cannot hold, such as a Fraction, raises TypeError, with == and != as with every other operator.

name = "x' OR '1'='1"
orders.filter(col("customer") == name).count(con)    # 0: the text is compared as it is

Names are quoted, so a name cannot turn into SQL either:

  • A string you give col, table, select, drop, create or any other method is one name. It is never split at a dot: col("user.id") is the column called user.id, and table("a.b") the table called a.b.
  • For a name with a schema, pass a tuple: table(("main", "orders")), plan.create(con, ("shop", "daily")), con.create_macro(("util", "rate_of"), ...). col() takes only a string. A field inside a struct column is a bracket, col("address")["city"], and a column of one side of a join is order["id"], inside the join's condition.
  • DuckDB compares names ignoring the case of the letters A to Z: col("TOTAL") finds total, and two columns whose names differ only in case count as one name twice.
  • Function names are written as SQL writes them, without quotes unless the name is a SQL keyword or has unusual characters: fn("sum", ...) gives sum(...), fn("range", ...) gives "range"(...).
runs whatever the name holds
sql(f"SELECT * FROM {name}")
one quoted name
table(name)

sql() and sql_expr() take SQL exactly as you write it. Never build either from text you do not trust.

Writing SQL yourself

sql() makes a plan from a whole query, as in Where a plan starts. For a piece of an expression, sql_expr() takes SQL text, including a whole condition for filter:

from duckdb.frame import sql_expr

orders.filter(col("placed") > sql_expr("DATE '2026-01-01' + INTERVAL 30 DAY")).count(con)    # 3
orders.filter(sql_expr("region = 'emea' AND total > 1000")).count(con)                    # 2

Write in SQL what plans cannot say: a subquery that refers to the outer row, a recursive query, or a PIVOT. The result is a plan like any other, so you can carry on with methods:

sql("SELECT id FROM orders o WHERE total > (SELECT avg(total) FROM orders WHERE customer = o.customer)").sort("id").rows(con)
# [(3,), (5,)]

countdown = sql("WITH RECURSIVE n(i) AS (SELECT 3 UNION ALL SELECT i - 1 FROM n WHERE i > 1) SELECT i FROM n")
countdown.rows(con)    # [(3,), (2,), (1,)]

pivoted = sql("PIVOT orders ON region IN ('emea', 'amer', 'apac') USING sum(total) GROUP BY customer")
pivoted.sort("customer").rows(con)
# [('acme', Decimal('4000.00'), None, None), ('bolt', None, Decimal('1470.00'), None), ('cora', None, None, Decimal('900.00'))]

Give PIVOT the list of values that become columns, with IN (...), as above.

For cursors and execute(), use duckdb.dbapi, Python's standard database interface. A plan does not run on its connections, but a cursor can run the plan's SQL and values: query, sent = plan.render_parameterized(parameters={...}), then cursor.execute(query, sent), as in this example. Use render_parameterized rather than render() here: render() writes a param() as NULL, so the query would quietly run without its values. A plan whose SQL depends on its tables' columns, such as a join with suffix=, cannot render without a frame connection and raises NeedsConnection. Rename the clashing columns before the join instead, or pass a frame connection to the same data: render_parameterized(con, parameters={...}). For a database file, render with the frame connection and close it before you open the DB-API connection, since a program can open a file only once at a time. Pass the connection whenever you have one: without it, the SQL can differ from what the plan runs, for example a column that with_columns replaced moves to the end.
