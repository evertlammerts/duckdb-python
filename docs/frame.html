Building queries

A plan is a query you build a step at a time. An expression is a piece of one. A connection is where a plan runs. Plans and expressions are plain values: build them anywhere, run them on any connection.

Start here

import duckdb
from duckdb import col, table

con = duckdb.connect("shop.db")
orders = table("orders")

orders.filter(col("total") > 1000).select("customer", "total").rows(con)

orders is a plan. Each verb on it returns a new plan and leaves the old one alone. Nothing runs until a method takes a connection; rows(con) is that method here. Put the plan on the connection once and the methods take no argument:

orders.on(con).rows()
orders.on(con).first()

To see rows while you work:

>>> orders.head(3).show(con)
┌─────────┬──────────┬─────────┬────────────┬──────────────┬─────────┐
│ id      │ customer │ region  │ placed     │ total        │ state   │
│ INTEGER │ VARCHAR  │ VARCHAR │ DATE       │ DECIMAL(6,2) │ VARCHAR │
├─────────┼──────────┼─────────┼────────────┼──────────────┼─────────┤
│ 1       │ acme     │ emea    │ 2026-02-01 │ 1400.00      │ active  │
│ 2       │ bolt     │ amer    │ 2026-01-11 │ 320.00       │ active  │
│ 3       │ acme     │ emea    │ 2026-03-02 │ 2600.00      │ closed  │
└─────────┴──────────┴─────────┴────────────┴──────────────┴─────────┘

A plan prints as its SQL: >>> orders gives <Frame SELECT * FROM "orders">.

Where a plan starts

table(name)
A table or view. The name may be qualified: table("main.orders"). A file name reads the file: table("orders.csv"), table("data/*.parquet").
read_csv(path, **options) / read_parquet / read_json
A file, a list of files or a glob through the engine's reader, with its options under their SQL names: read_csv("orders.csv", header=True, delim="|").
table_function(name, *args, **named)
Any table function: table_function("range", 10), table_function("read_xlsx", "book.xlsx", sheet="Q1") once its extension is loaded.
sql(text)
Any query, as SQL. Carry on from it with verbs.
values(rows, columns)
Rows given here, in memory. Every value is bound when the plan runs. A column given as (name, type) is cast to that type.
from duckdb import table, sql, values

orders  = table("orders")
emea    = sql("SELECT * FROM orders WHERE region = 'emea'")
labels  = values([("nl", "Netherlands"), ("be", "Belgium")], columns=["code", "label"])
recent  = emea.filter(col("placed") >= "2026-01-01")

values needs no table, so a plan can be built and tried before any database exists. Give columns as (name, type) pairs when there are no rows to take the types from.

files

A reader is a table function, and its arguments are spelled the way SQL spells them: a string, number or date is bound when the plan runs; a list is a list; a dict is a struct. The engine works the columns out from the arguments, so a param() cannot be one.

orders = read_csv("orders.csv", header=True, dateformat="%d/%m/%Y")
year   = read_parquet(["jan.parquet", "feb.parquet"], union_by_name=True)
events = read_json("events/*.json", filename=True)
typed  = read_csv("raw.csv", columns={"id": "INTEGER", "note": "VARCHAR"})

orders.columns(con)                 # the engine reads the file's head to answer
orders.filter(col("total") > 1000).create(con, "big_orders")   # loading a file is a plan with a sink

Loading into a table that exists is read_csv(...).insert_into(con, "orders"), or the statement itself: con.run("COPY orders FROM 'orders.csv' (HEADER)").

Building it up

Every verb returns a new plan. Branch from any point:

recent = orders.filter(col("placed") >= "2026-01-01")

by_customer = recent.group_by("customer").agg(col("total").sum().alias("spent"))
biggest     = recent.sort(col("total").desc()).head(10)

rows and columns

VerbDoes
.filter(pred)keep the rows where pred holds
.select(*cols)keep these columns or expressions, in this order
.with_columns(**cols)add columns; a name already present is replaced in place
.drop(*names) / .rename(old=new)remove or rename
.sort(*cols)order by. Use .desc(), .nulls_last() on a column
.limit(n, offset) / .head(n) / .offset(n)fewer rows
.distinct(on=…)drop duplicate rows, or duplicates of on
.sample(n) / .sample(percent=)a random subset; seed= makes it repeatable

In select, with_columns, sort and distinct a bare string names a column: orders.select("customer", "total"). filter takes only an expression; a condition written as SQL is filter(sql_expr(...)).

grouping

orders.group_by("region").agg(
    col("total").sum().alias("spent"),
    count_all().alias("orders"),
)

# a HAVING clause is a filter after the aggregate
orders.group_by("region").agg(col("total").sum().alias("spent")).filter(col("spent") > 1000)

Group keys come first in the output. .aggregate(*aggs, group_by=…) does the same in one call, and with no keys aggregates the whole plan to one row.

joining

orders.join(customers, on="customer_id")                          # same name on both sides
orders.join(customers, on=["region", "year"])                     # several
orders.join(customers, on=col("l.customer") == col("r.name"))     # any condition

orders.join(refunds, on=col("l.id") == col("r.order_id"), how="left")

Inside on, the left side is l and the right side is r. how is inner (the default), left, right, outer (or full), semi, anti, cross, positional, natural or asof. Semi and anti keep the left rows that do or do not have a match, and add no columns. .cross(other) is every combination.

When both sides have a column of the same name, pass suffix and the right side's copy is renamed: orders.join(orders, on=…, suffix="_r") gives total and total_r. Without a suffix the join is refused, since the result would have two columns called total. Columns joined with on="name" are merged and do not need one.

combining

a.union(b)                  # rows of both, by position; all=False drops duplicates
a.union_by_name(b)          # by column name
a.intersect(b)              # rows in both
a.except_(b)                # rows in a and not in b

reshaping

orders.unnest("tags")                                       # one row per element
quarters.unpivot("q1", "q2", "q3", name="quarter", value="sales")   # columns to rows
orders.describe()                                            # statistics per column, as a plan

Expressions

An expression is a piece of a query: a column, a value, or a computation over them. Build them with col and ordinary Python operators.

from duckdb import col, lit

col("age") >= 18
100 - col("discount")
(col("a") > 1) & (col("b") < 9)
~col("cancelled")
col("first").concat(" ", col("last"))

Combine with &, | and ~, in parentheses. Python's and, or and not do not work on expressions, and using one raises TypeError.

Inside an expression, a bare string is a value. col("state") == "active" compares with the text active. For a column, write col("active").

Text joins with .concat(). + on two text columns is an error.

null

col("v").is_null()       # True where v is NULL
col("v") == None         # NULL, never True: SQL's rule
coalesce(col("v"), 0)   # the first non-NULL

tests and casts

col("total").between(100, 500)
col("region").isin(["emea", "amer"])
col("x").isin(col("xs"))                # ("x" IN "xs"): a list held in another column
col("sku").like("AB-%")               # % any run, _ any one character; .ilike ignores case
col("amount").cast("DECIMAL(10,2)")
col("amount").try_cast("INTEGER")       # NULL where the cast would fail

isin takes a list of values, a plan with one column (Plans inside plans), or an expression of list type. The last is the engine's IN over a list: 2 IN [1, 2, 3] is true, 5 IN [1, NULL] is false and NULL IN [1, 2] is NULL.

function namespaces

The engine's functions come in families, entered by saying how the expression is meant: .str() for text, .dt() for dates and times, .list() for lists, .json() for JSON documents. The entry is the same expression with that family's methods in scope; nothing is checked or cast, and the engine still judges every call.

col("customer").str().upper()
col("placed").dt().trunc("month")
col("tags").list().contains("vip")
col("payload").json().extract("$.id")

col("name").str().lower().trim()                # a text result keeps the text methods in scope
col("payload").json().keys().contains("id")   # keys() gives a list, so list methods follow

What a method returns is scoped by the engine's own return type for it, so chains keep going without a second entry. The families exist for two reasons: without them every engine function would be a method on every expression, several hundred names after each dot; and the short names could not exist, since .list().min() can mean list_min only while .min() still means the aggregate. Which functions sit where is declared in one table, scripts/func_namespaces.toml, checked against the engine's catalog on every build.

Anything else: fn("regexp_extract", col("path"), r"/(\d+)/", 1) calls any function by name.

choosing a value

tier = (when(col("total") > 2000).then("big")
        .when(col("total") > 500).then("mid")
        .otherwise("small"))

orders.with_columns(tier=tier)

A list value needs lit: with_columns(tags=lit(["a", "b"])). A dict is a struct: lit({"city": "NYC", "zip": 10001}). Both are bound as one value.

aggregates and windows

col("total").sum()          col("total").mean()       col("customer").n_unique()
col("total").quantile(0.9)  col("tag").string_agg(", ")  count_all()

# aggregate only some rows
col("total").sum().where(col("state") == "active")

# any aggregate becomes a window function with .over()
row_number().over(partition_by=col("region"), order_by=col("total").desc())
col("total").sum().over(order_by=col("placed"), rows=(None, 0))      # running total
col("total").mean().over(order_by=col("placed"), rows=(-6, 0))       # seven-row moving average
last_value(col("total")).ignore_nulls().over(order_by=col("placed"))

rows=(start, end) or range=(start, end) bounds the window around the current row: a negative number is that many rows before, positive that many after, 0 the current row, None unbounded.

lambdas

The list functions take little functions: keep some elements, change each one, fold the list to one value. Write them as Python lambdas:

col("tags").list().filter(lambda x: x.str().length() > 3)      # list_filter("tags", lambda x: len(x) > 3)
col("prices").list().transform(lambda p: p * 1.21)
col("xs").list().reduce(lambda acc, x: acc + x)

Your lambda runs once, while the expression is being built, and it receives an expression, not a value. Everything you do to it must build a bigger expression, which is what every operator and method here already does. The SQL variable takes your parameter's name, so lambda p: ... becomes lambda p: ... in SQL, and shadows a column called p exactly as SQL would.

The one trap: Python's own if is not SQL's. lambda x: a if use_a else b is fine, but it is Python choosing which expression to build, once, now; it does not look at the element. A condition on the element is an expression too:

# wrong: raises at build time, an expression has no truth value
col("xs").list().transform(lambda x: 0 if x < 0 else x)

# right: the SQL conditional
col("xs").list().transform(lambda x: when(x < 0).then(0).otherwise(x))

A lambda that returns a plain value is a constant body (lambda x: 1 is legal SQL); one that returns anything else is refused when you build it. The body cannot hold a subquery or an unnest: SQL itself refuses those, with its own message.

The signature must be plain positional parameters, because each one becomes a SQL variable. A default (lambda x, y=1:) would not default at all, it would be a second variable and pick a different engine overload, so it is refused, and so are *args and keyword-only parameters. A function taking no parameters is refused too: a SQL lambda has no zero-variable form, and a bare function where a value was meant is usually a call you forgot to make, col("amount") > threshold for threshold(). Any callable in expression position becomes a lambda, so one handed to something that cannot take a lambda is the engine's to refuse, which it does at bind time.

Running a plan

plan.rows(con)          # every row, as tuples
plan.first(con)         # the first row, or None
plan.to_dicts(con)      # every row, as a dict keyed by column
for row in plan.iter_rows(con): ...   # streamed in batches
plan.count(con)             # how many rows, without fetching them
plan.show(con)              # print the first ten as a table; preview(con) returns the text

arrays and dataframes

plan.to_numpy(con)      # {column: ndarray}; columns holding NULLs come back masked
plan.to_pandas(con)     # a DataFrame

Columns convert from the engine's own vectors, never through rows. In a frame, a column holding NULLs gets pandas' nullable dtype and pd.NA; one without stays a plain numpy dtype, so a clean result costs nothing extra. ENUM becomes an ordered Categorical, TIMESTAMPTZ comes back UTC‑aware, and to_pandas(con, date_as_object=True) gives dates as datetime.date. DECIMAL and HUGEINT become float64 on this path; when the exact values matter, fetch rows, which keeps Decimal and Python's int. An empty result keeps every column's dtype.

stopping a query

A Ctrl‑C while a query runs cancels it and raises KeyboardInterrupt. From another thread, con.interrupt() cancels whatever the connection is running; the query fails with InterruptError.

transactions

with con.transaction():
    plan.insert_into(con, "daily_totals")
    con.run("DELETE FROM staging")

The block is one transaction: COMMIT when it ends, ROLLBACK on any error. Statements and plans inside run on the connection as usual, so they share it.

values supplied at run time

Use param(name) where a value goes, and pass it when running:

from duckdb import param

by_region = orders.filter(col("region") == param("where"))

by_region.rows(con, parameters={"where": "emea"})
by_region.rows(con, parameters={"where": "amer"})

Every method that runs the plan also takes parameters=. A name with no value, or a value for no name, is an error.

a plan on a connection

plan.on(con) fills the connection in, so every method below takes none. In a notebook it shows its rows.

bound = orders.filter(col("total") > 1000).on(con)

bound.rows()
bound.count()
bound.to_csv("big.csv")
bound                   # prints the first rows as a table

The plan is not changed by this: plan.on(other) runs the same plan elsewhere.

Writing rows out

Straight from the engine, without passing through Python.

plan.create(con, "daily_totals")                  # a new table; returns the row count
plan.create(con, "daily_totals", replace=True)     # replacing one that exists
plan.create(con, "scratch", temporary=True)        # gone when the connection closes
plan.insert_into(con, "daily_totals")             # append; returns the row count

files

A file is written by DuckDB's COPY, and the sinks are that statement with the plan inside: copy_to takes any format the engine has, and to_parquet, to_csv, to_json fill the format in. Keyword arguments are COPY's own options under their SQL names, written as SQL writes them: a list is a column list, star() is *, a dict is a struct.

plan.to_parquet(con, "totals.parquet")                                  # [(1234,)]  what COPY returns
plan.to_csv(con, "totals.csv", header=True, delimiter="|", force_quote=star())
plan.to_json(con, "totals.json", array=True)
plan.to_parquet(con, "by_day", partition_by=["year", "month"], compression="zstd")
plan.copy_to(con, "totals.arrow", format="arrow")                        # any loaded writer
plan.copy_to(con, Path("out") / "totals.parquet")                              # no options: the engine reads the extension

(count, files), = plan.to_parquet(con, "parts", partition_by="year", return_files=True)
stats = plan.to_parquet(con, "parts", partition_by="year", return_stats=True)   # one row per file

Each returns the rows the statement returns: one row with the count, the count and the file names with return_files, or one row per file with return_stats. The engine refuses an option it does not know, by name. Options are written into the statement, so a param() cannot be one; a value from Python goes in as a literal.

The rest of the family is SQL: sql("EXPORT DATABASE 'dir' (FORMAT parquet)").rows(con), con.run("COPY FROM DATABASE a TO b"). For any other statement, run it on the connection: con.run("CREATE INDEX …") returns the number of rows changed.

Looking before you run

plan.columns(con)   # ['id', 'customer', 'total']
plan.types(con)     # ['INTEGER', 'VARCHAR', 'DECIMAL(6,2)']
plan.schema(con)    # the two together, as pairs

print(plan.render())         # the SQL, from the plan alone
print(plan.render(con))      # the SQL as it will run on this connection
print(plan.explain(con))     # how DuckDB will run it; analyze=True runs it and times each step

None of these fetch rows. columns() needs the connection only to read what the tables hold; the names a plan makes itself, through select, rename and the rest, it knows without one.

render() with no connection cannot know what the tables hold, so it neither checks names nor keeps the position of a column that with_columns replaced; that column comes last. render(con) gives the exact text rows(con) would run.

Plans inside plans

A plan can stand in for a value inside an expression:

average = orders.aggregate(col("total").mean().alias("m"))
orders.filter(col("total") > average.scalar())          # one row, one column

big = orders.filter(col("total") > 1000).select("customer")
orders.filter(col("customer").isin(big))                # one column, any rows
orders.filter(~col("customer").isin(big))

The inner plan is computed once, however many times it is used. It cannot refer to the outer row. A correlated subquery is written one of three ways: as SQL (SQL in and out); as a semi or anti join, which is what an EXISTS usually is; or, for a value per group, as an aggregate joined back, which is what a correlated scalar usually is:

orders.join(big, on="customer", how="semi")    # orders whose customer is in big
# each order against its customer's average: the aggregate once, then joined back
averages = orders.group_by("customer").agg(col("total").mean().alias("avg_total"))
orders.join(averages, on="customer").filter(col("total") > col("avg_total"))
orders.join(big, on="customer", how="anti")    # orders whose customer is not

One plan, many places

A plan holds no connection. Build it once and run it wherever its tables exist:

report = table("orders").filter(col("total") > 1000).select("id")

report.rows(production)
report.rows(staging)

Each connection reads its own tables, so the same plan is right on both even when their columns differ. Closing a connection does not affect the plans built from it.

as a macro

A plan's SQL can be the body of a DuckDB macro:

body = sql('SELECT unnest("i") AS uid').filter(col("uid") > 2)

con.run("CREATE MACRO big_ids(i) AS TABLE " + body.render())
sql("SELECT * FROM big_ids([1, 3, 9])").rows(con)   # [(3,), (9,)]

Or let the connection write the statement. An expression makes a scalar macro, a plan a table macro; parameters are names, or (name, default) pairs, and col(name) inside the body refers to one:

con.create_macro("add_up", ["a", ("b", 1)], col("a") + col("b"))
con.create_macro("big_orders", ["floor"], table("orders").filter(col("total") > col("floor")))

sql("SELECT add_up(2), * FROM big_orders(1000)").rows(con)

The body is bound when the macro is defined, not when it is rendered: a name it cannot resolve is refused by CREATE MACRO or create_macro, and what depends on the arguments' types surfaces at the first call. Macros go further than this; see Macros and Extensions.

the same plan over different relations

A plan starts from a relation; to build the same plan over another, write a function that takes the relation:

def recent(lineitem):
    return lineitem.filter(col("l_shipdate") > date(2026, 1, 1)).select("l_orderkey", "l_quantity")

recent(table("lineitem")).rows(con)
recent(sql("SELECT * FROM read_parquet('l.parquet')")).rows(con)
recent(values(sample_rows, columns=["l_orderkey", "l_shipdate", "l_quantity"])).rows(con)

A plan over table(name) already runs wherever a table of that name exists, so a function is only needed when the relation is not a table, or not always the same one. Give values its types as (name, type) pairs and the plan can answer columns() and types() with no connection at all.

What is bound, what is quoted

Values you pass never become part of the SQL text. Text, bytes and anything composite, a list, tuple or dict, are sent to the engine separately as parameters, because that is where an injection would come from; dates, times, intervals, decimals and UUIDs are bound too, so they arrive exact. Numbers, booleans and None are written as literals.

name = "'; DROP TABLE orders; --"
orders.filter(col("customer") == name).rows(con)    # WHERE ("customer" = $1); the table is fine

Table and column names are always quoted, so a name from outside your program cannot turn into SQL:

runs whatever name contains
sql(f"SELECT * FROM {name}")
one quoted name
table(name)

sql() and sql_expr() take SQL as written. Never build either from input you do not trust.

SQL in and out

Any query can be a plan, and any plan can show its SQL:

plan = sql("SELECT * FROM orders WHERE region = 'emea'")
plan.filter(col("total") > 1000).rows(con)

print(plan.render())

For a fragment inside an expression, sql_expr takes SQL text as written. That includes a whole condition: filter takes an expression, so a condition written as SQL is wrapped.

orders.filter(col("placed") > sql_expr("DATE '2026-01-01' + INTERVAL 30 DAY"))
orders.filter(sql_expr("region = 'emea' AND total > 1000"))

Correlated subqueries, recursive queries and PIVOT are written in SQL through sql(); the result is a plan like any other.

For cursors and execute, use duckdb.dbapi, the PEP 249 interface. Plans do not run on its connections; run plan.render() on a cursor instead.

Changes from the old client

What is different for code written against the old duckdb package's relational API. Code that needs the old client as it was runs on duckdb.compat.

A plan holds no connection
duckdb.sql() returns a plan and runs nothing. The old module-level sql, execute and query ran on an implicit default connection. Pass one to rows(), or put the plan on one with on().
sql() runs nothing
Whatever the text is, it is a plan until a connection runs it. The old sql() ran a statement without rows on the spot and returned None; here that is con.run(). In duckdb.compat, a row-producing CALL runs once at sql() and its rows are carried; the old relation re-ran it on every fetch.
A string inside an expression is a value
col("state") == "active" compares with the text active. The old client read it as a reference to a column named active. A column is always col(...).
A string in a verb is a column name
select("total * 2") names a column called total * 2, quoted, and the engine refuses it. The old project("total * 2") was a SQL fragment. Write col("total") * 2, or sql_expr("total * 2").
filter() takes an expression
SQL text goes through sql_expr: filter(sql_expr("total > 1000")). The old filter("total > 1000") took the text as it was.
aggregate() returns its group keys
They come first in the output. The old aggregate("sum(total)", "customer") returned the aggregate alone. select() is a projection and never groups.
Duplicate names are refused
A step that would produce one name twice, and a join whose sides share a name, are refused when the plan is resolved or run, with a message. The old client let the engine bind the first. Pass suffix= or rename before joining. Inside on the sides are l and r; there is no set_alias.
intersect() and except_() drop duplicates
They render INTERSECT and EXCEPT. The old client's were INTERSECT ALL and EXCEPT ALL. union() keeps duplicates as it did; all=False drops them.
types() is text
columns(), types() and schema() are methods and take the connection whose catalog answers. Types come back as text, DECIMAL(6,2), where the old client returned DuckDBPyType objects.
describe() is SUMMARIZE
One row per column, with the engine's statistics. The old describe() gave one row per statistic (count, mean, stddev, min, max, median) and a column per input column.
No len(), shape or iteration
A plan cannot count or iterate itself. count(con) counts; rows(con) and iter_rows(con) iterate; for row in plan raises.
Fetching and writing
fetchall(), fetchone(), fetchnumpy() and fetchdf() are rows(con), first(con), to_numpy(con) and to_pandas(con). sql_query() is render(). write_csv(sep=...) and write_parquet() are to_csv and to_parquet, with COPY's own option names.
Expression names
ColumnExpression, ConstantExpression, FunctionExpression, StarExpression, SQLExpression and CoalesceOperator are col, lit, fn, star, sql_expr and coalesce. CaseExpression(cond, value) is when(cond).then(value). isnull and isnotnull are is_null and is_not_null; isnotin is ~col(...).isin(...).
No replacement scan
A DataFrame or a plan in scope is not a table: sql("SELECT * FROM df") does not find it. The implicit FROM df scan of local DataFrames and relations is not there yet.

If a column does not exist or a type will not convert, the error comes from DuckDB, with the message it would give any client.
